# The Goat Programming Language

[![Build and test](https://github.com/kniazkov/g0at/actions/workflows/build_and_test.yml/badge.svg)](https://github.com/kniazkov/g0at/actions/workflows/build_and_test.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE.txt)

**Goat is an experimental programming language implemented in C, with its own compiler and bytecode virtual machine.**

Created by Ivan Kniazkov, the project is a hands-on exploration of language implementation: parsing, lexical scope, closures, object models, memory management, and static analysis. It also serves as a working demonstration for technical talks and discussions. The implementation is deliberately open to inspection: you can print the generated bytecode, regenerate source from the syntax tree, and visualize that tree.

Goat is a work in progress. Its language and implementation evolve together; the examples and tests in this repository describe the currently supported behavior.

## A taste of Goat

Functions are values, and an inner function can capture its enclosing scope:

```text
const add = func(a) {
    return func(b) {
        return a + b
    }
}

const add_two = add(2)
print(add_two(3))
```

Output: `5`.

Recursion and conditional branches work with the same function syntax:

```text
const fibonacci = func(n) {
    if (n < 1) {
        return 0
    }
    else if (n < 2) {
        return 1
    }
    else {
        return fibonacci(n - 1) + fibonacci(n - 2)
    }
}

print(fibonacci(10))
```

Output: `55`.

A block can also produce an object whose properties come from its local bindings:

```text
var point = {
    x = 20
    y = 10
    sum = x + y
}
print(point)
```

See [the functional tests](test) for more examples, including nested objects, closures that update outer variables, and functions that return functions.

## What is implemented

### Language and runtime

- Dynamically typed values: integers, real numbers, strings, booleans, `null`, functions, and user-defined objects.
- Variable and constant declarations with `var` and `const`, assignment, and implicit variable declarations.
- Arithmetic operators `+`, `-`, `*`, `/`, `%`, and `**`, string concatenation, and comparisons with `<` and `>`.
- Parenthesized expressions and operator precedence.
- Lexical scopes, first-class functions, arguments, closures, recursion, and `return`.
- `if` / `else`, including nested branches and block bodies.
- Block-based object construction and a runtime object model with prototype lookup.
- A small built-in environment: `print`, `sign`, `sqrt`, `atan`, and `pi`.
- UTF-8 source-file input and English/Russian compiler messages.

### Implementation and inspection tools

- A handwritten scanner and a parser that reduces grouped tokens into an abstract syntax tree (AST).
- AST nodes implemented as C structures with virtual method tables for analysis, code generation, and visualization.
- Semantic analysis that builds lexical scopes and binds variable references to declarations.
- An initial abstract interpreter with a value lattice, including constants, integer ranges, and operations for combining abstract values. Control-flow analysis is still under development.
- Bytecode generation, code/data linking, a textual bytecode listing, and a stack-based virtual machine.
- Arena allocation for compiler data, reference counting for runtime objects, and a mark-and-sweep collector.
- AST export to PNG or SVG through Graphviz and source regeneration from the AST.
- A memory-accounting mode enabled by the current CMake configuration, plus unit and functional test runners.

The implementation is not a complete language specification. For example, loops are not implemented yet, and the VM contains comparison instructions that are not all exposed by the parser. Static analysis is experimental and should not be treated as a complete correctness checker.

## Build and run

### Linux

Requirements:

- GCC, GNU Make, and Bash.
- CMake 3.10 or newer.
- The standard C development libraries, including pthread and libm.
- Optional: Graphviz (`dot` on `PATH`) for AST images.

From the repository root:

```bash
git clone https://github.com/kniazkov/g0at.git
cd g0at
bash build.sh
./goat example/hello_world.goat
```

The build script creates `goat` in the repository root, runs the unit tests, and then runs the functional tests if the unit tests pass. The included example prints `it works!`.

To build individual targets directly:

```bash
mkdir -p build
(cd build && cmake ../src)
cmake --build build --target goat
cmake --build build --target unit_testing
./build/goat example/hello_world.goat
```

### Windows (MinGW)

Install CMake and a MinGW toolchain with GCC, `mingw32-make`, and pthread support available on `PATH`. From a command prompt in the repository root, run:

```bat
build_mingw.cmd
goat.exe example\hello_world.goat
```

This script builds the interpreter and runs both test suites. GitHub Actions currently exercises the Linux build.

## Inspect a program

The following commands assume the root-level executable produced by `build.sh`:

```bash
./goat --print-bytecode test/currying/program.goat
./goat --print-source-code test/fibonacci_blocks/program.goat
./goat --print-graph ast.svg test/fibonacci_blocks/program.goat
./goat --enable-warnings --lang en example/hello_world.goat
```

These inspection options also execute the program after compilation. Graph output requires Graphviz; both `.svg` and `.png` are supported.

| Option | Purpose |
| --- | --- |
| `--print-bytecode` | Print the generated instructions and referenced static data. |
| `--print-source-code` | Print source regenerated from the analyzed AST. |
| `--print-graph <file>` | Render the AST as PNG or SVG using Graphviz. |
| `-w`, `--enable-warnings` | Enable compiler warnings. |
| `-l`, `--lang`, `--language <lang>` | Select diagnostic language: `en` or `ru`. |
| `-h`, `--help`, `/?` | Show command-line help. |

The `GOAT_LANGUAGE` environment variable can also select the diagnostic language.

## How it works

The compilation and execution pipeline is coordinated in [`src/cli/launcher.c`](src/cli/launcher.c):

1. Read a UTF-8 source file and scan it into tokens.
2. Group brackets and apply parser reduction rules to build the AST.
3. Assign scopes, bind names, and perform abstract interpretation.
4. Optionally regenerate source or render the analyzed AST.
5. Generate bytecode, including deferred function bodies, and link code with static data.
6. Release the compiler's AST and execute the bytecode in the VM.

Runtime values share an object interface. Execution contexts hold bindings, function objects retain the context needed by closures, and the VM operates on an object stack. Compiler nodes and runtime objects are separate representations, so the syntax tree does not have to remain alive while a program runs.

## Testing

`bash build.sh` runs both suites. To run them separately after building with CMake:

```bash
./build/unit_testing
gcc src/functional_testing.c -o build/functional_testing
(cd test && ../build/functional_testing ../build/goat list.txt)
```

Each functional test has a directory containing `program.goat` and an `expected_output.txt` and/or `expected_error.txt` file. Add its directory name to [`test/list.txt`](test/list.txt) to include it in the suite.

When extending the language, keep parsing, AST behavior, bytecode generation, and runtime semantics consistent, and add a focused regression test for the new behavior. The existing tests are useful executable examples, but do not cover every subsystem or edge case.
