# Политика GC по выделениям (#638)

Политика принадлежит процессу. С #639 обычные CLI-запуски исходников, архивов
и модулей (включая поддерживаемый native) и REPL включают её с минимумом 64 КиБ.
Workers наследуют протокол исполнения. Compile-only не исполняет программу.
Embedding сохраняет явное включение: create_process/run не предполагают, что
C-local ссылки host опубликованы. CLI владеет своим процессом исключительно.
`configure_gc_policy(process, minimum_bytes, exclusive_host)` требует простоя,
model lock и обещания исключительного владения host во всех последующих run.
Во время execution/session, collection, release drain и destruction настройка
запрещена. Нулевой минимум выключает и очищает политику. Успешная настройка
сбрасывает счётчики и измеряет исходную активную кучу. Рекомендуемый минимум
`GC_POLICY_DEFAULT_MIN_BYTES` — 64 КиБ; сам по себе он ничего не включает.

## Учёт байтов

Долг учитывает логическую активацию managed-объектов через существующее измерение
`gc_owned_payload`, положительный рост ёмкости массивов, полей объектов
(ячейки, векторы, индекс) и хранилища StringBuilder, включая копирование.
Это собственная память объекта с оболочкой, без памяти объектов по ссылкам.
Повторная активация оболочки из пула учитывается заново даже без malloc.
Освобождения и DECREF не уменьшают долг: короткоживущие объекты тоже создают
нагрузку. Нулевое начисление не увеличивает число событий.

Это не сумма malloc и не RSS. Исключены временные буферы преобразования/печати,
неуправляемые выделения компилятора/native, метаданные process/thread/context,
вспомогательные root/cache-структуры, заголовки аллокатора, общие метаданные
модулей и последующий рост access-descriptor/transfer-векторов вне этих hooks.
Первичная активация включает собственные метаданные, измеренные в этот момент.
Помещение в пул не начисляет долг. Hooks не выделяют память, не публикуют корни
и не запускают tracing; они используют правила сериализации модели.
Долг, счётчики событий/сборок, суммы измерений кучи и удвоение порога насыщаются
на `SIZE_MAX`, а не переполняются до малого значения.

## Порог и обратная связь

Исходный бюджет: `max(minimum_bytes, active_bytes / 2)`. После завершённой сборки,
включая явную и финальную, `live` — активные байты после прохода. Полезной считается
сборка, убравшая ненулевое количество и не менее `ceil(before / 8)` активных байтов.
Это выход из активного графа, а не возврат памяти аллокатору: оболочки могут
остаться в ограниченных пулах.

Полезная сборка уменьшает показатель backoff на один до нуля; бесполезная
увеличивает на один до четырёх. Новый бюджет:
`max(minimum_bytes, live / 2) * 2^backoff`, с насыщением при удвоении.
Завершённая сборка очищает долг и pending, но сохраняет общий счётчик событий.
Интервал в байтах обеспечивает гистерезис; это не интервал времени и не гарантия
максимальной паузы. Полный синхронный проход по-прежнему обходит живой граф.

Достижение бюджета фиксирует один pending-запрос. Следующий poll существующей
сессии преобразует его в обычный отложенный запрос; допуск определяет только
прежний протокол участников, корней и lock. Отказ poll сохраняет запрос.
Завершение сессии без сборки переносит долг/pending в следующую сессию.
Явные запросы работают и ниже бюджета. Статистика для работы политики не нужна.
При opt-in VM и module run создают обычные GC-сессии без принуждения на каждой
инструкции; workers и поддерживаемые native-границы используют прежний протокол.
Произвольный callback всё ещё может откладывать сборку неограниченно:
см. [аудит границ](gc-boundary-audit.md).

## Проверки

Восемь `core.gc_policy.*` входят в `gc_acceptance_runners` и метку
`gc-acceptance`, уже запускаемую Debug/Release CI на Linux/Windows.
Проверяются точные границы порога/полезности, насыщение, изоляция процессов,
повторное использование пулов, рост изменяемой памяти, отложенные запросы между
сессиями, повторные VM run, worker/join/исключения, module run и привязанный
scalar-v1 native adapter с заимствованной строкой. Нагрузки не включают force mode
и не инъецируют запрос сборки. Контроль с выключенной политикой проверяет defaults.

Linux x86-64 Debug: живой граф 65 976 активных байтов, 16 384 повторных активации
скаляра из пула — четыре сборки, итоговый бюджет 527 808 байтов. Проверяется защита
от постоянного обхода большого неизменного графа. Циклическая нагрузка проверяет
ограничения active objects/bytes и прогресс сборок в десяти точках каждого run.
Критерии основаны на счётчиках и порогах, не времени исполнения. Проверяются
пулы, корни, очистка и баланс аллокатора. Размеры байтов зависят от платформы;
приведённые измерения не являются переносимыми константами.
Pressure/OOM, длительный стресс и итоговая приёмка остаются в #640–#643; эта работа не объявляет их завершёнными.

## Приёмка CLI (#639)

CLI настраивает политику один раз до исполнения; REPL сохраняет её между строками
и после исключений. Используется существующий API под lock, нового CLI-флага
настройки нет. Host может выбрать другой минимум или выключить политику при
простое через configure_gc_policy. Ограничения допуска, финальная сборка и
фатальный OOM-контракт не меняются.

core.gc_cli компилируют настоящие исходники launcher с наблюдающими обёртками run
и настоящую реализацию статистики с наблюдателем проходов. Тесты не включают
политику, не меняют бюджет, не публикуют корни и не запрашивают GC. Проверяются
штатный минимум 64 КиБ при входе, более десяти сборок внутри исполнения, менее
1 МиБ active payload перед каждым проходом и 256 КиБ после него, очистка сессии.
Покрыты исходник, сохранённый архив, native-required с успешными native-вызовами,
workers и постоянная REPL-сессия с исключением. Обычный тест вывода REPL отдельно
проверяет, что сохранённое замыкание возвращает 42 до и после восстановления
от исключения. Измеряется собственная managed-память, не RSS; синхронные паузы
и задержки в исключённых callbacks по-прежнему не ограничены.
