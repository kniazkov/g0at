# Приёмка протокола GC (#637)

Актуальный контракт допуска и владения описан в [аудите границ](gc-boundary-audit.md).
Этот набор проверяет production-протокол с принудительными запросами. Он не вводит
пороги выделений, pressure или восстановление после OOM. Автоматическая политика
остаётся в #638/#639 после принятия CI этого этапа.

## Воспроизводимый набор

```sh
cmake --build build --parallel 4 --target gc_acceptance_runners
ctest --test-dir build --output-on-failure -L gc-acceptance --no-tests=error
```

Метка объединяет все `core.gc_*`, `core.thread_memory.*` и
`component.init_snapshot.*` (307 тестов на момент добавления). Target собирает все
нужные runners, включая shared fixture scalar-v2. Существующая матрица Linux
GCC/Clang и Windows MSYS2 запускает набор в Debug и Release. Пустой набор — ошибка.
Одних Debug integration tests недостаточно: многие scalar/protocol cases не имеют
метки `integration`, а явный список Release runners не охватывал весь GC.

## Смешанная нагрузка

`core.gc_acceptance.vm` и `.native` выполняют одну модульную программу. В native
режиме bridge связан с адаптером scalar-v1; в VM режиме исполняется его Goat-тело.
Один процесс последовательно запускает четыре standalone driver с сохранённым
модулем: успех, пойманная ошибка worker, снова успех, непойманная ошибка worker и
teardown. В каждом run один worker работает, пока главный поток блокируется в
настоящем `join`. Sleeps и ручной публикации тестовых участников нет: worker
дожидается join и проверяет production-публикацию главного потока.

В каждой из 256 итераций создаются мёртвые циклы, вызывается конструктор, вложенная
функция возвращает heap-значение через `finally`, выбрасывается и перехватывается
heap-исключение, bridge получает временную строку, выполняются clone/flat.
Проверяются постоянный живой цикл, поля экземпляра, результаты и точные счётчики
конструкторов/finally. Адаптер проверяет borrowed строку до и после сборки через
`gc_session_request/poll` при штатной публикации native-вызова. Этот C-адаптер
связывается внутри процесса; загрузку shared-library scalar-v2 проверяют другие
тесты того же набора, а не этот bridge.

Каждая итерация проверяет последний снимок сборки внутри run. Непроверенный
checkpoint callback запрашивает GC, восемь раз отпускает/берёт model mutex и
требует `GC_DEFERRED`, сохранения запроса и неизменности счётчика сборок. Следующий
checkpoint обязан увидеть более десяти новых сборок; последний запрос также
обслуживается до завершающей сборки run. Прямого вызова collector или подделки
participant из callback нет.

Embedding caller выбирает инструкцию ноль для каждого нового standalone image.
После пойманной ошибки следующий run использует тот же контекст. Непойманная
ошибка разматывает входной контекст и завершается teardown: не обещается неявный
restart размотанного контекста. После каждого run проверяются session/execution,
корни, токены потоков, waiter/reaper state и глубина lock. Байткод модуля и drivers
неизменен; после teardown проверяется полный баланс аллокатора.

`core.gc_acceptance.native-error` возвращает неверный native-результат на вызове
bridge 128 после 127 полных итераций. Проверяются terminal backend failure,
отсутствие retry/fallback, очистка токенов/корней и отказ следующего run без
повторного исполнения bridge. Native retry и host cancellation проверяются
scalar/continuation сценариями того же набора.

## Бюджеты памяти

Ограничения относятся к этому постоянному графу, а не любым программам Goat или RSS:

| На каждом checkpoint | Граница |
|---|---|
| Последнее после GC и текущее число активных объектов | Менее 512 |
| Прямой active payload после GC | Менее 256 КиБ |
| Таблицы корней/кеша | Менее 32 КиБ |
| Текущий и последний sampled pooled payload | Не более `GOAT_POOL_BYTE_LIMIT` (512 КиБ) |
| Активные корни / зарезервированные slots | Менее 64 / не более 64 |
| После прогрева (итерация 16) | Не более +16 объектов, +16 КиБ active/pool payload, +1 КиБ auxiliary относительно прогрева |

Сравнение с прогревом осмысленно благодаря постоянной структуре итерации: внутри
run не растут пользовательский контейнер, глубина вызовов или история workers.
Небольшой постоянный запас учитывает повторное использование scalars/кеша и
различия платформенных размеров. Тест выводит пики и счётчики сборок для каждого
run. Таймаут CTest 90 с ограничивает зависание теста, но не обещает длительность
паузы GC. Непроверенный host callback всё ещё может задерживать сборку неограниченно.

## Доказательства и условия приёмки

| Критерий #552 / #618 | Проверки единого набора |
|---|---|
| Сборки при смешанном исполнении, ограниченный мусор | `core.gc_acceptance.*`: четыре run, 1024 checkpoint на режим |
| Временные значения, finally, конструкторы, VM/native модулей | Смешанный workload; `core.gc_continuation.*`, `component.init_snapshot.*`, `core.gc_runtime*` |
| Startup/join/result/reap workers | Смешанный workload, dispatch/native-startup/thread-memory |
| Блокирующие I/O/native, отсутствие replay при ошибке/retry/отмене | gc_io, scalar-native/native-wait/runtime-native, continuation |
| Lazy module waits, изменяемый граф, повтор observation/copy | `core.gc_module_initialization.*` |
| Deferred request, рекурсивный C, отказ, повторный run | Смешанный workload, embedding/protocol/runtime |
| Корни/refcounts/pools, teardown | ownership/roots/refcounts/sweep/mark/release/pools/stats и баланс fixture |

Два локальных отрицательных контроля подтверждают чувствительность новой нагрузки:
удаление маркировки pending-value из finally даёт ASan use-after-free в
`FINALLY_END`; отключение публикации join нарушает проверку допуска worker.
Обе временные production-мутации отменены перед итоговым прогоном и не входят в PR.

Исторический статус #552 не заменяет приёмку. Завершение #618 и разблокировка
автоматической политики требуют полной матрицы и принятого PR; одного этого
документа недостаточно. #645 остаётся отдельным исследованием
intermittent ELF: диагностический CI не воспроизвёл исходную ошибку. Этот набор
не объявляет её исправленной. Длительный стресс включённой автоматической политики
и pressure/OOM остаётся в #640–#643. Прогоны с отключённым LSan указываются отдельно
от проверки собственного баланса аллокатора.
