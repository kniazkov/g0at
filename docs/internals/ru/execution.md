# Байткод, объекты и исполнение

[Contents](index.md) · [English](../en/execution.md)

## Генерация заканчивается неизменяемым образом

Узлы графа создают инструкции через `code_builder_t`, константы — через
`data_builder_t`. link_code_and_data() собирает образ байткода. В `src/vm/bytecode.h`
определены записи формата фиксированной ширины; `image.c` проверяет количества,
смещения и инструкции. Это не произвольный дамп C-объектов. decode_bytecode_image()
копирует недоверенные байты в выровненную память и проверяет их перед использованием.

Образ остаётся неизменяемым. Нативные привязки, идентичности деклараций и кеши живут
в оболочке или объектах процесса. borrow_bytecode_image() создаёт отдельную runtime-
оболочку без копирования образа: владелец обязан сохранить его до уничтожения
оболочки и всех зависимых объектов. Файлы модуля разделяют один образ, а не копируют
его при каждом include.

## У VM и модели разные обязанности

run() выполняет диспетчеризацию кодов операций в `src/vm/vm.c`. Модель в `src/model`
предоставляет объекты, контексты, стеки, функции, свойства, идентичности доступа и
исключения. `process_t` — владелец Goat runtime, не дескриптор дочернего процесса ОС
из `lib/process`. Контекст связывает кадры исполнения и лексические данные; функция
сохраняет окружение замыкания. Структурные родители AST здесь уже не участвуют.

`operation_result_t` владеет ненулевым обычным или брошенным значением. Goat null —
полноценный объект; C NULL не заменяет брошенный null. При переходе через вызов или
инициализацию модуля нужно сохранять исключение и связанную сохранённую трассу.
Корректный языковой exit завершает процесс ОС; run() не возвращается обычным путём
через очистку хоста. Проверять это нужно в дочернем процессе.

## Ссылки и сборка мусора дополняют друг друга

INCREF/DECREF учитывают владеющие ссылки runtime. Реализации типов могут помещать
очищенные оболочки в пулы, а статические одиночные объекты не обязаны иметь обычный
изменяемый счётчик. Для циклов нужна сборка по достижимости дополнительно к счётчикам.
collect_garbage() помечает корни файлов модулей, каталог запуска, кеши строк, явные
корни хоста, цепочки контекстов всех потоков, ожидающие значения, исключения и стеки
операндов, затем очищает список объектов процесса.

Локальный C-указатель сам по себе не является корнем GC. add_gc_root() защищает
внешнее значение до remove_gc_root(); повторная регистрация работает как множество,
а не счётчик. Нельзя самостоятельно снять корень, ещё нужный другому владельцу.
Нативные дескрипторы имеют отдельную цепочку владения, сохраняющую загруженный код.

## Потоки и инициализация

Потоки программы принадлежат одному runtime-процессу. `execution_mutex` защищает
короткие операции модели; блокирующие ожидания не должны удерживать его. Отдельная
рекурсивная блокировка сериализует инициализацию модулей. join_program_thread()
запрещает ожидание себя, циклические ожидания и ожидания при динамической инициализации.
Одного API потоков ОС недостаточно для этих языковых контрактов.

run_module_file() — внешний вход для подготовленных файлов, не повторный вход при
активном run. Инициализация сохраняет успех или исходную ошибку в общем состоянии
файла. Include/import повторно используют это состояние, а не исполняют исходник
заново; см. [модули](modules.md).

## Проверять свойство на его уровне

`core.unit` проверяет контракты VM/модели, включая владение и исключения;
`core.functional` — видимое поведение языка. Сценарии модулей проверяют постоянные
области и однократную инициализацию. Нативные тесты должны проверять и выбранный
нативный путь, и fallback. Равенство вывода не доказывает освобождение GC,
неизменяемость образа или отсутствие повторной инициализации.
