# Итоговый аудит GC и проверки CI (#643)

Автоматическая сборка по выделениям включена в CLI/REPL, включая module/native.
Embedding включает её явно под model lock неисполняющегося процесса. Контракты:
[политика](gc-allocation-policy.md), [границы](gc-boundary-audit.md),
[pressure](gc-memory-pressure.md), [фатальный OOM](gc-fatal-oom.md).
Принудительная сборка на границах инструкций — отдельный тестовый режим,
по умолчанию выключенный.

## Воспроизводимая приёмка с лимитами

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 4 --target gc_acceptance_runners
cmake -DBUILD_DIR=build -P scripts/check_gc_acceptance.cmake
```

Скрипт сверяет `scripts/gc-acceptance-tests.txt` с реальным списком CTest.
Каждый обязательный тест должен существовать, иметь метку `gc-acceptance`,
положительный timeout не больше 180 секунд и ровно одну группу исполнения.
Потеря регистрации или метки останавливает приёмку до запуска. Новые тесты
допускаются; удаление требует явного пересмотра manifest и аудита.

Обязательны 328 регистраций: 325 `gc-regression` и три `gc-stress`.
Группы исполняются последовательно, общий deadline — 900 и 600 секунд.
CI даёт шагу приёмки 27 минут вместе со сборкой runners. Автоматических retry
нет; timeout означает ошибку. Логи `gc-regression.log` и `gc-stress.log`
сохраняются в build-каталоге и загружаются в артефакты CI, включая успешные
стресс-измерения. Зависимость archive-теста от setup fixture CTest сохранена.

| Обязательная конфигурация | Проверки |
|---|---|
| Linux x86_64/aarch64, GCC/Clang | Debug и Release, обе группы |
| Windows MINGW32/MINGW64/UCRT64 | Debug и Release, обе группы |
| Linux x86_64, GCC и Clang | Отдельная полная сборка runtime с ASan/UBSan, обе группы, job не больше 30 минут |
| Инъекция отказов выделения | Прежние отдельные fault-сборки, `gc-oom`: 19 тестов Linux / 18 Windows |

Санитайзеры инструментируют сам runtime и runners, а не только генерируемый код.
UBSan останавливает исполнение при первой ошибке. LSan явно отключён: это не
успешная проверка leak sanitizer. Баланс аллокатора проверяется самими fixtures.
Фатальный OOM намеренно завершает процесс без teardown и проверяется отдельными
подпроцессами; его нельзя интерпретировать как обычную утечку санитайзера.

## Доказательства, ограничения и закрытие

Последний коммит PR #656 `6e96c268` прошёл 14/14 проверок: 11 основных и три
module-format. Первоначальная ошибка ссылок Doxygen исправлена. Последующий
сбой GitHub startup не создал jobs и не считался успешной приёмкой.
Успешный повтор: [run 45649602762](https://github.com/kniazkov/g0at/actions/runs/45649602762).
Новая sanitizer-матрица и manifest требуют собственного полного CI этого PR.
Исторические измерения отдельных этапов сохраняются в архиве issues.

Невозвращающийся C-callback может откладывать GC неограниченно. Учёт payload не
равен RSS или всем malloc. Сборка остаётся полным синхронным проходом; бюджеты
фиксированной нагрузки не являются SLA приложения. Embedding обязан соблюдать
контракты idle-конфигурации, model lock и владения.

[#645](https://github.com/kniazkov/g0at/issues/645) остаётся инфраструктурным
блокером закрытия всей программы: поздний ELF probe получил `CHILD_IO_ERROR`,
`cleanup=EIO` при получении ответа supervisor. Причину старого общего сообщения
задним числом установить нельзя. Успешные повторы и исправление comparator UB
не доказывают исправления этого отказа. Здесь нет retry/skip или увеличения
таймаутов, скрывающих его. Следующий шаг — исследовать потерю control reply и
статус supervisor по доказательствам, уже сохранённым в #645.

Реализация по #642 включительно принята. #643 принимается только после полного
CI и слияния этого PR; #542/#555 остаются открытыми до разрешения #645.
Исторические пункты чеклиста — архив доказательств, а не дополнительные активные
задачи или действующие ограничения runtime.
