# Тестирование реализации

[Содержание](index.md) · [English](../en/testing.md) · [Анализ ветвей](static-analysis.md)

## Что проверяется

[Раннер анализа](https://github.com/kniazkov/g0at/blob/master/test/src/analysis/analysis_testing.c) разбирает исходник
Goat и вызывает analyze() со сборщиком наблюдений. Он проверяет решения
анализатора, не исполняя полученный байткод. В примерах ветвления наблюдаемый факт —
событие `ANALYSIS_UNREACHABLE` у корня пропущенного поддерева. Правильный текст,
напечатанный программой, сам по себе не доказывает наличие такого вывода.

Вход и эталон находятся в разных файлах `test/data/analysis/`:

- `<имя>.goat` — исходная программа.
- `<имя>.expect` — вручную заданные утверждения о событиях анализа.
- `list.txt` — список пар, которые запускает раннер.

Doxygen вставляет эти файлы напрямую. Проверка документации дополнительно
требует, чтобы у каждого включённого исходника были файл ожиданий и запись в
`list.txt`. Обычные базовые тесты Debug запускают раннер анализа на Linux и
Windows; в CTest тот же набор доступен как `core.analysis`.

## Как читать ожидание достижимости

Возьмём ожидания [dead_known_true](https://github.com/kniazkov/g0at/blob/master/test/data/analysis/dead_known_true.expect):

<!--! \verbinclude dead_known_true.expect -->

В строке шесть полей: режим совпадения, вид события, строка исходника, строка
объявления, селектор переменной и ожидаемое значение. Для `unreachable`
последние три поля должны быть `0 - -`: у события нет объявления и значения.

`one unreachable 3 0 - -` требует ровно одно событие на строке исходника 3.
`none unreachable 2 0 - -` запрещает это событие на строке 2. Нулевая строка
исходника означает любое расположение, поэтому пример неизвестного условия
запрещает события недостижимости во всём примере. Общий раннер также поддерживает
`last`: требуется хотя бы одно совпадение, и проверяется последнее значение;
в примерах достижимости используются `one` и `none`.

Ожидаемый ответ не перегенерируется текущим анализатором. Иначе неправильная
реализация могла бы переписать собственный эталон и выглядеть правильной.
Проверка и недостижимой ветки, и той, которая должна остаться достижимой, ловит
ошибки, которые одна положительная проверка может пропустить.

## Запуск и диагностика

Из корня репозитория:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 4 --target analysis_testing
ctest --test-dir build --output-on-failure -R '^core[.]analysis$'
```

Либо напрямую: `build/analysis_testing test/data/analysis` (на Windows исполняемый
файл — `build/analysis_testing.exe`). Запускается весь список анализа, включая
все примеры из обзора ветвлений.

При несовпадении выводятся имя файла `.expect`, номер строки ожидания, селектор
и число совпавших событий, затем — наблюдавшиеся события анализа. Начинайте с
позиции в исходнике: событие недостижимости относится к корню пропущенного
поддерева, а не к каждому его потомку. Изменяя пример, проверяйте селекторы строк
вместе с ожидаемой семантикой. Не меняйте эталон только ради устранения падения.

run_case() сохраняет исходник, AST и сборщик до окончания проверок и вывода
диагностики, затем освобождает их и проверяет баланс выделений памяти. Пустой
или некорректный набор ожиданий приводит к провалу, как и пустой или некорректный
список тестов.

Эти проверки подтверждают явно заданные свойства анализа. Они не доказывают
произвольный поясняющий текст, поведение байткода или все случаи применения
правила: ревью и отдельные тесты исполнения по-прежнему необходимы.


## Остальная система тестов

| Слой | Код и данные | Что устанавливает |
| --- | --- | --- |
| Unit | `test/src/unit` | Локальные алгоритмы, модель/VM и владение |
| Component | `test/src/component` | Реальная подсистема через управляемый хост |
| Analysis | `test/src/analysis`, `test/data/analysis` | Явные события фактов, эффектов и допустимости |
| Functional | `test/src/functional`, `test/data/functional` | Наблюдаемые результаты языка |
| Сценарии | Исполнители `test/src`, `test/support`, `test/data/<family>` | Процессы, файлы, библиотеки и сквозные транзакции |
| Форматы / генераторы | Независимые helpers, сохранённые векторы, схемы и UCD | Байтовые контракты, неверный ввод и воспроизводимость |

Точные регистрации и метки находятся в `test/CTestLists.cmake`. Случай CTest может
включать много утверждений: число случаев не равно числу всех проверок. SKIP также
не равен PASS. Недоступность на платформе сообщается явно, а не маскируется успехом.

## Жизненный цикл сценария и независимые эталоны

scenario_create() создаёт эксклюзивный рабочий каталог внутри дерева сборки, не меняет
данные тестов и сохраняет каталог при ошибке или явном запросе. scenario_execute()
даёт телу один монотонный дедлайн, сохраняет команды и бинарный вывод дочерних
процессов, выполняет отложенную очистку в обратном порядке. Тело работает кооперативно:
произвольные аварии и зависания проверяются в контролируемом дочернем процессе.
Вложенный этап не продлевает внешний дедлайн. scenario_finish() может превратить
успешное тело в провал, если собственные ресурсы не удалось очистить.

`test/support/format_*` предоставляет независимые эталоны JSON, ZIP, бинарного формата
и хеша; `process_watch` наблюдает закреплённые идентичности ОС без production-supervisor.
Это не даёт общей ошибке writer/reader подтвердить саму себя. Отрицательные контрольные
проверки намеренно портят вход или ожидание и обязаны проваливаться. У замороженных
образцов описано происхождение; нельзя пересоздавать ожидаемый ответ проверяемой
реализацией только ради успешного сравнения.

Сохранённая диагностика должна отвечать: какая команда, как завершилась, какие байты
stdout/stderr, какое утверждение и какая операция очистки отказали? Начинай с этого,
а не с перезапуска нестабильного случая. Неверный вывод, тайм-аут, авария и ошибка очистки
требуют разных исправлений. Правила сравнения зависят от helper: модульный исполнитель
сохраняет длины байтов и нормализует CRLF, но не произвольные пробелы.

## Локальный выбор и CI

Из корня, для одноконфигурационной Debug-сборки:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 4
ctest --test-dir build -N
ctest --test-dir build --output-on-failure -L core
ctest --test-dir build --output-on-failure -R '^integration[.]module_delivery[.]execution$'
bash scripts/check_docs.sh
```

Для многоконфигурационного генератора добавь `-C Debug`. `-R` выбирает имя случая,
`-L` — метку; сначала посмотри `-N`, не предполагая одинаковый набор на всех платформах.
Собери цели, нужные выбранному набору. Регистрация сценариев разрешает параллельные
изолированные случаи, соблюдает блокировки ресурсов и сериализует замеры производительности;
старые регистрации наборов остаются последовательными.

Скрипты сборки поддерживают разделённые фазы build/test для CI. Актуальные комбинации
компиляторов/платформ и артефакты определяют workflows; локальный Linux не подтверждает
поведение Windows-загрузчика и дескрипторов процессов. Для документации локально нужны
Doxygen и связанные примеры; CI дополнительно ловит платформенные регрессии компиляции
и интеграции. Для проверки представления открой HTML-артефакт Doxygen, одного кода
завершения задания недостаточно.

## Добавить полезный тест

Выбери самый низкий слой, наблюдающий обещанное свойство, задай проверенный эталон и
включи тест в обычный манифест/CTest. Проверь разрешённый случай и соседний запрещённый
или неизвестный. Для объяснения анализа проверяй событие; для времени жизни — ресурс;
для нативной скорости — исполнение уже скомпилированного кода. Связывай примеры и
документацию, чтобы при изменении исходника пересматривать построчные селекторы.
