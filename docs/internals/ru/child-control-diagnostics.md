# Потеря ответа Linux supervisor (#645)

Статус дочерней программы и статус её supervisor — разные сведения. Supervisor
сначала очищает дерево процессов, затем отправляет один ответ `SOCK_SEQPACKET`.
Раньше обе точки отправки игнорировали возможный `EINTR`, а вызывающая сторона
сводила EOF, ошибки recv и истечение срока ожидания к общему `cleanup=EIO`.
Короткий пакет также не распознавался как ошибка протокола.

Теперь повторяется **только** системный вызов send, прерванный с `EINTR`.
Компилятор и ребёнок не перезапускаются, cleanup не повторяется, окончательная
ошибка отправки не превращается в успех. Обычный ответ и статус очистки сохранены.

Новые Linux-поля `child_result_t`:

| Поле | Значение |
|---|---|
| `control_error` | 0 без транспортной ошибки; `EPIPE` при EOF без ответа, `EPROTO` для короткого пакета, конкретный errno recv, `ETIMEDOUT` при истечении срока ожидания cleanup reply |
| `supervisor_reaped` | Получен ли реальный статус supervisor через waitpid |
| `supervisor_status` | Raw Linux wait status, только при `supervisor_reaped=true`; декодируется WIFEXITED/WEXITSTATUS либо WIFSIGNALED/WTERMSIG |

На других платформах эти поля нулевые. `system_error` сохраняет прежний смысл
ошибки запуска/системного вызова; `signal_number` относится к ребёнку, не supervisor.
`cleanup_error=EIO` остаётся ошибкой, если полный ответ не подтвердил cleanup.
Диагностика native toolchain включает новые поля. Внутренний cleanup-service
передаёт одну и ту же пересобранную структуру на обеих сторонах; формат модулей
Goat и scalar ABI не меняются.

При отказе канала статус supervisor запрашивается без блокировки: процесс ещё
может жить/завершаться, либо embedding SIGCHLD handler уже забрал его статус.
`supervisor_reaped=0` означает отсутствие сведений, а не успешный выход. Нет
новой гарантии очистки дерева при неожиданном убийстве supervisor. Окружение
и аргументы исполняемого файла в эту диагностику не выводятся.

## Постоянные тесты и доказательства

`integration.child_control.*` линкует отдельную Linux-реализацию с compile-time
hooks; в production нет переключателя через окружение или публичного тестового API.
Отказы вставляются только при доставке итогового ответа, после настоящей очистки
дерева ребёнка. Режимы: `ok`, `eintr`, `eof`, `signal`, `short`, `send-error`,
`receive-error`, `launch-error`. Проверяются отказ без ложного успеха, конкретные
ошибки транспорта, доступный статус supervisor, неизменность повторного wait и
баланс аллокатора. Ребёнок — `/bin/true`; launch-error запускает отсутствующий путь.

```sh
cmake --build build --target child_process_scenarios
ctest --test-dir build -L child-control --no-tests=error --output-on-failure
```

Тесты входят в обычный Linux Debug/Release integration. Диагностический workflow
повторяет каждый отказ 25 раз, затем выполняет 50 настоящих StringBuilder/native
прогонов: 5 изолированных, 15 при concurrency 3, 30 при concurrency 6.
12 конфигураций: Ubuntu 22.04/24.04 × GCC/Clang × Debug/Release/ASan+UBSan.
Любая ошибка остаётся ошибкой; повторения исследуют воспроизводимость и не
заменяют неуспешный результат успешной попыткой.

Отрицательный контроль без цикла EINTR детерминированно падает в проверке
успешного выполнения. После восстановления тест проходит. Это доказанный
дефект транспорта, **но не доказанная причина старого CI-сбоя**: прежние
`status=6 system=0 cleanup=5` не позволяют различить EOF, errno или гибель
supervisor. Старое общее сообщение ELF также не получает диагноз задним числом.
#645 остаётся открытой до результатов диагностической матрицы и разбора
доказательств; одни зелёные повторы не доказывают исправления исходного отказа.
Локальные измерения записаны в `test/data/child-control/README.md`.

## Регрессия через cleanup-service

Варианты `service-*` повторяют восемь отказов через настоящий отдельный процесс
cleanup-service, которым пользуется compiler probe. Доставка результата ребёнка
должна вернуть `CLEANUP_OK`, даже если сам результат содержит `CHILD_IO_ERROR`;
финальная очистка в этом случае обязана вернуть `CLEANUP_TREE_FAILED`.
Ошибка запуска отличается от ошибки очистки дерева. Повторный finish сохраняет
уже записанный исход. Тестовое окружение выбирает отказ только в fixture,
не в production; supervisor, запускающий сам сервис, остаётся исправным.
Так проверяется сохранение диагностики при сериализации child-result.

Матрица PR #658 прошла все 12 конфигураций (600 native-нагрузок), но исходный
ELF-сбой не повторился. Новые тесты закрывают непроверенный путь, а не объявляют
причину исторического отказа установленной.

При локальных повторах ASan найден отказ старта сервиса до инъекции. Исходный
сбой сохранён в `test/data/child-control/linux-asan-service-first-failure.txt`.
Следующий диагностический прогон из 400 запусков прошёл, но не объясняет отказ.
Добавлены status и elapsed time запуска. Отдельный блокер: [#659](https://github.com/kniazkov/g0at/issues/659).

## Диагностика запуска сервиса (#659)

Существующая единственная попытка запуска сохраняет неизменяемый снимок
`cleanup_start_diagnostic_t`. `cleanup_service_startup_diagnostic` копирует его
под блокировкой; до попытки возвращает false. Чтение не опрашивает процесс,
не ожидает его завершения и не продлевает дедлайн запуска 1000 мс. Повторные
ensure/finish не перезаписывают снимок. Проверка компилятора, подготовка native
и загрузка модулей включают эти данные в ограниченное по длине сообщение.
Путь программы, окружение, вывод процесса и каталог из READY не печатаются.

| Поле | Значение |
|---|---|
| `status` | Прежний `cleanup_status_t`, без изменения семантики |
| `stage` | Последний этап: 0 создание канала, 1 создание объекта процесса, 2 заголовок READY, 3 тело READY, 4 проверка READY, 5 ACK, 6 готовность |
| `transport` | -1 до транспортной операции; далее 0 OK, 1 таймаут, 2 закрытый канал, 3 ошибка (`channel_status_t`) |
| `elapsed_ms` | Длительность исходной попытки, а не момент наблюдения |
| `type`, `size` | Значения заголовка после проверки magic и предельного размера; до этого нули |

Отказ с `transport=0 stage=4` означает, что полный пакет не прошёл проверку
READY. `stage=2 transport=3` может означать неверный заголовок или ошибку ввода-
вывода; это не код ОС. `stage=2 transport=2` не отличает ошибку запуска программы
от раннего выхода сервиса: запуск асинхронный. Здесь намеренно нет poll процесса,
поскольку окончательная очистка дерева может блокировать и нарушить бюджет
запуска. Получение статуса процесса остаётся отдельным шагом расследования.
Эти данные не устанавливают причину исторических отказов #645 и #659.

Восемь тестов `startup-*` запускают реальные процессы: нормальный сервис,
отсутствующая программа, ранний выход, отсутствие READY, неверные magic/тип/путь
и оборванное тело. Проверяются сохранность снимка и отсутствие повторного
запуска. Существующие межплатформенные тесты проверяют снимок после конкурентных
ensure; сценарии отказа native проверяют доставку диагностики вызывающему коду.
Инъекция отказов есть только в тестовой программе. Матрица расследования из
12 jobs повторяет эти тесты по 25 раз и сохраняет журналы CTest даже при падении
тестового шага. Неуспешная попытка или таймаут не заменяются успешным повтором.
