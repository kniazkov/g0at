# Сопровождение комментариев и обзоров

[Contents](index.md) · [English](../en/maintenance.md)

## Что писать рядом с декларацией

Объясни назначение функции и вызывающий её этап. Добавь неочевидные правила владения,
времени жизни, ошибок и частичных результатов. Единицы, специальные значения и порядок
нужны там, где их не выражают тип и имя. Не повторяй очевидные параметры, getters и
присваивания. Комментарии C пишутся по-английски; обзоры имеют согласованные английскую
и русскую версии.

Обоснование алгоритма помещается рядом с зависящим от него решением: почему объединение
не учитывает завершившиеся пути, загрузчик откладывает публикацию, неизвестный вызов
сбрасывает знание. Точный API-контракт хранится в заголовке и связывается с обзором
через `@see`; не нужно поддерживать несколько копий длинного контракта.

## При изменении подсистемы

1. Проверь точку входа, владельца/деструктор и пути ошибок, а не только изменённую строку.
2. Обнови соответствующую страницу [карты реализации](architecture.md) на обоих языках.
   Отличай текущее ограничение от инварианта.
3. Объясняя правило анализа, предпочитай зарегистрированный тест. Подключай реальные
   `.goat` и `.expect`, не вставляй вторую независимо редактируемую программу.
4. Выполни нужные тесты и генерацию документации. Проверь HTML: работающая на GitHub
   ссылка может не разрешаться в Doxygen.
5. Отделяй статус CI от проверки текста. Тесты устанавливают заявленные утверждения,
   но не полную корректность документации.

## Чтение сгенерированной документации

Из корня выполни `bash scripts/check_docs.sh` и открой
`build/doxygen-check/html/index.html`. Конфигурация включает production-код,
публичные заголовки, инструменты, тесты и их поддержку. Сгенерированные Unicode-
и schema-таблицы исключены из API: их источники и обновление описаны в
[инструментах](tools.md). Сторонний код не входит в область владения этого руководства.

Markdown-фильтр раскрывает `<!--! ... -->` для Doxygen 1.9.8. GitHub скрывает директивы
и показывает соседние ссылки на канонические исходники. Каждый включённый пример
анализа обязан иметь непустой файл ожиданий и присутствовать в обычном манифесте
тестов. Эта проверка не исполняет тесты; см. [тестирование](testing.md).

Старая книга реализации явно описывает указанные ревизии. Она полезна для общей
подготовки, но перед изменением кода сверяй актуальные пути и контракты с этими
обзорами и заголовками. Обзоры охватывают границы подсистем; это не утверждение,
что каждой вспомогательной функции нужен новый комментарий.
