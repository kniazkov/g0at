<a id="section-11-1"></a>

## 11.1. У памяти несколько владельцев

Вопрос «когда освободить объект?» имеет разные ответы на разных этапах. Токены обычно нужны до завершения разбора, AST — до завершения компиляции, а замыкание может пережить вызов, в котором создано. Поэтому Goat использует несколько механизмов, каждый для своей группы данных.

| Данные | Основной механизм |
|---|---|
| Токены, AST, данные анализа | Арены с общим освобождением |
| Значения во время исполнения | Счётчики ссылок и сборщик достижимости |
| Повторно используемые оболочки объектов | Ограниченные пулы процесса |
| Загруженная нативная библиотека | Отдельные дескрипторы со счётчиками ссылок |
| Все выделения через `ALLOC` | Учёт размера; дополнительные проверки при `MEMORY_DEBUG` |

Эти механизмы не заменяют друг друга. Например, освобождение арены AST не должно уничтожить окружение исполняемой функции, а нулевой счётчик ссылок объекта не обязательно означает немедленный возврат его оболочки системному аллокатору.

<a id="section-11-2"></a>

## 11.2. Арена освобождает этап целиком

Арена (набор крупных блоков для множества небольших выделений) реализована в [arena.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/lib/arena.c). Новая запись занимает очередной выровненный участок текущего блока; при нехватке места выделяется следующий. Отдельные узлы не освобождаются по одному. При уничтожении арены освобождаются её блоки.

Это соответствует работе компилятора: AST состоит из множества связанных узлов, которые обычно перестают быть нужны одновременно. В [launcher.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/cli/launcher.c) раздельно организована память исходных позиций, токенов, графа и ошибок. Токены можно убрать после построения дерева; данные, которые ещё нужны графу, должны уже иметь подходящего владельца.

Арена упрощает время жизни, но не отменяет его границ. Ссылка на узел внутри уничтоженной арены становится недействительной. Поэтому байткод копирует необходимые инструкции и данные в собственный буфер, а нативные дескрипторы имеют отдельное владение.

<a id="section-11-3"></a>

## 11.3. Счётчик ссылок отвечает за обычный случай

Динамический объект хранит число владеющих ссылок. Получение новой такой ссылки сопровождается `INCREF`, отказ от неё — `DECREF`. При достижении нуля объект очищает удерживаемые ссылки и освобождает либо помещает свою оболочку в пул. Методы конкретных типов находятся в `src/model`.

Важны договорённости на границах. Стек принимает переданную ссылку; создание свойства удерживает и ключ, и значение; функция удерживает окружение и имена параметров. Поэтому вызывающий код после создания свойства может уменьшить собственную ссылку на значение: свойство уже имеет свою.

Синглтоны — `null`, логические значения и другие статические объекты — могут использовать пустые методы `INCREF` и `DECREF`. Само наличие макроса в вызывающем коде не означает, что у каждого объекта физически есть изменяемый счётчик.

В [process.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/model/process.c) процесс ведёт список активных динамических объектов и отдельные пулы целых, вещественных, строк и пользовательских объектов. Пулы позволяют повторно использовать уже выделенные оболочки. Состояние `ZOMBIE` обозначает такую очищенную оболочку, а не значение, к которому программа может продолжать обращаться. `DYING` у пользовательского объекта защищает глубокую очистку от повторного входа.

<a id="section-11-4"></a>

## 11.4. Почему счётчика недостаточно

Если окружение хранит функцию, а функция удерживает окружение, обе ссылки существуют даже после исчезновения последней внешней ссылки. Их счётчики не становятся нулевыми. Такая группа называется циклическим мусором: она связана внутри, но недоступна программе снаружи.

[11-cycles.goat](../examples/11-cycles.goat) создаёт именно эту ситуацию:

```goat
const make = func() {
    const self = func() { return self; };
    return self;
};
var saved = make();
println(saved() == saved);
saved = null;
println("released binding");
```

Результат:

```text
true
released binding
```

`self` возвращает собственный объект функции; равенство подтверждает его идентичность. После `saved = null` внешняя переменная больше не удерживает функцию, но связь между `self` и окружением остаётся.

Последняя строка сообщает только о выполнении программы. Она не измеряет освобождение памяти и не доказывает момент сборки мусора. Для проверки владения нужны внутренние тесты с наблюдением за объектами или ресурсами, а не только напечатанный результат.

<a id="section-11-5"></a>

## 11.5. Пометка и удаление

[gc.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/vm/gc.c) реализует *mark-and-sweep* (пометку достижимых объектов и удаление остальных). Корни — ссылки, с которых начинается обход. В текущем коде это строки кеша процесса и, для каждого потока, данные текущего контекста, ожидающее исключение и все значения стека.

Метод `mark` объекта помечает его и продолжает обход удерживаемых объектов. Пользовательский объект посещает ключи, значения свойств и прототипы; функция — окружение и имена параметров. Проверка уже поставленной пометки останавливает повторный обход цикла.

После этого сборщик проходит список активных объектов процесса. Непомеченные объекты очищаются; у выживших пометка сбрасывается для следующего прохода. При такой очистке используются специальные пути без обычного рекурсивного уменьшения ссылок: обход всего недостижимого графа уже выполняет сборщик. Некоторые оболочки попадают в пулы.

Ожидающее исключение является корнем не случайно. Его значение может быть динамическим объектом, который больше не удерживается уничтоженными контекстами. [test_vm_exceptions.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/test/test_vm_exceptions.c) проверяет сохранение такого значения, в том числе при повторном вызове сборщика.

> [!CAUTION]
> Обычный цикл VM вызывает сборщик после окончания исполнения, а не периодически по числу выделений. Недостижимые циклы могут накапливаться до этого момента. Кроме того, текущая пометка начинает с данных текущего контекста и не обходит цепочку `context->previous` отдельно. Этот код нельзя без дополнительной проверки корней просто перенести в произвольную точку посреди вызова функции.

<a id="section-11-6"></a>

## 11.6. Нативная библиотека тоже должна оставаться живой

Объект функции может содержать адрес машинного кода из загруженной `.so` или `.dll`. Если выгрузить библиотеку раньше функции, этот адрес станет недействительным. Поэтому [native_library.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/model/native_library.c) использует два уровня: дескриптор функции удерживает библиотеку, а байткод и динамические объекты функций удерживают дескриптор.

Счётчики этих дескрипторов атомарные. Это свойство управления ресурсом; оно само по себе не делает всю VM потокобезопасной. При последнем освобождении выполняется выгрузка и связанная очистка ресурсов. Уничтожение динамической функции освобождает дескриптор и при обычном `DECREF`, и при сборке недостижимого цикла.

Тест времени жизни в [test_native_call.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/test/test_native_call.c) проверяет несколько маршрутов: сохранённый псевдоним функции, замыкание с циклом и завершение процесса. В частности, освобождение байткода не должно выгружать библиотеку, если нативную функцию ещё удерживает живой объект.

Это не общее разрешение вызывать байткодную функцию после освобождения её инструкций: её адрес тела по-прежнему имеет смысл только вместе с соответствующим байткодом. Нативный дескриптор защищает свой ресурс — библиотеку.

<a id="section-11-7"></a>

## 11.7. Отладочный учёт и завершение процесса

Обёртки [allocate.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/lib/allocate.c) учитывают размер выделенной памяти и обеспечивают выравнивание. Переполнение размера и невозможность выделения завершают процесс с диагностикой. При `MEMORY_DEBUG` дополнительно сохраняются файл и строка выделения, список блоков и защитные байты после полезной области. `FREE` проверяет эти байты; список оставшихся блоков помогает искать утечки.

В [CMakeLists.txt](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/CMakeLists.txt) `MEMORY_DEBUG` включён для конфигураций, отличных от `Release`. В `Release` исчезают дополнительные записи и проверки защитных байтов, но базовый учёт размера остаётся. Поэтому сравнивать скорость двух сборок следует с учётом этих различий.

> [!CAUTION]
> Защитные байты не являются полной проверкой корректности памяти. Этот механизм не обнаруживает автоматически каждое чтение после освобождения или каждую запись за границы. Он также учитывает только выделения, прошедшие через проектные обёртки.

При уничтожении процесса освобождаются потоки, оставшиеся активные объекты, пулы и кеш. Завершение процесса — последняя граница владения, но оно не заменяет проверку правильного освобождения временных данных во время длительного исполнения.
