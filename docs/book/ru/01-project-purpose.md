## 1.1. Зачем создавать свой язык

За короткой строкой программы скрывается целая последовательность решений. Нужно распознать имена и операции, определить, к каким переменным относятся эти имена, выбрать порядок вычислений и разместить значения в памяти. Даже сложение двух чисел требует договорённостей: что делать при переполнении и как поступить, если одно число целое, а другое вещественное.

Goat позволяет разобрать такие решения на работающей системе. Это экспериментальный язык программирования и его реализация на C, разработанные Иваном Князьковым. Здесь можно проследить путь от исходного текста до результата, изменить отдельный механизм и проверить последствия. Статический анализ и генерация нативного кода дают особенно содержательные примеры: сведения о программе превращаются в основания для выбора способа её исполнения.

У проекта есть и личная задача — показывать инженерную работу автора. Во время консультации или технического обсуждения полезно иметь возможность открыть конкретный алгоритм, показать тест и воспроизвести результат. Репозиторий предоставляет такую опору: исходники, примеры и история изменений доступны для проверки.

Книга устроена вокруг тех же решений. Мы будем разбирать, какую задачу решает каждый механизм, какие данные ему нужны и где заканчиваются его возможности. Знание устройства компиляторов для начала не требуется: необходимые понятия вводятся по мере появления.

<a id="section-1-2"></a>

## 1.2. От текста к исполнению

Для человека программа начинается с текста. Для исполнения Goat преобразует этот текст в несколько внутренних представлений. Сначала он распознаёт отдельные элементы записи, затем собирает из них дерево программы. Дерево отражает структуру выражений и инструкций: например, какие два выражения складываются и к какому условию относится ветвь.

Обычный путь исполнения проходит через байткод — последовательность инструкций собственной виртуальной машины. Виртуальная машина написана на C; она выполняет эти инструкции, хранит промежуточные значения и управляет вызовами функций. Все основные этапы соединены в [модуле запуска](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/src/cli/launcher.c).

До исполнения анализатор пытается установить, что уже известно о программе. Например, для выражения `2 + 3` можно получить точное значение. Если вместо констант стоят параметры функции, сведений может быть меньше: известен тип, но неизвестны конкретные числа. Такое вычисление сведений без обычного запуска программы называется статическим анализом.

Помимо значений, анализатор учитывает действия программы. Функция может выводить текст или изменять переменную из внешнего окружения. Такие действия называют побочными эффектами. Они важны при преобразованиях: одинаковое возвращаемое число ещё не означает одинаковое поведение двух вариантов функции.

Для части функций Goat умеет подготовить нативную реализацию. Анализатор проверяет необходимые условия, генератор записывает подходящий код на C, внешний компилятор создаёт динамическую библиотеку с машинным кодом, а Goat загружает её. Реализация для определённой функции и упорядоченного набора типов параметров называется специализацией.

Здесь возникает один из главных вопросов книги: каких сведений достаточно, чтобы выбрать такую реализацию и сохранить поведение программы? Ответ складывается из анализа типов, эффектов, тела функции и её вызовов. Неизвестное свойство нельзя просто принять за подходящее — для перехода к нативному коду нужны основания.

## 1.4. Одна программа, два пути

Разницу между VM и нативным исполнением можно увидеть уже сейчас. В репозитории есть [пример вычисления числа Фибоначчи](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/example/fibonacci_analysis.goat). Его функция рекурсивна: для вычисления результата она вызывает саму себя с меньшими аргументами. Программа вычисляет значение для аргумента `10`.

Запустим один и тот же исходник двумя способами. После сборки Goat, из корня репозитория на Linux:

```sh
./goat --native off --save-analysis analysis.txt example/fibonacci_analysis.goat
./goat --native required --save-native native.txt example/fibonacci_analysis.goat
```

Для Windows PowerShell:

```powershell
.\goat.exe --native off --save-analysis analysis.txt example/fibonacci_analysis.goat
.\goat.exe --native required --save-native native.txt example/fibonacci_analysis.goat
```

Первый запуск использует VM и записывает сведения анализатора в `analysis.txt`. Второй подготавливает нативную библиотеку и записывает отчёт в `native.txt`. Для него нужен совместимый компилятор C: по умолчанию `cc` на Linux или `gcc` на Windows. Другой исполняемый файл можно выбрать переменной окружения `CC`. Отчёты сохраняются в текущем каталоге.

На экране в обоих случаях появится `55`, без завершающего перевода строки. По одному этому числу ещё нельзя понять, какой путь сработал. Поэтому заглянем в `native.txt`:

```text
preparation=ready
succeeded=1
retries=0
```

Это часть отчёта: библиотека подготовлена, один вызов успешно выполнен нативно, повторов в VM не было. Здесь считается вход через нативный адаптер; рекурсивные вызовы внутри сгенерированной функции не увеличивают `succeeded`.

Таким образом, у примера есть два наблюдаемых результата: вычисленное число и подтверждение выбранного пути исполнения. Он даёт отправную точку для дальнейшего разбора. Проверке общих свойств и измерению производительности посвящены отдельные главы.

## 1.5. Как проверить объяснение

При чтении книги полезно переходить от описания к коду и обратно. Исходник показывает, как устроен механизм; небольшой тест помогает понять, какое поведение от него ожидается. Например, пограничный случай с переполнением часто объясняет выбор алгоритма лучше, чем его обычный успешный запуск.

Для такой проверки в репозитории есть несколько видов материалов:

- исходный код определяет алгоритмы, структуры и условия отказа;
- [юнит-тесты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/src/test) проверяют отдельные механизмы и их взаимодействие;
- [тесты анализа](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/test/analysis) сопоставляют полученные сведения с ожидаемыми;
- [функциональные тесты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/test/functional) и [проверочные скрипты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/scripts) проверяют результаты исполнения и интеграцию компонентов;
- [конфигурация CI](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/.github/workflows/build_and_test.yml) задаёт проверки для Linux с GCC и Clang и для Windows с вариантами MinGW;
- история коммитов и PR фиксирует последовательность изменений и обсуждение решений.

Ссылка на конкретную редакцию кода позволяет вернуться к тому же объяснению после последующих изменений. Для результата проверки следует также указать сам тест и окружение, где он прошёл. Для измерения скорости нужны платформа, конфигурация сборки и методика: без них число теряет значительную часть смысла.

<a id="section-1-6"></a>

## 1.6. Где проходят границы

Экспериментальный проект особенно полезен, когда его ограничения видны. В Goat анализатор работает с поддерживаемыми конструкциями и имеет вычислительные лимиты. Нативный бэкенд принимает подмножество числовых функций. Если для специализации не удалось установить необходимые свойства, оснований генерировать её нативную реализацию нет.

По ходу книги мы будем встречать свойства, которые важно не смешивать. Например, функция может не менять внешнее состояние и при этом бесконечно вызывать саму себя. Поэтому доказанная чистота ещё не доказывает завершение. Аналогично, успешный запуск примера подтверждает этот случай, а измеренное ускорение относится к конкретной программе и окружению.

Goat даёт материал для изучения этих различий, но его текущие механизмы не устанавливают промышленную готовность, совместимость будущих версий или безопасность запуска недоверенного кода. В частности, нативная библиотека выполняет машинный код без изоляции. В книге рассматривается существующая реализация указанной редакции; возможные дальнейшие расширения не считаются уже работающими возможностями.
