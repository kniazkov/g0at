## 1.1. Цели

Goat — экспериментальный язык программирования и его реализация на C, разработанные Иваном Князьковым. Проект предназначен для исследования механизмов обработки и исполнения программ, проверки выбранных решений и демонстрации результатов этой работы.

Репозиторий также выполняет функцию технического портфолио автора. Он предоставляет материал для консультаций, докладов и профессиональных обсуждений: исходный код, примеры, тесты и историю изменений. Утверждение об устройстве системы можно соотнести с конкретной реализацией и проверить запуском соответствующего примера или теста.

Предмет этой книги — устройство существующей системы. Описание привязано к указанной редакции кода. Планируемые возможности не включаются в перечень реализованных механизмов. История изменений используется для объяснения решений; текущее поведение устанавливается по исходному коду и проверяющим его тестам.

<a id="section-1-2"></a>

## 1.2. Объект исследования

Язык задаёт правила записи программы и значение её конструкций. Реализация языка читает исходный текст, проверяет его структуру, строит внутреннее представление и исполняет программу.

В Goat для обычного исполнения используется байткод — последовательность инструкций собственной виртуальной машины. Виртуальная машина представляет собой программу на C, которая выполняет эти инструкции и управляет значениями и контекстами исполнения. Порядок основных этапов задан в [модуле запуска](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/src/cli/launcher.c).

До исполнения может выполняться статический анализ: вычисление сведений о программе без её обычного запуска. В частности, анализатор определяет возможные значения и типы, зависимости вызовов и побочные эффекты. Побочным эффектом здесь называется наблюдаемое действие, например вывод или изменение внешнего для функции состояния. Неизвестные сведения сохраняются как неизвестные; они не считаются доказательством допустимости преобразования.

Для части функций предусмотрено нативное исполнение. Анализатор проверяет условия применимости, генератор создаёт код на C, внешний компилятор строит машинный код в динамической библиотеке, а Goat загружает её и вызывает подходящую реализацию функции. Такая реализация называется специализацией: она соответствует определённой функции и упорядоченному набору типов её параметров. Машинный код создаётся внешним компилятором C; Goat формирует его исходный текст и организует использование результата.

Эта последовательность позволяет исследовать связь между сведениями, полученными анализатором, и преобразованиями, которые на их основании допускает исполнительная система.

## 1.4. Проверяемый пример

В репозитории имеется [пример вычисления числа Фибоначчи](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/example/fibonacci_analysis.goat). Он содержит рекурсивную функцию, то есть функцию, вызывающую саму себя, и вычисляет результат для аргумента `10`.

После сборки Goat из корня репозитория на Linux выполняются команды:

```sh
./goat --native off --save-analysis analysis.txt example/fibonacci_analysis.goat
./goat --native required --save-native native.txt example/fibonacci_analysis.goat
```

В Windows PowerShell используются команды:

```powershell
.\goat.exe --native off --save-analysis analysis.txt example/fibonacci_analysis.goat
.\goat.exe --native required --save-native native.txt example/fibonacci_analysis.goat
```

Второй запуск требует доступного совместимого компилятора C: `cc` на Linux или `gcc` на Windows по умолчанию. Переменная окружения `CC` позволяет выбрать другой исполняемый файл компилятора. Первый запуск исполняет программу в VM и сохраняет журнал анализа в `analysis.txt`. Второй подготавливает нативную библиотеку и сохраняет отчёт о её использовании в `native.txt`. Файлы отчётов записываются в текущий каталог.

Оба запуска выводят `55` без завершающего перевода строки. Для второго запуска отчёт содержит `preparation=ready`, `succeeded=1` и `retries=0`: библиотека подготовлена, один вызов успешно выполнен нативно, повторов в VM не было.

Совпадение результата в этом примере подтверждает работу двух путей исполнения для данного случая. Счётчик успешных вызовов позволяет отличить фактическое нативное исполнение от одной лишь подготовки библиотеки. Пример не устанавливает эквивалентность всех возможных программ и не является измерением производительности.

## 1.5. Основания для технических выводов

В репозитории представлены несколько видов проверяемых материалов:

- исходный код определяет алгоритмы, структуры и условия отказа;
- [юнит-тесты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/src/test) проверяют отдельные механизмы и их взаимодействие;
- [тесты анализа](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/test/analysis) сопоставляют полученные сведения с ожидаемыми;
- [функциональные тесты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/test/functional) и [проверочные скрипты](https://github.com/kniazkov/g0at/tree/09d0cffb08303b07c1c3af27ccbfc6af94466b97/scripts) проверяют результаты исполнения и интеграцию компонентов;
- [конфигурация CI](https://github.com/kniazkov/g0at/blob/09d0cffb08303b07c1c3af27ccbfc6af94466b97/.github/workflows/build_and_test.yml) задаёт проверки для Linux с GCC и Clang и для Windows с вариантами MinGW;
- история коммитов и PR фиксирует последовательность изменений и обсуждение решений.

При ссылке на результат следует указывать редакцию кода и конкретную проверку. Для измерений дополнительно указываются платформа, конфигурация сборки и методика. Наличие проверки в репозитории и успешное выполнение этой проверки в определённом окружении являются разными утверждениями.

<a id="section-1-6"></a>

## 1.6. Границы результатов

Статический анализ ограничен поддерживаемыми конструкциями и вычислительными лимитами. Нативный бэкенд работает с подмножеством числовых функций. Отсутствие доказательства оставляет функцию без соответствующей нативной специализации. Даже доказанная чистота функции не устанавливает, что она завершится или не выбросит исключение; эти свойства требуют отдельных оснований.

Тестирование проверяет выбранные случаи и условия. Оно не является полным доказательством корректности реализации. Результат отдельного теста производительности характеризует его программу и окружение, а не скорость языка для произвольной нагрузки.

Наличие компилятора, VM, анализатора и нативного бэкенда не устанавливает промышленную готовность проекта. Из этих механизмов не следуют гарантии совместимости будущих версий, пригодности для произвольной нагрузки или безопасности исполнения недоверенного кода. В частности, загружаемая динамическая библиотека содержит машинный код и не образует изолированную среду исполнения.
