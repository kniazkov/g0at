## 4.1. Как читать реализацию

Одна операция Goat затрагивает несколько файлов. Сканер распознаёт `+`, парсер соединяет операнды, узел дерева описывает сложение, а исполнительная среда складывает конкретные значения. Если искать всю операцию в одном месте, устройство проекта покажется запутанным. Полезнее сначала определить, на каком этапе она нас интересует.

Реализация написана на C. Здесь нет классов языка C++, но есть структуры, общие интерфейсы и таблицы указателей на функции. Нет и отдельного генератора парсера: правила разбора записаны вручную. Эта глава объясняет соглашения, позволяющие читать такой код, прежде чем мы перейдём к отдельным алгоритмам.

Основной вход — [main.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/main.c), а последовательность подготовки и запуска находится в [launcher.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/cli/launcher.c). [Сборка CMake](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/CMakeLists.txt) объединяет общие исходники в библиотеку `core`; её используют интерпретатор, юнит-тесты и тесты анализа. Функциональный тестировщик запускает отдельный исполняемый файл Goat.

<a id="section-4-2"></a>

## 4.2. Карта каталогов

| Каталог | Что искать |
|---|---|
| `src/lib` | Выделение памяти, строки, контейнеры, пути и ввод-вывод |
| `src/common` | Координаты исходника, ошибки компиляции, общие типы и виды передачи управления |
| `src/scanner` | Распознавание токенов и операции над их списками |
| `src/parser` | Группировка скобок и правила построения дерева |
| `src/graph` | Узлы AST, их связи, представление в виде исходника и графа |
| `src/analysis` | Абстрактные значения, состояния, анализ функций и преобразования дерева |
| `src/codegen` | Построители кода и данных, генерация C, подготовка нативных модулей |
| `src/model` | Значения времени исполнения, контексты, функции и загруженные библиотеки |
| `src/vm` | Байткод, цикл исполнения, бинарный формат и сборка мусора |
| `src/builtins` | Встроенные функции, их исполнительные и абстрактные реализации |
| `src/cli`, `src/resources` | Параметры запуска, координация этапов и тексты сообщений |
| `src/test`, `test` | Юнит-тесты на C и программы с ожидаемыми результатами |

Это разделение обязанностей, а не строгая последовательность вызовов между каталогами. В частности, метод генерации байткода конкретной операции находится рядом с её узлом в `graph`, а общие построители инструкций — в `codegen`. Аналогично, узел может содержать метод абстрактного вычисления, использующий операции из `analysis`.

<a id="section-4-3"></a>

## 4.3. Общая часть структуры и таблица методов

Рассмотрим [бинарную операцию](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/binary_operation.h), то есть выражение с двумя операндами. Её структура начинается с общей части выражения:

```c
struct binary_operation_t {
    expression_t base;
    expression_t *left_operand;
    expression_t *right_operand;
};
```

Само `expression_t` начинается с `node_t`. Благодаря такому вложению код может обращаться к общей части разных узлов одинаковым способом. Это соглашение о расположении данных, явно выраженное структурами C. Оно не превращает произвольный указатель в узел нужного вида: конкретный метод должен получать структуру, соответствующую своему типу.

В общей части находится `vtbl` — указатель на таблицу методов (набор функций, описывающих поведение данного вида узла). Например, общий вызов получения числа детей в [node.h](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/node.h) выглядит так:

```c
return node->vtbl->get_child_count(node);
```

У бинарной операции детей два, у литерала их нет, а у списка инструкций число зависит от программы. Обходу дерева не требуется знать устройство каждого конкретного вида: он спрашивает число детей и получает их по индексам.

В таблице есть также методы печати исходника, абстрактного вычисления, генерации байткода и C, замены дочерних узлов. Для неприменимых действий используются [общие методы](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/common_methods.c): например, `no_children`, `no_child_replacement`, `execute_nothing`. Их результаты имеют конкретный смысл. `no_child_replacement` сообщает об отказе через `false`, а `execute_nothing` возвращает неизменённое абстрактное состояние. Это не скрытая реализация недостающей возможности.

<a id="section-4-4"></a>

## 4.4. Три разных представления одного числа

В строке `2 + 3` легко увидеть числа и предположить, что система везде хранит один и тот же объект. На деле нужно различать три уровня:

| Уровень | Что означает число |
|---|---|
| AST | Узел литерала: в этой точке программы написано `2` |
| Анализ | Абстрактное значение: здесь известно ровно `2`, диапазон или только тип |
| Исполнение | Объект целого числа, с которым работают инструкции VM |

Узел находится в `graph`, абстрактное описание — в `analysis`, исполнительный объект — в `model`. Они решают разные задачи и имеют разное время жизни. Дерево уже может быть освобождено, когда VM создаёт результат сложения.

Это различие заметно в [addition.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/addition.c). Метод `calculate` получает описания операндов и обращается к `lattice_add`. Метод `generate_bytecode` сначала генерирует код левого операнда, затем правого, затем инструкцию `ADD`. Конкретное сложение объектов выполняется позже. Поэтому название `execute` в таблице узлов не следует автоматически понимать как исполнение Goat-программы: там оно относится к абстрактной интерпретации.

Исполнительные объекты тоже имеют таблицы методов, но это другой интерфейс, описанный в [object.h](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/object.h). Его операции работают с конкретными значениями, ссылками, свойствами и вызовами.

<a id="section-4-5"></a>

## 4.5. Память освобождается по этапам

Многие объекты компилятора удобно создавать по одному, а освобождать вместе. Для этого служит арена (область памяти, из которой выдаются небольшие участки без отдельного освобождения каждого участка).

[parser_memory_t](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/arena.h) содержит четыре арены:

| Поле | Содержимое и срок использования |
|---|---|
| `positions` | Координаты и диапазоны исходника, нужные в том числе после разбора |
| `tokens` | Сканер, его рабочая копия текста и токены; освобождаются после построения AST |
| `graph` | Узлы, связанные структуры и данные анализа; нужны до окончания подготовки кода |
| `errors` | Описания ошибок и предупреждений компиляции |

[Реализация арены](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/arena.c) хранит цепочку блоков. Небольшое выделение сдвигает указатель внутри текущего блока; когда места не хватает, добавляется новый. Крупные выделения получают отдельные блоки. Адреса ранее выданных участков не перемещаются. Выравнивание (размещение по адресам, пригодным для соответствующих типов C) обеспечивается через `memory_alignment_t`.

`destroy_arena` освобождает всю цепочку. Вызывать `FREE` для отдельного узла внутри арены нельзя. При этом временные массивы, некоторые контейнеры и строковые построители могут выделяться отдельно и требуют собственного освобождения. Само нахождение структуры в компиляторе не означает, что она обязательно принадлежит арене.

Обёртки [ALLOC, CALLOC и FREE](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/allocate.h) централизуют выделение и учёт памяти. При `MEMORY_DEBUG` дополнительно сохраняются места выделения и проверяются защитные байты. Ошибка выделения или переполнение размера завершают процесс; это не исключение языка Goat. Объекты исполнительной среды используют другой жизненный цикл — счётчики ссылок и сборку мусора, рассмотренные в главе 11.

## 4.6. Строки и контейнеры: кто владеет данными

Владение (обязанность освободить память после использования) не определяется одним наличием указателя. В [value.h](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/value.h) это различие выражено явно. `string_view_t` содержит адрес и длину, но не владеет строкой. `string_value_t` дополнительно содержит `should_free`; результат освобождают через `FREE_STRING`, который учитывает этот флаг. Длина измеряется в единицах `wchar_t`, без завершающего нуля.

Копирование такой структуры не обязательно копирует текст. Если представление строки ссылается на память арены, оно пригодно только пока жива арена. Поэтому, например, [конструктор переменной](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/variable.c) копирует имя из токена в арену графа: имя должно пережить освобождение токенов.

[string_builder_t](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/string_ext.h) накапливает текст в растущем буфере. Результаты добавления используют этот же буфер; следующее добавление может изменить его адрес. После получения окончательной строки построитель больше не используют, а строку освобождают один раз. Нельзя отдельно освободить каждый промежуточный результат.

Вместо одного универсального контейнера используются небольшие структуры под конкретные задачи: [вектор](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/vector.h) для индексируемой последовательности, [очередь](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/queue.h) для отложенной обработки функций, [связный список](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/linked_list.h) для последовательностей узлов и [AVL-дерево](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/lib/avl_tree.h) для поиска по ключу. AVL-дерево — упорядоченное дерево, поддерживающее баланс для ограничения длины поиска. Освобождение контейнера и освобождение его элементов — разные действия; нужный вариант виден из используемого API.

<a id="section-4-7"></a>

## 4.7. Как проверить прочитанное

Для небольшого исследования достаточно проследить одну операцию: её конструктор, таблицу методов, обращение к анализатору и генерацию инструкции. Затем можно перейти к исполнительному объекту и увидеть, где вычисляется конкретный результат. Такой маршрут не требует сразу читать все исходники проекта.

Проверки выравнивания и роста арены находятся в [test_lib_safety.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_lib_safety.c), строк — в [test_string_ext.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_string_ext.c), свойств и методов узлов — в [test_node_properties.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_node_properties.c). Они проверяют отдельные соглашения, но не заменяют чтение правил владения при добавлении нового поля или контейнера.

Наконец, базовая сборка и дополнительные инструменты — разные уровни. Для вывода изображения AST вызывается Graphviz, для нативной библиотеки — внешний компилятор C. Их наличие не требуется для самого распознавания токенов и построения дерева. В следующих главах мы будем рассматривать эти этапы отдельно от последующих способов исполнения.
