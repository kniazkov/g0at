## 17.1. Вызов требует знать, кого вызывают

Для анализа сложения достаточно описаний двух операндов. Для вызова нужны ещё сведения о функции и её окружении. Элемент `LATTICE_KNOWN_FUNCTION` содержит идентичность пользовательского тела и лексической активации либо дескриптор встроенной функции. Общее `FUNCTION` сообщает лишь, что значение вызываемо, но не какое тело будет работать.

Две функции, созданные из одного узла `func` в разных вызовах фабрики, могут иметь разные захваты. Поэтому одного указателя на AST недостаточно для точного разбора их поведения. Идентичность активации позволяет обычному анализу не смешивать такие окружения.

У встроенной функции известный дескриптор выбирает `interpret`, описанный в главе 13. Написание имени само по себе не заменяет это знание. У пользовательской функции возможен ограниченный обход тела с текущими фактами вызывающего кода.

<a id="section-17-2"></a>

## 17.2. Анализ одного известного вызова

[function_call.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/analysis/function_call.c) сначала проверяет нормальность пути и аргументов. Затем для пользовательской функции регистрируется типовая специализация, создаётся абстрактная активация и клонируется состояние вызывающего кода. Локальные значения предыдущего обхода этой функции сбрасываются.

Параметры получают описания фактических аргументов. Пропущенные параметры получают `null`; лишние аргументы не образуют параметры, но уже вычислены и могут прекратить путь. Тело обходится до завершения нормального исполнения. Каждый `return` добавляет значение и сохраняет состояние обычного выхода. Достижение конца добавляет `null`.

Состояния выходов объединяются. Изменения захваченных переменных возвращаются вызывающему коду, локальные текущие значения функции не подменяют его собственные записи. Наблюдения за объявлениями сохраняются и с завершившихся путей.

Это контекстно-зависимый анализ: при аргументе `2` можно узнать больше, чем при произвольном целом. Но его результат относится к данному исследованному вызову, а не автоматически ко всем будущим вызовам.

<a id="section-17-3"></a>

## 17.3. Где обход останавливается

> [!CAUTION]
> Обычный анализ вызовов ограничен глубиной 32 и общим бюджетом 1024 точных входов в пользовательские тела. Он также прекращает точный обход при повторном входе в уже активное тело, неактивном владельце захваченного окружения или наличии `try/catch`. В этих случаях факты забываются, результат расширяется до `TOP`. Это лимиты анализатора, а не ограничения допустимого числа вызовов программы.

Владелец окружения особенно важен для возвращённого замыкания. VM умеет сохранять его данные после выхода фабрики, но обычный абстрактный анализ не восстанавливает произвольное уже завершившееся окружение с той же точностью. «Работает в VM» и «полностью известно анализатору» здесь снова различаются.

Неизвестный вызов тоже не должен получать выдуманный результат. Возможность изменения привязок заставляет отказаться от части текущих сведений. Рекурсия при этом не запрещается: для неё существует отдельный механизм анализа типов следующей главы.

<a id="section-17-4"></a>

## 17.4. Как образуется специализация

`function_summary_set_t` хранит записи по упорядоченному набору типов формальных параметров. Регистрация в [function_summary.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/analysis/function_summary.c) убирает уточнения: целые константы и диапазоны становятся `integer`, вещественные константы — `real`, известная функция — `function`, типизированный массив — `array`.

Поэтому вызовы с `2` и `3` регистрируют одну сигнатуру `(integer)`, а вызов с `2.5` — другую, `(real)`. Порядок важен: `(integer, real)` отличается от `(real, integer)`. Недостающие параметры входят в ключ как `null`, лишние не входят. Однако `BOTTOM` даже в лишнем вычисленном аргументе не позволяет зарегистрировать состоявшийся вызов.

У ни разу не зарегистрированной функции нет выдуманной специализации «на всякий случай». Записи появляются из наблюдённых вызовов, а затем могут добавляться при исследовании графа зависимостей.

<a id="section-17-5"></a>

## 17.5. Повторный анализ для всех значений типа

Сводка содержит тип результата, эффекты, захваты, статус анализа и независимый статус допуска к C. Чтобы получить тип результата сигнатуры, [function_return.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/analysis/function_return.c) заново исследует тело: параметры теперь имеют общие типы из ключа, а внешние привязки не получают случайные значения из одного вызова.

Такой анализ обязан учитывать и ветви, не выбранные при первоначальном конкретном аргументе. Если при `x = 1` функция вернула число, это ещё не исключает строковый результат при `x = 0`, хотя оба входа имеют тип `integer`.

Статусы `unanalyzed`, `analyzing`, `analyzed`, `inconclusive` описывают ход попытки. `analyzed` не означает «всё известно»: завершённый анализ может получить `TOP`. `inconclusive` означает, что необходимый анализ не завершён достаточно для соответствующего вывода. Нативный допуск проверяется отдельно.

<a id="section-17-6"></a>

## 17.6. Пример с записью и двумя результатами

Файл [17-calls.goat](../examples/17-calls.goat):

```goat
var total = 0;
const add = func(x) { total = total + x; return total; };
println(add(2));
println(add(3));
const choose = func(x) {
    if (x) { return 1; }
    return "zero";
};
println(choose(1));
println(choose(0));
```

Результат:

```text
2
5
1
zero
```

Обычный обход первых двух вызовов видит изменение `total`: сначала `2`, затем `5`. Но типовая сводка `add(integer)` не может привязать результат к этим двум числам: ключ не фиксирует внешнее состояние `total`.

У `choose` оба вызова имеют одну сигнатуру `(integer)`. Её нормальные результаты включают целое и строку, поэтому типовая сводка содержит `not null`. Это шире точных результатов отдельных вызовов, но соответствует всем исследуемым значениям параметра данного типа.

<a id="section-17-7"></a>

## 17.7. Сводка не является кешем исполнения

Сводка хранит доказательства и приближения, а не результат, который можно вернуть вместо выполнения функции. В её ключе нет конкретных аргументов и значений захватов. Даже чистая функция с известным типом результата должна вычислить само значение при запуске.

События анализа сохраняют снимки изменяемых записей сводок; указатели на AST и неизменяемые элементы остаются заимствованными. Поэтому диагностическая история не должна задним числом меняться при очередном уточнении текущей сводки.

Проверки регистрации и раздельности этих смыслов находятся в [test_function_specialization.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_function_specialization.c) и [test_function_summary.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_function_summary.c). Следующая задача — связать специализации вызовами, включая циклы, и получить сведения, которые одиночный обход тела дать не может.
