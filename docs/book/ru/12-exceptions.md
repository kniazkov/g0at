<a id="section-12-1"></a>

## 12.1. Исключение — значение с другим маршрутом

Обычное выражение передаёт результат следующей операции. `throw` передаёт значение обработчику, пропуская незавершённую часть вычисления. В Goat исключением может быть любое значение, включая строку, число, объект и `null`. Специального обязательного класса исключений нет.

Стандартные ошибки операций используют строки, например `DIVISION_BY_ZERO`, `INVALID_ARGUMENT` и `INVALID_OPERATION`. [exceptions.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/exceptions.c) предоставляет неизменяемый объект `Exceptions` со стандартными именами. Эти строки остаются обычными значениями: строка с текстом ошибки, возвращённая нормальным путём, сама по себе не вызывает исключение.

Значение `null` языка также отличается от нулевого C-указателя. У него есть объект. Поэтому `throw null` означает настоящее исключение со значением `null`, а не отсутствие ошибки.

<a id="section-12-2"></a>

## 12.2. Результат операции содержит признак

В [object.h](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/object.h) `operation_result_t` состоит из указателя на значение и `is_exception`. `operation_success` и `operation_exception` создают эти два варианта. Контракт требует непустого указателя на принадлежащее результату значение.

Арифметический обработчик VM снимает операнды, вызывает метод объекта и освобождает использованные ссылки. Затем он смотрит на признак результата: нормальный кладёт на стек, исключительный передаёт `dispatch_exception`. Это позволяет одной инструкции обслуживать как успешное вычисление, так и деление на ноль.

Встроенные функции возвращают тот же тип результата. Их общая обёртка освобождает аргументы, а при ошибке сохраняет значение в `thread->exception` и сообщает неуспех. Обработчик `CALL` забирает это значение и запускает общий поиск обработчика. Следовательно, ошибки встроенных функций входят в тот же механизм, что и явный `throw`.

<a id="section-12-3"></a>

## 12.3. Как компилируется try/catch

[try_catch.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/graph/try_catch.c) выдаёт `TRY` с адресом обработчика. Во время исполнения эта инструкция создаёт контекст с признаком `FLOW_THROW`, сохраняет адрес и границу стека на момент входа.

После нормального завершения защищённого тела `RESTORE` удаляет контекст обработчика, а `JUMP` пропускает `catch`. На исключительном пути VM сама передаёт управление к обработчику и кладёт исключение на стек. Его начало — `ENTER; VAR`: новый контекст получает локальное имя исключения. В конце `catch` стоит `RESTORE`.

Это схема управления, а не обещание выполнить оба блока. Если защищённое тело завершилось нормально, тело `catch` не запускается. Если из него вернули результат функции, `RET` разворачивает необходимые контексты своим маршрутом.

> [!CAUTION]
> В описываемой версии реализован `try/catch`, но нет `finally` и автоматического вызова пользовательских обработчиков освобождения ресурсов при выходе из области. Нельзя переносить такие гарантии из других языков на этот синтаксис.

<a id="section-12-4"></a>

## 12.4. Поиск обработчика и очистка

`THROW` снимает значение со стека и передаёт владение им функции `dispatch_exception` в [vm.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/vm/vm.c). Та идёт по `context->previous` к ближайшему `FLOW_THROW`. Это поиск по цепочке исполнения: ошибка из вызываемой функции может попасть в `catch` вызывающей.

Затем уничтожаются вложенные контексты, а стек сокращается до сохранённой границы. Временные значения выше неё получают `DECREF`. Вспомогательный буфер операндов `ARG` очищается. Само значение исключения удерживается отдельно и не должно исчезнуть вместе с контекстом, где возникло.

При найденном обработчике удаляется и его служебный контекст, исключение кладётся на стек, а номер инструкции меняется на адрес `catch`. Поэтому повторный `throw` внутри `catch` уже ищет внешний обработчик: прежний `TRY` не остаётся активным для своего собственного обработчика.

Если обработчика нет, разворачивание доходит до корневого контекста, временный стек очищается, а значение сохраняется в потоке. VM останавливается с ненулевым статусом. [binary_program.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/cli/binary_program.c) печатает диагностику неперехваченного исключения. Пока эта диагностика нужна, значение остаётся корнем сборщика мусора.

<a id="section-12-5"></a>

## 12.5. Незавершённое выражение не продолжается

Файл [12-exceptions.goat](../examples/12-exceptions.goat):

```goat
const divide = func(x) { return 10 / x; };
try {
    println(100 + divide(0));
} catch (error) {
    println(error);
}
try {
    try { throw "stop"; } catch (inner) { throw inner; }
} catch (outer) {
    println(outer);
}
println(2 + 3);
```

Результат:

```text
DIVISION_BY_ZERO
stop
5
```

Перед вызовом `divide(0)` число `100` уже находится на стеке как левый операнд сложения. Ошибка не возвращает произвольное число вместо частного. Она отменяет незавершённое сложение и внешний `println`, очищает временные значения и ведёт в `catch`. Поэтому строка с результатом `100 + ...` не печатается.

Второй фрагмент передаёт строку через два обработчика. Имя `inner` существует только в своём обработчике; внешний `catch` получает то же выброшенное значение под именем `outer`. Последняя строка показывает, что после обработки программа продолжает обычное вычисление.

## 12.6. Четыре разных вида отказа

| Категория | Пример | Что происходит |
|---|---|---|
| Исключение языка | Деление на ноль, `throw`, неверный аргумент встроенной функции | Поиск `catch`; при его отсутствии завершение с диагностикой |
| Ошибка компиляции | Неподходящая синтаксическая конструкция | Диагностика до исполнения программы |
| Отказ нативного пути | Не удалось подготовить библиотеку или нативный вызов вернул статус отказа | Решение по режиму и виду статуса: VM, ограниченный повтор либо остановка |
| Нарушение внутреннего инварианта | Недостаточно элементов стека, повреждение защитных байтов | Аварийное завершение через проверки реализации |

`catch` в исходной программе не может обработать ошибку её собственного разбора: программа ещё не исполняется. Он также не превращает любой отказ загрузчика или C-аллокатора в значение Goat.

Повтор в VM после защитного лимита нативного вызова имеет специальные условия: чистая специализация (не меняющая наблюдаемое внешнее состояние), сохранённые аргументы и допустимый статус. Это не универсальное правило «при любой ошибке попробовать ещё раз». Подробности относятся к части V.

## 12.7. Что проверяют тесты

[test_vm_exceptions.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_vm_exceptions.c) проверяет переход к обработчику, разворачивание вызовов, возврат через защищённые области, очистку временных значений и сохранение неперехваченного объекта. Отдельно проверяется, что `null` может быть значением исключения. Это проверки структуры исполнения, а не только совпадения строк вывода.

[test_operation_result.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/test/test_operation_result.c) проверяет договорённости о нормальных и исключительных результатах операций. Вместе эти уровни нужны потому, что правильное значение ошибки ещё не гарантирует правильный стек после неё. Если после `catch` следующий оператор получает остаток чужого выражения, механизм обработки остаётся ошибочным даже при верной первой строке диагностики.

> [!CAUTION]
> Механизм исключений не изолирует произвольный машинный код и не является песочницей. Внутренние аварии и ошибки памяти C-реализации не получают общей гарантии безопасного перехвата на уровне Goat.
