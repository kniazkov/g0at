<a id="section-15-1"></a>

## 15.1. Значение относится к объявлению

В программе могут существовать несколько переменных `x` в разных областях. Таблица «имя → значение» смешала бы их. Поэтому абстрактное состояние использует идентичность объявления: ключом служит указатель на связанный с переменной декларатор AST. Связывание имён из главы 7 уже решило, какое объявление имеется в виду.

`abstract_state_t` в [abstract_state.h](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/abstract_state.h) содержит AVL-дерево таких записей, режим управления, ссылки на арену и сборщик событий, а также данные анализа вызовов. Это состояние анализатора. Оно не является `context_t` VM и не содержит исполнительные объекты чисел и строк.

Состояние меняется при обходе программы. Его запись сообщает, что известно в текущей точке, а не что будет находиться в переменной при любом будущем запуске.

<a id="section-15-2"></a>

## 15.2. Текущее значение и сводка

Каждая запись в [abstract_state.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/abstract_state.c) содержит `current` и `summary`. При записи нового значения `current` заменяется, а `summary` объединяется с новым значением через `join`.

| Шаг | `current` для `x` | `summary` для `x` |
|---|---|---|
| Объявление `x = 0` | `0` | `0` |
| Присваивание `x = 10` | `10` | `[0..10]` |
| Присваивание `x = 20` | `20` | `[0..20]` |

Текущее значение нужно следующему выражению. Сводка сохраняет историю наблюдений за объявлением, например для отображения результата анализа. Если подставить сводку вместо текущего значения, точность потеряется без причины: сразу после `x = 20` известно именно `20`.

Файл [15-state.goat](../examples/15-state.goat):

```goat
var x = 0;
x = 10;
println(x);
x = 20;
println(x);
```

Он печатает:

```text
10
20
```

При `--print-analysis` сводка выглядит так:

```text
#4 15-state.goat, 1.1: summary x = [0..20]
```

Интервал включает и значения, которые программа фактически не записывала. Это следствие формы домена, а не дополнительные скрытые присваивания.

<a id="section-15-3"></a>

## 15.3. Разделение при ветвлении

Когда условие неизвестно, анализатор должен рассмотреть две версии состояния. `clone_abstract_state` создаёт отдельное AVL-дерево, но записи пар значений сначала разделяются между копиями. У пары есть счётчик ссылок.

Перед изменением разделяемой пары создаётся её частная копия. Это *copy-on-write* (копирование при первой записи). Изменение одной ветви поэтому не меняет другую. Копируются ссылки на неизменяемые абстрактные значения, а не все диапазоны и строки.

Деревья и пары принадлежат состояниям. Деклараторы, элементы решётки и арена заимствуются: уничтожение состояния их не освобождает. Обе копии можно уничтожать в любом порядке, но общая арена должна пережить их. Коллектор и некоторые аккумуляторы намеренно разделяются: ветви оставляют события в общем журнале и добавляют результаты в общую сводку возвратов.

<a id="section-15-4"></a>

## 15.4. Объединение учитывает выход из ветви

`join_abstract_states` объединяет записи обоих состояний. Для текущих значений участвуют только пути с `FLOW_NORMAL`, то есть продолжающие обычное выполнение. Путь, закончившийся `return`, не должен влиять на значение переменной после условия: до этой точки он не дошёл.

Сводки, напротив, объединяются с обоих путей. Присваивание перед `return` действительно было рассмотрено и относится к истории объявления. Поэтому прекращение пути не означает стирание всех наблюдений о нём.

Если запись отсутствует на продолжающемся пути, при объединении используется абстрактный `null`. Если путь не продолжается, его вклад в текущее значение — `BOTTOM`. Эти случаи различаются: отсутствие записи не означает недостижимость.

Итоговое управление тоже объединяется. Если хотя бы один путь продолжается, результат — `FLOW_NORMAL`. Когда нормальных путей нет, сохраняется возврат, если он есть среди входов, иначе — недостижимость. Это договорённость данного прохода, а не универсальная модель всех возможных переходов языка.

<a id="section-15-5"></a>

## 15.5. Когда сведения приходится забыть

Неизвестная функция может изменить захваченную переменную. Сохранить после такого вызова старую константу было бы опасно. `forget_abstract_values` заменяет текущие значения на `TOP` и отмечает неизвестность корневых привязок. Эта потеря точности намеренная.

Встроенные имена имеют общий синтетический декларатор. Для их поиска дополнительно нужен текст имени, а флаг `builtin_bindings_unknown` запрещает полагаться на исходную привязку после возможного изменения. Иначе пользовательская замена `print` могла бы анализироваться как стандартный вывод.

При известном вызове используется более точный перенос состояния. Изменения внешних переменных возвращаются вызывающему коду; локальные переменные вызываемой функции не становятся текущими переменными вызывающей. Их наблюдения могут войти в сводки. Перед повторным анализом вызова локальные текущие значения сбрасываются, чтобы не продолжать предыдущую активацию.

> [!CAUTION]
> Забывание после неизвестного вызова грубое: оно затрагивает все отслеживаемые записи, а не только доказанно доступные этому вызову переменные. В текущем состоянии нет точной модели всех объектов и связей между ними, позволяющей всегда сузить область возможной записи.

<a id="section-15-6"></a>

## 15.6. Что остаётся в AST

`flush_abstract_state` переносит накопленные сводки в `declarator->abstract_value` и создаёт события `summary`. Затем временное состояние можно уничтожить. Значения в арене остаются доступны, пока живёт граф.

Не следует смешивать это поле с `expression->immediate_value`, которое относится к отдельной точке непосредственного исполнения, или со сводкой функции для набора типов параметров. У одного выражения, объявления и функции разные вопросы: результат здесь, значения за историю объявления и поведение целой специализации.

Порядок проходов в [analysis.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/analysis.c) сохраняет это разделение. Сначала идёт обычная абстрактная интерпретация и сводки объявлений; затем анализ функций; позже отдельный проход достижимости устанавливает факты для безопасного изменения общего AST.

<a id="section-15-7"></a>

## 15.7. Проверяемые договорённости

[test_abstract_state.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/test/test_abstract_state.c) проверяет независимость копий, объединение текущих значений и сводок, освобождение разделяемых записей. Такие проверки нужны даже при правильных формулах `join`: ошибка владения может незаметно изменить соседнюю ветвь.

Журнал анализа — последовательность наблюдений нескольких этапов. Ранняя запись `write x = 10` не обещает, что все дальнейшие чтения равны `10`. Окончательная сводка также не заменяет точечное знание. Читать эти записи следует вместе с их видом и координатами, а не как одну таблицу окончательных значений.
