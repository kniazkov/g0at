## Единица сборки и распространения

Один скомпилированный модуль — один файл без исходников. Модуль представляет библиотеку или программу для независимого распространения и многократного использования. Он содержит:

- байткод;
- метаданные для импорта и связи байткода с нативными реализациями;
- ноль или несколько нативных библиотек, в том числе для разных платформ.

По метаданным механизм исполнения выбирает подходящую библиотеку и соответствующие реализации. При отсутствии подходящего нативного варианта используется байткод. Разрешено извлекать библиотеку во временный каталог или кеш и загружать штатными средствами ОС. Предпочтительны простые переносимые решения с использованием возможностей ОС.

Метаданные используют JSON, как и описание сборки. Контейнер — ZIP; байткод и нативные библиотеки остаются бинарными частями, не кодируются в JSON. Расширение файла — .gbin. Полная схема метаданных и точные правила совместимости платформ уточняются ниже.

## Исходные файлы и состав модуля

Сборка модуля обязательно требует файла описания; именно его передают компилятору. В нём задаются имя, обязательная версия, входной исходный файл и зависимости. В модуль включаются входной файл и все исходники, достижимые по цепочке `include`, каждый один раз. Файлы, просто лежащие рядом, но не используемые, не включаются. Импорты готовых модулей становятся внешними зависимостями.

У каждого исходного файла собственная область имён. Объявления разных файлов не смешиваются, одинаковые имена допустимы. Байткод включённого файла хранится один раз; повторное включение не создаёт копий.

Отдельный файл `.goat` по-прежнему можно запускать без описания модуля для выполнения кода, тестирования и вывода в консоль. Это не сборка распространяемого модуля. В таком исходнике каждый импорт обязан явно содержать полную версию зависимости.

## Описание сборки

Формат описания — JSON:

```json
{
  "formatVersion": 1,
  "name": "geometry",
  "version": "1.2.0",
  "main": "src/main.goat",
  "dependencies": {
    "math": "2.0.0"
  }
}
```

Путь `main` разрешается относительно файла описания. Оно имеет расширение .gmod; полная схема ещё проектируется.

Версию зависимости можно задать в описании или непосредственно в импорте:

```goat
const math = import "math";          // Версия 2.0.0 из описания.
const oldMath = import "math@1.2.0"; // Явный выбор другой версии.
```

Явная версия действует для конкретного импорта и не меняет версию для импортов без версии. Обе версии могут использоваться в одной программе; их состояние раздельно. Если импорт не содержит версии и в описании её нет (либо самого описания нет), это ошибка компиляции. Автоматического выбора последней или случайно найденной версии нет.

## Проверка зависимостей и хеши

Все импортируемые готовые модули должны быть доступны при сборке. Компилятор читает их метаданные для проверки интерфейсов и анализа, не выполняя код инициализации. Отсутствующая зависимость — ошибка компиляции. Зависимости также должны быть доступны при исполнении.

Модуль содержит имя, версию и автоматически вычисленный основной хеш в метаданных. Он охватывает байткод и общие метаданные; нативные части хешируются отдельно по правилам ниже. Потребитель сохраняет имя, точную версию и ожидаемый основной хеш каждой зависимости.

Для одной пары «имя + версия» предусмотрена одна сборка. Хеш не входит в имя каталога. Пример размещения:

```text
geometry/1.2.0.gbin
geometry/2.0.0.gbin
```

Это позволяет старой и новой программам использовать разные версии библиотеки на одном компьютере. Если основная часть библиотеки изменилась под той же версией, а потребителя забыли пересобрать, несовпадение основного хеша при загрузке — немедленная ошибка. Искать другую сборку после этого нельзя. Выбор хеша пользователем в описании зависимости не требуется; предложение хранить несколько хешей одной версии в отдельных каталогах отклонено.

## Две разные операции

```goat
const math = include "./math.goat";
const geometry = import "geometry";
```

`include` подключает исходный файл своего модуля и возвращает объект его области. Это не текстовая вставка. `import` подключает отдельный скомпилированный модуль и возвращает объект области его входного файла. Внутренние файлы чужого модуля напрямую импортировать нельзя.

Аргументы обеих операций — только строковые литералы. Вычисляемые пути запрещены: состав модуля и внешние зависимости должны определяться при сборке.

Обе операции разрешены в выражениях, в том числе внутри функций и условных веток. Зависимость определяется при сборке даже для ещё не выполненного выражения; инициализация происходит при первом фактическом выполнении. Подключённый файл исполняется в собственной области, не видит локальных переменных вызывающей функции и сохраняет общее состояние для повторных обращений.

Пример двух файлов одного модуля:

```goat
// math.goat
const epsilon = 0.000001;
public square = func(x) { return x * x; };
```

```goat
// main.goat
const math = include "./math.goat";
println(math.square(5)); // 25
// math.epsilon недоступно из этого файла.
external square = math.square;
```

Потребитель готового модуля получает `square` через `import`. Автор явно формирует внешний интерфейс входного файла, в том числе переэкспортируя значения внутренних файлов.

## Уровни доступа

| Объявление | Граница доступа |
| --- | --- |
| Без модификатора | Только свой исходный файл |
| `public` | Все файлы своего модуля |
| `external` | Также другие модули |
| `protected` | Свой объект и его потомки по ранее согласованным правилам |
| `private` | Свой объект по ранее согласованным правилам |

`external` — самостоятельный модификатор, включающий доступность `public`. У объявления по-прежнему только один модификатор. Он ставится перед определением переменной или константы; при пропуске `const` подразумевается константа:

```goat
external f = func() {};
external var counter = 0;
```

Это изменение прежней модели: раньше `public` означал доступ между модулями, а отсутствие модификатора — доступ внутри модуля. Реализацию и старые примеры необходимо адаптировать, различая идентичности исходного файла и модуля. Правила объектов, захватов, `clone` и `flat` не отменяются; последствия новой границы доступа для них требуют отдельной сверки.

## Поиск

`include "./math.goat"` разрешается относительно исходного файла, содержащего выражение; переменная окружения не используется.

Для import используется единый набор каталогов программы: локальный modules, явно заданный --module-dir, затем GOAT_MODULE_PATH. Подробности для сборки и запуска приведены ниже. Разделитель GOAT_MODULE_PATH: `;` в Windows, `:` в Linux/macOS. Первый файл запрошенного имени и версии проверяется; повреждение или несовпадение ожидаемого основного хеша — ошибка без поиска другой сборки.

## Инициализация и циклы

Каждый исходный файл инициализируется один раз на запуск программы. Повторное подключение возвращает тот же объект области с текущими значениями переменных.

Объект области создаётся до выполнения кода файла. Циклические include внутри одного модуля разрешены: если файл уже инициализируется, возвращается существующий объект без повторного запуска. Чтение объявления, которое ещё не инициализировано, вызывает ошибку с цепочкой подключений. Циклы import между модулями запрещены.

```goat
// a.goat
const b = include "./b.goat";
public x = 10;

// b.goat
const a = include "./a.goat";
println(a.x); // Ошибка: x ещё не инициализировано.
```

Если вместо немедленного чтения файл b объявляет функцию, которая прочитает `a.x` после завершения инициализации, сам цикл этому не мешает.

Если инициализация завершается исключением, неудача и исключение запоминаются. Повторное подключение выбрасывает сохранённое исключение и не выполняет код заново: уже совершённые побочные эффекты не повторяются.

## ZIP и нативные реализации

Файл модуля — ZIP-контейнер с JSON-метаданными, байткодом и нативными библиотеками. Поддержка чтения и записи ZIP встраивается в Goat через небольшую переносимую библиотеку на C; внешние команды zip/unzip не требуются. Конкретная библиотека выбирается после проверки размера, лицензии и сборки на поддерживаемых платформах.

Основной хеш зависимости вычисляется по байткоду и общим метаданным, включая имена, версии и ожидаемые основные хеши зависимостей. Собственное поле хеша, нативные библиотеки и их описания исключаются. Каждая нативная библиотека имеет отдельный хеш в своём описании. Добавление платформы или пересборка нативной части не требуют пересборки потребителей, пока основная часть не изменилась.

Хеширование использует содержимое частей в фиксированном порядке. Порядок записей ZIP, временные метки и способ сжатия не влияют на идентичность. Алгоритм — SHA-256; согласованные правила канонического JSON приведены ниже.

Описание нативного варианта учитывает ОС и минимальную версию, архитектуру, разрядность, необходимые расширения процессора, системный ABI/среду исполнения (например, семейство и минимальную версию libc) и версию нативного ABI Goat. Неизвестное или непроверяемое обязательное требование делает вариант неподходящим. Несколько одновременно подходящих вариантов — ошибка неоднозначности. Точная схема требований платформ ещё не определена; метаданные сами по себе не гарантируют успешную загрузку ОС. Ограничение зависимостей только заранее перечисленными системными библиотеками не принято.

Нативная библиотека извлекается и загружается при первом вызове функции, которой она нужна. Нет совместимого варианта либо нативное исполнение отключено — используется VM. Если ОС не смогла загрузить выбранную библиотеку, обычный режим сообщает причину и переходит на VM. Неудача запоминается до конца запуска: повторные вызовы не повторяют попытку и сообщение. В режиме `--native required` невозможность загрузить требуемую нативную реализацию остаётся ошибкой.

Несовпадение хеша — повреждение модуля и ошибка, а не повод перейти на VM. Если нативная функция уже начала исполняться, повторно запускать её на VM нельзя: побочные эффекты не должны дублироваться. Это правило относится к обработке неудачной загрузки, а не к проектированию иных протоколов нативного исполнения.

## Объединение и просмотр модулей

Отдельная утилита goat-merge объединяет сборки одного модуля для разных платформ в один файл. Основные хеши должны совпадать; при несовпадении — ошибка. При одинаковых требованиях платформы одинаковые хеши нативных библиотек дают одну копию, разные — ошибку, без автоматического выбора или замены. Правило неоднозначности выбора совместимых вариантов сохраняется.

Отдельная утилита goat-inspect показывает имя, версию, основной хеш, зависимости и нативные варианты с требованиями. Она также пробует загрузить подходящую DLL/SO. Байткод модуля и его нативные функции не запускаются, но штатный загрузчик ОС может выполнить код инициализации библиотеки (DllMain или конструкторы SO).

Пробная загрузка выполняется в дочернем процессе, чтобы сбой не завершил основную команду. Зависший процесс завершается по таймауту; выводится результат проверки. Таймаут настраивается параметром команды; предложено значение по умолчанию 5 секунд. Это диагностический таймаут, а не ограничение обычного исполнения.

При составлении нового списка задач отдельно запланировать переносимую обвязку в `lib`: запуск текущего исполняемого файла с аргументами, ожидание/результат, таймаут и завершение дочернего процесса. Также отдельный API потоков: создание, ожидание завершения, мьютексы и условные переменные. Пул потоков пока не требуется. Потоки не заменяют процессы для изоляции аварий.

## Граф зависимостей и проверки перед запуском

Циклы `include` разрешены только внутри одного модуля. Циклические зависимости готовых модулей через `import` запрещены, с диагностикой цепочки. Модули собираются начиная с зависимостей. Предложения исключить хеши зависимостей из основного хеша и собирать взаимозависимую группу одновременно отменены.

Если A и B импортируют одну версию C, она загружается один раз на запуск и имеет общую область и состояние. Разные ожидаемые основные хеши одной пары «имя + версия» — ошибка несовместимых зависимостей.

До выполнения пользовательского кода проверяется весь граф зависимостей и всё, что возможно проверить без исполнения: доступность, структура, версии, хеши, отсутствие циклов и согласованность требований. Это относится и к зависимостям из ещё не выполненных веток. Проверка не выполняет код инициализации и не отменяет ленивую загрузку нативных библиотек.

Ошибки версии, хеша и структуры — ошибки загрузчика, которые нельзя перехватить Goat `try/catch`. Исключения из кода инициализации — обычные перехватываемые исключения языка.

## Ссылки на неуспешно инициализированный файл

При цикле include объект области может выйти наружу до завершения инициализации. После её неудачи любые последующие обращения к свойствам этой области выбрасывают сохранённое исключение, даже для уже заполненных свойств.

Вызов ранее переданной функции, определённой в неуспешно инициализированном файле, также выбрасывает сохранённое исключение. Это сохраняется для копий через `clone` и `flat`. Уже переданные обычные значения не отзываются; выполненные побочные эффекты не откатываются.

Пока инициализация ещё идёт, вызов уже объявленной функции разрешён. Она может использовать готовые значения; чтение ещё не инициализированного объявления вызывает исключение. Полный запрет вызова по состоянию файла наступает после неудачи инициализации.

## Имена, версии и расширения

Уточнение для реализации #179: максимальная длина имени — 255 ASCII-байт, версии — 250 ASCII-байт; запрещены также `com0` и `lpt0` с любыми расширениями. Внутренние повторные точки и завершающие `-`/`_` разрешены. Строки не нормализуются, сравниваются точно. Общий API разбора импортов для `char` и `wchar_t` возвращает срезы без копирования; `string_view_t` не меняется. Отдельная [глава книги](30-modules.md) постепенно описывает реализацию.



Версия — точный строковый идентификатор, например `1.2.0` или `1.2.0-beta.1`. Диапазонов, упорядочивания версий и автоматического подбора нет. Имена модулей и версии используют только строчные латинские буквы, цифры, точку, подчёркивание и дефис; первый символ — буква или цифра. Запрещены завершающая точка и зарезервированные Windows-имена, в том числе формы с расширением вроде `con.txt`. Ограничения одинаковы на всех ОС.

Расширения: `.goat` — исходники; `.gmod` — JSON-описание сборки; `.gbin` — ZIP-модуль. Проверяется содержимое и версия формата, а не только расширение.

Версии формата `.gmod`, контейнера `.gbin`, байткода и ABI Goat независимы от версии библиотеки. В `.gmod` обязательно `"formatVersion": 1`; отсутствие или неподдерживаемая версия — ошибка. Неизвестные и повторяющиеся поля JSON в описании и метаданных запрещены; новые поля вводятся через новую версию соответствующего формата. Неподдерживаемый байткод запрещает загрузку всего модуля даже при подходящей нативной части.

## Канонизация исходников и диагностика

При сборке пути include канонизируются, включая разрешение символических ссылок. Пути с одинаковым каноническим путём внутри модуля дают одну область, одну копию байткода и одну инициализацию; разные пути жёстких ссылок различаются по решению 156.

Include за пределами каталога описания разрешён. Включённый файл принадлежит собираемому модулю; включение того же исходника другим модулем создаёт отдельную копию и состояние. Рекомендация для пользователя: общий переиспользуемый код лучше оформлять небольшими модулями и подключать через import, а не размножать через внешние include.

В модуле сохраняются логическое имя исходного файла, строка, столбец и имя функции. Исходники и абсолютные пути машины сборки не сохраняются. Внешним исходникам назначаются отдельные логические имена; таблица соответствия нужна и для ошибок нативного кода. Пример диагностики:

```text
geometry@1.2.0: src/vector.goat:24:9, length
```

## Прямой запуск и встроенные константы

Прямой запуск готового модуля выполняет код входного файла; обязательной функции main нет. При импорте этот код служит однократной инициализацией.

`__main__` — встроенная булева константа, истинная только во входном файле прямо запускаемого модуля или отдельного исходника. Во включённых файлах и импортируемых модулях она ложна. Присваивание и переобъявление в любой области запрещены.

```goat
external square = func(x) { return x * x; };
if (__main__) {
    println(square(5));
}
```

Значение определяется исходным файлом объявления функции, а не вызывающим кодом. Clone/flat сохраняют эту связь. Оно устанавливается при запуске: компилятор и нативный генератор не могут навсегда подставить значение, зависящее от способа запуска, и удалить нужную ветку.

`__dir__` — встроенная строковая константа с абсолютным путём каталога главного запускаемого .gbin либо главного .goat. Она общая для всего запуска, включая библиотеки; это не каталог библиотеки. Присваивание и переобъявление запрещены; значение не зашивается при сборке.

Ресурсы пока не включаются в архив. Данные программы лежат рядом с ней и могут находиться через `__dir__`. Упаковку ресурсов по метаданным и API их чтения можно добавить позже.

## Каталоги сборки и единый поиск

В корне хранилища используется структура `<имя>/<версия>.gbin`, например `geometry/1.2.0.gbin`. Отдельного каталога версии и файла module.gbin нет. Имя и версия в метаданных должны совпадать с запросом; рекурсивный поиск произвольных архивов не выполняется.

Компилятор принимает `--module-dir` и создаёт эту структуру, включая недостающие каталоги. Без параметра используется каталог modules рядом с .gmod, независимо от рабочего каталога. Успешная сборка заменяет существующую версию без подтверждения через временный файл; неудачная сохраняет прежний результат.

При сборке порядок поиска: modules рядом с .gmod, затем явно заданный --module-dir, затем GOAT_MODULE_PATH. Повторяющиеся каталоги проверяются один раз.

При запуске порядок поиска: modules рядом с главным .gbin (либо главным .goat), затем --module-dir, затем GOAT_MODULE_PATH. Это один набор каталогов для всего запуска, включая косвенные импорты. Каталог каждого импортирующего файла не добавляется; корень хранилища не угадывается по расположению архива. Эти правила заменяют первоначальный поиск рядом с импортирующим файлом.

Пример переносимой поставки:

```text
my-app/
    app.gbin
    modules/
        geometry/
            1.2.0.gbin
    config.json
    data/
```

Запуск из общего хранилища с явным корнем:

```sh
goat modules/app/1.0.0.gbin --module-dir ./modules
```

## Параметры нативной сборки

Пример описания (все показанные поля согласованы, полная схема ещё проектируется):

```json
{
  "formatVersion": 1,
  "name": "geometry",
  "version": "1.2.0",
  "main": "src/main.goat",
  "dependencies": { "math": "2.0.0" },
  "native": { "mode": "auto", "target": "host" }
}
```

Режимы off/auto/required задаются в .gmod и могут переопределяться командной строкой; по умолчанию auto. В auto отсутствие C-компилятора даёт предупреждение и модуль только с байткодом. Если компилятор найден, но сгенерированный C не собирается, это ошибка сборки, а не тихий переход к байткоду.

Required требует хотя бы одну нативную реализацию в самом собираемом модуле; код зависимостей не считается. Остальные функции могут оставаться в VM. Если нативных реализаций нет, сборка завершается ошибкой.

За сборку создаётся вариант для одной целевой платформы. Поле target — строка, по умолчанию host; параметр --native-target имеет приоритет. Host разрешается в конкретные требования текущей платформы и не сохраняется как абстрактное слово в .gbin. Явно выбранная другая платформа без настроенного подходящего компилятора — ошибка, а не сборка для текущей машины.

По умолчанию используются базовые инструкции целевой архитектуры, без автоматического -march=native. Дополнительные расширения включаются явно и отражаются в метаданных. Путь C-компилятора и дополнительные флаги задаются командной строкой или окружением, не машинными путями в .gmod.

Режим, целевая нативная платформа, выбор C-компилятора и его флаги не входят в основной хеш. При неизменных байткоде и общих метаданных варианты off/auto/required можно объединять. Одинаковые исходники, настройки основной компиляции и зависимости должны давать одинаковый основной хеш на Windows и Linux; это проверяется тестами. Даты сборки, абсолютные пути и случайные идентификаторы в основную часть не попадают.

Нативные библиотеки пока не вызывают друг друга напрямую и не встраивают код друг друга: межмодульные вызовы проходят через механизм Goat. Загруженные модули и библиотеки удерживаются до завершения программы.

## Проверка и временные файлы

Перед запуском проверяются хеши всех нативных частей, в том числе для чужих платформ, без загрузки этих библиотек ОС. Повторяющиеся имена ZIP-записей, абсолютные пути и компоненты .. запрещены. Ссылки метаданных должны однозначно указывать на существующие части архива.

Для запуска создаётся отдельный временный каталог. Нативные библиотеки извлекаются по необходимости и переиспользуются внутри запуска; постоянного кеша пока нет. Временный каталог после завершения процесса удаляет заранее запущенный уборщик по решению 152. Неудача очистки даёт предупреждение и не меняет исходный код завершения программы.

## Утилиты и описание нативного ABI

Просмотр и объединение — отдельные утилиты:

```sh
goat-merge windows.gbin linux.gbin --output geometry.gbin
goat-inspect geometry.gbin
```

Они входят в дистрибутив и проверяются пакетными тестами. Общая реализация чтения, проверки и упаковки используется повторно. Merge проверяет все входы, совпадение имени, версии и основного хеша, затем записывает результат через временный файл. Ошибка сохраняет прежний выходной файл.

Inspect проверяет в дочернем процессе загрузку подходящей библиотеки и наличие всех заявленных символов без вызова функций. Повреждение, ошибка загрузки или отсутствие символа дают ненулевой код завершения. Отсутствие варианта для текущей платформы — нормальный результат с сообщением.

При обычном исполнении все символы проверяются после загрузки до первого вызова. Отсутствие одного делает непригодной всю выбранную библиотеку: обычный режим один раз сообщает причину и использует VM; required и inspect сообщают ошибку.

Библиотека экспортирует генерируемую компилятором JSON-строку UTF-8 без небольшого фиксированного лимита. Она заменяет ранее предложенную короткую структуру ABI. Загрузчик читает её через экспортируемый символ без вызова функций и сверяет с метаданными .gbin. Строка содержит версию своего формата, имя и версию модуля, основной хеш, версию ABI Goat, требования платформы, список нативных символов и идентификаторы их ABI-сигнатур. Пример части описания:

```json
{
  "formatVersion": 1,
  "module": "geometry",
  "version": "1.2.0",
  "mainHash": "...",
  "goatAbiVersion": 1,
  "target": { "os": "linux", "architecture": "aarch64" }
}
```

Полная схема списка функций и служебное имя символа пока не определены. Проверка сверяет заявленный ABI; она не доказывает поведение машинного кода. Отсутствующее/несовместимое описание обрабатывается как непригодная библиотека. Хеш самой DLL/SO хранится только снаружи, чтобы не создавать самоссылку.

## SHA-256, JSON и зависимости реализации

Основной хеш и хеши нативных библиотек используют SHA-256 и записываются 64 шестнадцатеричными символами нижнего регистра. JSON хешируется в каноническом представлении: UTF-8, сортировка ключей объектов, фиксированная запись значений, отсутствие лишних пробелов. Порядок массивов сохраняется. Изменение форматирования и порядка полей не меняет хеш. Исключаются только явно определённые поля; точные правила канонизации нужно специфицировать.

Для сторонних библиотек предусматривается third_party/ (ZIP, JSON, при необходимости SHA-256), с лицензией, источником и точной версией каждой зависимости. Сборка не требует их скачивания. Обёртки Goat находятся в lib. JSON-библиотека должна позволять выявлять повторяющиеся ключи и выполнять каноническую запись; конкретные библиотеки ещё не выбраны.

## Файловая видимость, копирование и принадлежность объектов

При clone и flat перенесённые поля сохраняют исходные файл, модуль и ограничения доступа. Перенесённые методы сохраняют права, а их захваты перенаправляются на копируемые ячейки по согласованным правилам. Удаление прототипов при flat не открывает скрытые поля.

```goat
// a.goat
public obj = {
    var secret = 42;
    public read = func() { return secret; };
};

// b.goat того же модуля
const a = include "./a.goat";
var copy = a.obj.clone();
println(copy.read()); // 42.
// println(copy.secret); // Ошибка доступа.
```

Код одного модуля может добавлять свойства в объекты, созданные другими файлами этого модуля. Принадлежность объекта определяет право расширения, принадлежность поля — доступ к нему:

```goat
// a.goat
public obj = { public var x = 1; };

// b.goat
const a = include "./a.goat";
a.obj.x = 2; // Доступная переменная.
a.obj.y = 3; // Добавление разрешено внутри модуля.
println(a.obj.y); // 3.
```

Поле y принадлежит b.goat и без модификатора доступно только коду этого файла. Последующее obj.y = 4 из a.goat вызывает ошибку доступа: скрытое существующее поле не считается отсутствующим, второе поле с тем же ключом обычным присваиванием не создаётся. Чужой модуль не может расширять исходный объект, даже получив его через external.

Результат clone/flat принадлежит модулю кода, непосредственно вызвавшего встроенную операцию. Поэтому B может расширить копию объекта A, но её перенесённые поля сохраняют защиту A. Новые поля принадлежат файлу, который их добавляет. Обёртка, объявленная в A и вызывающая obj.clone(), создаёт объект A, даже если обёртку вызвали из B.

То же правило действует для фабрик: объект, созданный функцией A, принадлежит A независимо от вызывающего кода. B может менять доступные external-переменные такого объекта, а для расширения должен сделать собственную копию. Потомок, созданный кодом B через прототип A -> конструктор, принадлежит B; поля прототипа сохраняют защиту A, включая ранее согласованные права protected.

## Наблюдение из другого файла

Перебор ключей, print, str и остальные строковые представления используют права наблюдающего кода. Код другого файла того же модуля видит public и external; поля без модификатора доступны только коду исходного файла. Для private/protected нужны соответствующие права объекта, совпадения файла недостаточно.

```goat
// a.goat
public obj = {
    var hidden = 10;
    public var shared = 20;
    external var exported = 30;
    private var secret = 40;
};

// b.goat
const a = include "./a.goat";
println(a.obj); // Только shared и exported.
var copy = a.obj.clone();
println(copy);  // Также только shared и exported.
```

Копия содержит все четыре поля. Обычный внешний по отношению к объекту код a.goat при печати дополнительно видит hidden, но не secret. Перебор из тех же контекстов показывает тот же доступный набор собственных ключей. Копирование полного состояния не превращается в копирование только видимых полей.

## Права функций: пять согласованных примеров

Примеры независимы. Файлы a.goat и b.goat в первых четырёх случаях принадлежат одному модулю. Права задаются происхождением исполняемого кода, не местом вызова или хранения ссылки.

### 1. Функция печатает с правами своего файла

```goat
// a.goat
public obj = {
    var hidden = 10;
    public var shared = 20;
};
public show = func(value) { println(value); };

// b.goat
const a = include "./a.goat";
println(a.obj); // Только shared.
a.show(a.obj);  // hidden и shared.
```

Автор a.goat может намеренно предоставить функцию, раскрывающую данные этого файла. Вызов из b.goat не отнимает у show её права.

### 2. Callback не получает права вызывающей функции

```goat
// a.goat
public obj = {
    var hidden = 10;
    public var shared = 20;
};
public inspect = func(callback) { callback(obj); };

// b.goat
const a = include "./a.goat";
const show = func(value) { println(value); };
a.inspect(show); // Только shared.
```

Show исполняется с правами b.goat. Чтение value.hidden внутри неё вызвало бы ошибку доступа, хотя вызов сделан из a.goat.

### 3. Возвращённое замыкание сохраняет права и захваты

```goat
// a.goat
public makeReader = func() {
    const obj = { var hidden = 10; };
    return func() { return obj.hidden; };
};

// b.goat
const a = include "./a.goat";
const read = a.makeReader();
println(read()); // 10.
```

Это геттер с захваченным объектом: функция сохраняет права a.goat после возврата, но не предоставляет вызывающему коду прямой доступ к скрытому объекту.

### 4. Хранение функции как метода не меняет её файл

```goat
// b.goat
public readHidden = func(obj) { return obj.hidden; };

// a.goat
const b = include "./b.goat";
public obj = {
    var hidden = 10;
    public read = b.readHidden;
};
obj.read(obj); // Ошибка доступа.
```

ReadHidden остаётся кодом b.goat. Сохранение ссылки как метода объекта a.goat не даёт файловых прав a.goat.

### 5. Переэкспорт сохраняет права исходной функции

```goat
// internal.goat
const obj = { var hidden = 10; };
public read = func() { return obj.hidden; };

// main.goat — входной файл библиотеки
const internal = include "./internal.goat";
external read = internal.read;

// Программа другого модуля
const lib = import "library@1.0.0";
println(lib.read()); // 10.
```

External открывает ссылку на функцию. Она сохраняет права internal.goat и захваты; скрытый объект напрямую наружу не открывается.

## Доступ к значениям и замена функций: примеры 6–10

Примеры независимы. External открывает конкретное объявление, а не рекурсивно всё содержимое значения.

### 6. Экспорт объекта не экспортирует его поля автоматически

```goat
// Входной файл library
external obj = {
    public var internal = 10;
    external var shared = 20;
};

// Другая программа
const lib = import "library@1.0.0";
println(lib.obj.shared);   // 20.
// println(lib.obj.internal); // Ошибка доступа.
```

Ссылка obj доступна снаружи; internal остаётся доступным только коду модуля library. Проверяется каждое обращение к полю.

### 7. Возврат объекта не передаёт права функции

```goat
// Входной файл library
const obj = {
    var hidden = 10;
    external var shared = 20;
};
external getObject = func() { return obj; };

// Другая программа
const lib = import "library@1.0.0";
const obj = lib.getObject();
println(obj.shared); // 20.
// println(obj.hidden); // Ошибка доступа.
```

GetObject может читать hidden, но получатель объекта не получает это право. Библиотека может намеренно раскрыть значение через отдельный геттер.

### 8. Константность ссылки не делает массив неизменяемым

```goat
// Входной файл library
external items = [1, 2];

// Другая программа
const lib = import "library@1.0.0";
lib.items.push(3);  // Разрешено: [1, 2, 3].
// lib.items = [4, 5]; // Ошибка: items — константа.
```

Ограничения поля не запрещают операции над полученным изменяемым значением. Для независимых данных библиотека возвращает копию через функцию; это не означает автоматического глубокого копирования.

В новый список GitHub-задач включить отдельную задачу на функцию создания неизменяемых объектов-обёрток, например обёртки массива. Точная семантика, глубина защиты и поведение при изменении исходного объекта через другую ссылку ещё не согласованы. Обёртки не являются уже реализованной частью модулей.

### 9. Присваивание сохраняет происхождение поля

```goat
// a.goat
public obj = { public var value = 1; };

// b.goat того же модуля
const a = include "./a.goat";
a.obj.value = 2;
```

Меняется только значение. Поле value сохраняет принадлежность a.goat и модификатор public; оно не становится локальным для b.goat.

### 10. Права поля и новой функции независимы

```goat
// a.goat
public obj = {
    var hidden = 10;
    public var read = func() { return hidden; };
};

// b.goat того же модуля
const a = include "./a.goat";
a.obj.read = func() { return a.obj.hidden; };
a.obj.read(); // Ошибка доступа к hidden.
```

Read остаётся публичным полем a.goat. Новая функция принадлежит b.goat и не наследует права заменённой функции. Даже последующий вызов из a.goat не даёт новой функции файловых прав a.goat.

## Переэкспорт и порядок присваиваний: примеры 11–15

Каждый пример независим; строки с ожидаемыми ошибками проверяются отдельно.

### 11. Переэкспорт переменной создаёт отдельную ячейку

```goat
// internal.goat
public var counter = 0;

// main.goat
const internal = include "./internal.goat";
external var counter = internal.counter;
counter = 5;
println(internal.counter); // 0.
```

Это обычное объявление с присваиванием значения, не живая связь двух переменных. Для массива или объекта обе ячейки первоначально содержат ссылку на один объект; замена ссылки в одной ячейке не меняет другую.

### 12. Область внутреннего файла можно явно переэкспортировать

```goat
// internal.goat
public helper = func() { return 10; };
external api = func() { return 20; };

// main.goat библиотеки
external tools = include "./internal.goat";

// Программа другого модуля
const lib = import "library@1.0.0";
println(lib.tools.api()); // 20.
// println(lib.tools.helper()); // Ошибка доступа.
```

Прямой импорт внутреннего файла остаётся запрещённым. Автор явно открыл ссылку на область, но доступ проверяется для каждого её поля; public не превращается в external.

### 13. Индекс и точка проверяют одинаковые права

```goat
// a.goat
public obj = {
    var hidden = 10;
    public var shared = 20;
};

// b.goat
const a = include "./a.goat";
println(a.obj["shared"]); // 20.
// println(a.obj["hidden"]); // Ошибка доступа.
```

Для чтения и записи через [] применяются те же правила доступа, что для точки. Однозначно доказанный запрет — ошибка компиляции. Если определить доступ статически нельзя, проверку выполняет VM; вычисляемый ключ не обходит защиту.

### 14. Ошибка чтения в составном присваивании предшествует правой части

```goat
// a.goat
public obj = { var hidden = 10; };

// b.goat
const a = include "./a.goat";
const rhs = func() {
    println("Выполнено");
    return 1;
};
const update = func(target, key) {
    target[key] += rhs();
};
update(a.obj, "hidden"); // Ошибка доступа; rhs не вызывается.
```

При проверке во время исполнения порядок таков: вычислить объект и ключ один раз, прочитать левую часть, вычислить правую часть, применить операцию, записать результат. Если чтение запрещено, правая часть не вычисляется, надпись не появляется и поле не меняется. Это делает порядок побочных эффектов предсказуемым. Уже выполненные эффекты вычисления объекта и ключа не откатываются.

### 15. Обычное присваивание проверяет запись до правой части

```goat
// a.goat
public obj = { var hidden = 10; };

// b.goat
const a = include "./a.goat";
const rhs = func() {
    println("Выполнено");
    return 1;
};
const write = func(target, key) {
    target[key] = rhs();
};
write(a.obj, "hidden"); // Ошибка доступа; rhs не вызывается.
```

Объект и ключ вычисляются по одному разу; затем проверяются доступ и допустимость записи. Правая часть вычисляется только после успешной проверки. Это относится также к записи в константу и запрещённому добавлению поля в объект чужого модуля. Ошибка, обнаруженная до правой части, предотвращает её побочные эффекты. Описанный порядок — требование к реализации, включая оптимизации; раздел не утверждает, что новая модульная модель уже реализована.

## Присваивание и побочные эффекты: примеры 16–20

Примеры независимы. Это требования к порядку исполнения, включая оптимизированный и нативный код, когда соответствующая операция поддерживается. Однозначно доказанная статическим анализом ошибка по-прежнему может отклонить программу до запуска; ниже описан порядок при проверках во время исполнения.

### 16. Составное присваивание заранее проверяет возможность записи

```goat
const obj = { public limit = 10; };
const rhs = func() {
    println("Выполнено");
    return 1;
};
const update = func(target, key) {
    target[key] += rhs();
};
update(obj, "limit"); // Ошибка изменения константы, без печати.
```

Разрешённого чтения недостаточно. Доступ и возможность записи проверяются до вычисления правой части также у составного присваивания. Rhs не вызывается, если результат нельзя записать. Это дополняет порядок из примера 14 ранней проверкой записи.

### 17. Используется значение, прочитанное до правой части

```goat
var obj = { public var x = 10; };
const rhs = func() {
    obj.x = 100;
    return 2;
};
obj.x += rhs();
println(obj.x); // 12, не 102.
```

Составное присваивание запоминает исходное значение 10. Rhs записывает 100, после чего операция вычисляет 10 + 2 и записывает 12. Повторного чтения левой части нет.

### 18. Исключение отменяет итоговую запись, но не побочные эффекты

```goat
var obj = { public var x = 10; };
const rhs = func() {
    obj.x = 100;
    throw "Ошибка";
};
try {
    obj.x += rhs();
} catch (e) {
    println(obj.x); // 100.
}
```

Результат сложения не вычисляется и не записывается после исключения. Уже выполненные изменения правой части сохраняются. Присваивание не является транзакцией и не откатывает побочные эффекты.

### 19. Объект назначения запоминается до правой части

```goat
var obj = { public var x = 10; };
const original = obj;
const rhs = func() {
    obj = { public var x = 100; };
    return 2;
};
obj.x += rhs();
println(original.x); // 12.
println(obj.x);      // 100.
```

Замена переменной obj не перенаправляет уже начатую запись. Назначение — исходный объект. Это относится и к обычному obj.x = rhs(): объект слева повторно не вычисляется.

### 20. Вычисленный ключ также запоминается

```goat
var obj = {
    public var x = 10;
    public var y = 20;
};
var key = "x";
const rhs = func() {
    key = "y";
    return 2;
};
obj[key] += rhs();
println(obj.x); // 12.
println(obj.y); // 20.
println(key);   // y.
```

Запоминаются объект и вычисленный ключ x. Изменение переменной key не переводит запись в y. То же правило действует для обычного obj[key] = rhs(). Эти примеры фиксируют однократность вычисления объекта/ключа и, для составного присваивания, однократность чтения исходного значения; отката эффектов не предусмотрено.

## Повторная проверка записи: примеры 21–25

Примеры независимы. Предварительная проверка до правой части не заменяет окончательную: правая часть может изменить состояние назначения. Повторная проверка не вычисляет заново выражения объекта и ключа и не перечитывает исходное значение составного присваивания.

### 21. Правая часть создала недоступное поле

```goat
// a.goat
public obj = {};
public prepare = func() {
    obj.x = 100; // Поле принадлежит a.goat.
    return 2;
};

// b.goat того же модуля
const a = include "./a.goat";
a.obj.x = a.prepare(); // Ошибка доступа при окончательной записи.
```

Сначала x отсутствует, и b.goat вправе добавить поле внутри своего модуля. Prepare создаёт x с файловой видимостью a.goat. Перед окончательной записью проверка обнаруживает запрет. Поле x со значением 100 сохраняется как выполненный побочный эффект; запись 2 не происходит.

### 22. Отсутствующее поле не создаётся заранее

```goat
var obj = {};
const rhs = func() {
    println(obj); // { }.
    throw "Ошибка";
};
try {
    obj.x = rhs();
} catch (e) {
    println(obj); // { }.
}
```

Предварительная проверка только разрешает будущую запись. Поле появляется после успешного вычисления правой части и окончательной проверки. Временной ячейки-заглушки нет; при исключении пустой объект остаётся пустым.

### 23. Доступное поле, созданное правой частью, обновляется

```goat
// a.goat
public obj = {};
public prepare = func() {
    obj.x = 100; // Поле принадлежит a.goat.
    return 2;
};
obj.x = prepare();
println(obj.x); // 2.
```

Обе записи исполняются кодом a.goat, поэтому окончательная проверка проходит. Используется уже созданная prepare ячейка с её исходной принадлежностью и метаданными; новая ячейка вместо неё не создаётся.

### 24. Индекс массива обозначает позицию, а не прежний элемент

```goat
var items = [10, 20, 30];
const rhs = func() {
    items.remove(0); // [20, 30].
    return 2;
};
items[1] += rhs();
println(items); // [20, 22].
```

Запоминаются массив, индекс 1 и прочитанное значение 20. После удаления вычисляется 20 + 2, затем 22 записывается в текущую позицию 1 того же массива. Запись не следует за элементом, сдвинувшимся в другую позицию.

### 25. Исчезнувшая позиция вызывает ошибку окончательной записи

```goat
var items = [10, 20];
const rhs = func() {
    items.clear();
    return 2;
};
try {
    items[1] += rhs();
} catch (e) {
    println(items); // [ ].
}
```

Первоначальное чтение успешно. После clear сохранённый индекс выходит за границы, и окончательная проверка запрещает запись. Массив не расширяется автоматически; выполненная очистка не откатывается.

## Исключения и состояния инициализации: примеры 26–30

Примеры независимы. Неудача инициализации определяется выходом исключения из верхнеуровневого кода файла, а не самим фактом возникновения исключения.

### 26. Внутренний catch позволяет успешно завершить инициализацию

```goat
// settings.goat
public var value = 10;
try {
    throw "Нет конфигурации";
} catch (e) {
    value = 20;
}

// main.goat
const settings = include "./settings.goat";
println(settings.value); // 20.
```

Исключение перехвачено внутри settings.goat, верхнеуровневый код завершился нормально. Файл успешно инициализирован; перехваченное исключение его не блокирует.

### 27. Перехват ошибки подключаемого файла не блокирует вызывающий файл

```goat
// broken.goat
println("Попытка");
throw "Ошибка";

// main.goat
public var ready = false;
try {
    const broken = include "./broken.goat";
} catch (e) {
    ready = true;
}
```

Main успешно инициализирован, broken — неуспешно. Повторный include broken выбрасывает сохранённое исключение без повторного исполнения; «Попытка» печатается один раз.

### 28. Неперехваченное исключение прерывает всю активную цепочку

```goat
// c.goat
println("C");
throw "Ошибка C";

// b.goat
const c = include "./c.goat";

// main.goat
try {
    const b = include "./b.goat";
} catch (e) {
    println(e);
}
```

C и B запоминают неудачу, поскольку исключение вышло за пределы инициализации каждого из них. Main перехватывает исключение и продолжает работу. Повторное подключение B или C выбрасывает сохранённое исключение без повторного исполнения; C больше не печатается.

### 29. Ошибка функции после инициализации не меняет состояние файла

```goat
// library.goat
public fail = func() { throw "Ошибка вызова"; };
public value = 42;

// main.goat
const lib = include "./library.goat";
try {
    lib.fail();
} catch (e) {
    println(e);
}
println(lib.value); // 42.
```

Library уже успешно инициализирован. Исключение относится к вызову fail, не превращает файл в неуспешный и не блокирует другие обращения. Повторный include возвращает прежнюю область.

### 30. Неудача потребителя не отменяет готовую зависимость

```goat
// b.goat
println("Инициализация B");
public value = 42;

// a.goat
const b = include "./b.goat";
throw "Ошибка A";

// main.goat
try {
    const a = include "./a.goat";
} catch (e) {
    println(e);
}
const b = include "./b.goat";
println(b.value); // 42.
```

B успел завершить инициализацию до ошибки A и остаётся работоспособным. «Инициализация B» печатается один раз. Неудача A не отменяет состояние успешно завершённой зависимости и не запускает её повторно.

## Сохранённые исключения и finally: примеры 31–35

Примеры независимы; файлы в каждом примере принадлежат одному модулю.

### 31. Повторно выбрасывается то же значение без клонирования

```goat
// broken.goat
throw { public var message = "Ошибка"; };

// main.goat
try {
    const first = include "./broken.goat";
} catch (e) {
    e.message = "Уточнённая ошибка";
}
try {
    const second = include "./broken.goat";
} catch (e) {
    println(e.message); // Уточнённая ошибка.
}
```

Загрузчик сохраняет ссылку на тот же объект исключения, не делает скрытой копии и не замораживает его. Обработчик может изменить доступные изменяемые поля или вложенные значения; последующие обработчики увидят изменения. Это сознательно принятое следствие обычной семантики значений. Поверхностная копия не обеспечила бы независимости вложенных объектов. Отдельное неизменяемое диагностическое представление загрузчика этим решением не утверждено.

### 32. Распространение одной ошибки сохраняет общую ссылку

```goat
// c.goat
throw { public var message = "Ошибка C"; };

// b.goat
const c = include "./c.goat";

// main.goat
try {
    const b = include "./b.goat";
} catch (e) {
    e.message = "Уточнённая ошибка";
}
try {
    const c = include "./c.goat";
} catch (e) {
    println(e.message); // Уточнённая ошибка.
}
```

Исключение прошло через B без замены и копирования. B и C сохраняют одну ссылку, поэтому изменение в обработчике результата подключения B видно при повторном подключении C.

### 33. Перехват с новой ошибкой разделяет сохранённые значения

```goat
// c.goat
throw "Ошибка C";

// b.goat
try {
    const c = include "./c.goat";
} catch (e) {
    throw "Ошибка B";
}

// main.goat
try {
    const b = include "./b.goat";
} catch (e) {
    println(e); // Ошибка B.
}
try {
    const c = include "./c.goat";
} catch (e) {
    println(e); // Ошибка C.
}
```

Каждый файл запоминает исключение, окончательно вышедшее из его собственного кода инициализации. Новая ошибка B не заменяет сохранённую ошибку C.

### 34. Исключение из finally становится окончательной ошибкой

```goat
// broken.goat
try {
    throw "Первая ошибка";
} finally {
    throw "Ошибка очистки";
}

// main.goat
try {
    const broken = include "./broken.goat";
} catch (e) {
    println(e); // Ошибка очистки.
}
```

Повторное подключение тоже выбрасывает «Ошибка очистки». Загрузчик сохраняет окончательно вышедшее исключение, не сохраняет отдельно первую ошибку и не меняет обычную семантику try/finally.

### 35. Finally не повторяется при повторном подключении

```goat
// broken.goat
try {
    throw "Ошибка";
} finally {
    println("Очистка");
}

// main.goat
try {
    const first = include "./broken.goat";
} catch (e) {
    println(e);
}
try {
    const second = include "./broken.goat";
} catch (e) {
    println(e);
}
```

Вывод:

```text
Очистка
Ошибка
Ошибка
```

Finally выполняется при первой попытке инициализации. Повторный include только выбрасывает сохранённое исключение; ни основной код, ни очистка снова не запускаются.

## Частичная инициализация области: примеры 36–40

Примеры независимы; циклы include происходят внутри одного модуля. Они не разрешают циклы import между модулями.

### 36. Преждевременное чтение можно перехватить

```goat
// a.goat
const b = include "./b.goat";
public x = 10;

// b.goat
const a = include "./a.goat";
try {
    println(a.x);
} catch (e) {
    println("Пока рано");
}

// main.goat
const a = include "./a.goat";
println(a.x); // 10.
```

Чтение известной, но ещё не инициализированной ячейки вызывает обычное перехватываемое исключение. B перехватывает его и завершается; A продолжает выполнение и объявляет x. Оба файла успешно инициализированы. Само преждевременное чтение не переводит A в состояние неудачи.

### 37. Запись в ещё не инициализированное объявление запрещена

```goat
// a.goat
const b = include "./b.goat";
public var x = 10;

// b.goat
const a = include "./a.goat";
try {
    a.x = 20;
} catch (e) {
    println("Пока рано");
}

// main.goat
const a = include "./a.goat";
println(a.x); // 10.
```

Объявление x уже известно, но не выполнено. Ячейка не считается отсутствующим полем, которое можно создать обычной записью. Даже доступная переменная не может быть записана раньше своего объявления. Исключение перехватывается; после возврата из B инициализатор A записывает 10.

### 38. Наблюдение пропускает ещё не готовые объявления

```goat
// a.goat
public first = 1;
const b = include "./b.goat";
public second = 2;

// b.goat
const a = include "./a.goat";
println(a); // Только first.

// main.goat
const a = include "./a.goat";
println(a); // first и second.
```

Печать и перебор частично инициализированной области пропускают ещё не выполненные объявления: их значения не заменяются null, а ключи не выдаются при переборе. Обычные ограничения видимости тоже действуют. Прямое чтение a.second из B по-прежнему вызывает исключение; пропуск при наблюдении не означает отсутствия ячейки.

### 39. Копирование незавершённой области запрещено

```goat
// a.goat
public first = 1;
const b = include "./b.goat";
public second = 2;

// b.goat
const a = include "./a.goat";
try {
    const copy = a.clone();
} catch (e) {
    println("Пока нельзя копировать");
}
```

Clone и flat объекта области файла до завершения её инициализации вызывают перехватываемое исключение. Не нужно ни отбрасывать неготовые ячейки, ни переносить их в копию, где их объявления уже не выполнятся. После успешной инициализации копирование разрешено. Это ограничение относится к самой области файла, а не ко всем обычным объектам, создаваемым во время инициализации.

### 40. Наследование от незавершённой области разрешено

```goat
// a.goat
const b = include "./b.goat";
public value = 10;
public child = b.child;

// b.goat
const a = include "./a.goat";
public child = a -> {};

// main.goat
const a = include "./a.goat";
println(a.child.value); // 10.
```

Наследование сохраняет ссылку на прототип, не копируя его неготовые ячейки. До выполнения объявления чтение value через потомка вызывает исключение, как прямое чтение из A. После успешной инициализации значение доступно через прототип с обычной проверкой прав.

## Области-прототипы и копирование: примеры 41–45

### 41. Неудачный прототип не блокирует собственные поля потомка

```goat
// a.goat
public value = 10;
const b = include "./b.goat";
throw "Ошибка A";

// b.goat
const a = include "./a.goat";
public child = a -> { public own = 20; };

// main.goat
try {
    const a = include "./a.goat";
} catch (e) {
    println(e);
}
const b = include "./b.goat";
println(b.child.own);   // 20.
// println(b.child.value); // Сохранённое исключение «Ошибка A».
```

B успел успешно инициализироваться, поэтому собственные доступные поля child остаются доступны. Поиск, дошедший до неуспешной области A, выбрасывает сохранённое исключение: наследование не обходит защиту такой области.

### 42. Flat не возвращает частичный результат при неуспешном прототипе

В состоянии из примера 41:

```goat
try {
    const flat = b.child.flat();
} catch (e) {
    println(e); // Ошибка A.
}
println(b.child.own); // 20.
```

Встроенный flat должен перенести состояние прототипов, поэтому выбрасывает сохранённое исключение A. Он не пропускает ошибочный прототип и не возвращает частичный объект только с own. Исходный объект не изменяется.

### 43. Clone потомка сохраняет ссылку на неуспешный прототип

В том же состоянии:

```goat
const copy = b.child.clone();
println(copy.own); // 20.
// println(copy.value); // Сохранённое исключение «Ошибка A».
```

Встроенный clone копирует только собственные поля и сохраняет ссылки на прототипы, не читая их поля. Поэтому копирование потомка разрешено, а обращения через неуспешный прототип остаются ошибочными. Это не разрешает clone самой неуспешной области файла.

### 44. Flat запрещён и при ещё не завершившейся инициализации прототипа

```goat
// a.goat
public first = 1;
const b = include "./b.goat";
public second = 2;

// b.goat
const a = include "./a.goat";
public child = a -> { public own = 3; };
try {
    const copy = child.flat();
} catch (e) {
    println("Пока нельзя");
}
```

Child уже создан, но A ещё не завершил инициализацию. Flat вызывает перехватываемое исключение о неготовом прототипе. После успешного завершения A тот же вызов разрешён.

### 45. Проверяется весь граф прототипов

```goat
// a — ранее полученная ссылка на область файла.
const middle = a -> { public middleValue = 2; };
const leaf = middle -> { public own = 3; };
const copy = leaf.flat();
```

Если A ещё инициализируется, flat выбрасывает исключение о незавершённой инициализации. Если A завершился ошибкой, выбрасывается сохранённое исключение. Проверка охватывает всю цепочку и все ветви множественного наследования, а не только непосредственные прототипы. Частичный результат не возвращается. Это дополняет согласованный обход прототипов с сохранением приоритета и однократным переносом каждого объекта.

## Идентичность модулей и строгий поиск: примеры 46–50

### 46. Разные версии — разные сущности и границы доступа

```goat
// Код geometry@2.0.0
const old = import "geometry@1.0.0";
println(old.api); // Разрешено, если api объявлено external.
// println(old.internal); // Ошибка, если internal объявлено public.
// old.extra = 1; // Ошибка: расширение чужого объекта.
```

Geometry@1.0.0 и geometry@2.0.0 — разные модули с отдельным состоянием и правами. Совпадение имени не даёт внутреннего доступа к другой версии. Обмен идёт через external, как между любыми разными модулями.

### 47. Физические копии одной сборки не создают разные экземпляры

```goat
// Входной файл geometry@1.0.0
external var counter = 0;

// consumer-a.goat
const geometry = import "geometry@1.0.0";
geometry.counter = 7;

// consumer-b.goat, выполняется после consumer-a.goat
const geometry = import "geometry@1.0.0";
println(geometry.counter); // 7.
```

Даже если одинаковая версия с одинаковым основным хешем находится и в локальном modules, и в GOAT_MODULE_PATH, в рамках одного запуска существует одна сущность. Выбирается файл по установленному порядку поиска; его инициализация однократна, состояние общее. Путь к физической копии не создаёт новый модуль.

### 48. Нативные части разных копий автоматически не объединяются

```text
app/modules/geometry/1.0.0.gbin   — только байткод
shared/geometry/1.0.0.gbin        — тот же основной хеш + Linux x64
```

На Linux выбирается локальный файл целиком, и обычное исполнение идёт на VM. Наличие более подходящей нативной части в следующем каталоге не меняет выбор. В required применяются согласованные требования строгого режима. Объединение выполняет автор через goat-merge, а не загрузчик во время запуска. Первый найденный модуль используется даже тогда, когда последующая копия могла бы быть «лучше».

### 49. Найденный, но нечитаемый файл останавливает поиск

```text
app/modules/geometry/1.0.0.gbin — существует, нет прав на чтение
shared/geometry/1.0.0.gbin      — читается
```

Ошибка загрузки содержит путь и причину; перехода к shared нет. Продолжение поиска разрешено при отсутствии нужного пути, а не при неисправности найденного кандидата.

Причина особенно важна при разработке: неисправная сборка в ближайшем каталоге не должна маскироваться загрузкой исправной, но старой копии. Это относится и к ранее согласованным ошибкам формата, несовместимости и несовпадения основного хеша.

### 50. Невозможность проверить каталог не равна отсутствию файла

```text
app/modules/geometry/ — нельзя проверить содержимое из-за прав доступа
shared/geometry/1.0.0.gbin — исправный модуль
```

Если загрузчик не может достоверно установить отсутствие локального файла, он останавливается с ошибкой доступа. Продолжать поиск можно только при достоверном отсутствии нужного пути. Ошибки проверки каталогов не превращаются в отсутствие зависимости и не переключают программу на другую копию.

## Пути поиска и диагностика: примеры 51–55

### 51. Явный относительный module-dir привязан к рабочему каталогу

```sh
# Текущий каталог: /work
goat build ./project/app.gmod --module-dir ./shared
```

Результат: /work/shared/<имя>/<версия>.gbin. Без --module-dir используется /work/project/modules/<имя>/<версия>.gbin: значение по умолчанию привязано к описанию проекта. Явный аргумент понимается как обычный путь командной строки. Абсолютный --module-dir разрешён и не дополняется рабочим каталогом.

### 52. Относительные пути окружения фиксируются при запуске

```text
Рабочий каталог: /work
GOAT_MODULE_PATH=./shared:./vendor
```

Это каталоги /work/shared и /work/vendor. Относительные элементы разрешаются один раз относительно рабочего каталога при запуске и сохраняются как абсолютные пути. Позднейшая смена рабочего каталога не меняет поиск. Каждый элемент GOAT_MODULE_PATH также может быть абсолютным; такие пути не привязываются к рабочему каталогу. Аналогичная однократная фиксация применяется к явному --module-dir.

### 53. Пустые элементы списка игнорируются

```text
Linux:   /opt/goat/modules::/home/user/modules:
Windows: C:\goat\modules;;D:\modules;
```

В каждом примере получается два каталога. Пустой элемент не обозначает текущий каталог. Чтобы явно добавить его, используется точка (.); она разрешается по правилу примера 52.

### 54. Отсутствие переменной окружения не является ошибкой

```sh
goat app.gbin
```

Если GOAT_MODULE_PATH не задана или содержит только пустые элементы, поиск использует modules рядом с главным файлом и явно заданный --module-dir, если он есть. Программа без внешних зависимостей не требует существования каталогов поиска. Ошибка отсутствующей зависимости возникает только тогда, когда требуемый модуль не найден; ошибки проверки существующих путей обрабатываются по строгим правилам 49–50.

### 55. Диагностика различает отсутствие и неисправность

Пример сообщения при полном отсутствии зависимости:

```text
Не найден модуль geometry@1.2.0.
Требуется модулю app@1.0.0.

Проверены:
  /work/app/modules/geometry/1.2.0.gbin
  /work/shared/geometry/1.2.0.gbin
  /opt/goat/modules/geometry/1.2.0.gbin
```

Показываются имя, точная версия, потребитель и все проверенные пути в порядке поиска. Если поиск остановился на запрете доступа, повреждении или другой ошибке кандидата, сообщение содержит конкретную причину и путь остановки, а не ошибочное «модуль не найден». Последующие каталоги не выдаются за проверенные.

## Состав и независимость зависимостей: примеры 56–60

### 56. Неиспользуемая запись описания даёт предупреждение

Фрагмент .gmod:

```json
{
  "dependencies": {
    "geometry": "1.2.0",
    "unused": "2.0.0"
  }
}
```

Если исходники используют только import "geometry", запись unused вызывает предупреждение, но не ошибку. Unused не требуется ни при сборке, ни при запуске и не записывается в зависимости .gbin. Запись описания задаёт версию для возможного импорта, а не подключает модуль сама по себе. Здесь показан фрагмент описания, не полный .gmod.

### 57. Импорт в недостижимой ветке считается использованием

```goat
if (false) {
    const geometry = import "geometry@1.2.0";
}
```

Geometry остаётся зависимостью готового модуля и проверяется при сборке и перед запуском. Его инициализация в этом примере не выполняется. Состав зависимостей определяется по исходникам; оптимизация и удаление недостижимого кода не меняют его.

### 58. Явная другая версия не использует версию из описания

Фрагмент .gmod:

```json
{
  "dependencies": {
    "geometry": "1.2.0"
  }
}
```

Единственный импорт в исходниках:

```goat
const geometry = import "geometry@2.0.0";
```

Готовый модуль зависит только от geometry@2.0.0. Неиспользованная настройка 1.2.0 даёт предупреждение; файл этой версии не требуется. Явный выбор версии не меняет настройку импортов без версии.

### 59. Внешние зависимости не встраиваются в потребителя

```text
app@1.0.0 → geometry@1.2.0 → math@2.0.0
```

App содержит собственный код и запись о geometry, geometry — собственный код и запись о math. Для запуска требуются три отдельных .gbin; загрузчик проверяет всю цепочку. Содержимое зависимостей не копируется внутрь потребителей.

Это принцип организации программ: большие программы должны быть модульными. Формат не предусматривает «толстые» модули с вложенными внешними библиотеками. Несколько исходников одного модуля и несколько нативных вариантов его собственного кода остаются разрешены.

### 60. Приложение не переопределяет зависимости библиотеки

```text
app@1.0.0 → geometry@1.2.0 → math@2.0.0
app@1.0.0 → math@3.0.0
```

App использует math@3.0.0; geometry продолжает использовать math@2.0.0, записанную при собственной сборке. Загружаются обе версии с раздельными состояниями и правами. Глобального переопределения версий описанием приложения нет.

Каждый модуль фиксирует имена, точные версии и ожидаемые основные хеши собственных зависимостей. Такая независимость нужна для детерминированного разрешения зависимостей при запуске: код библиотеки получает именно ту зависимость, с которой был собран. Это не обещание детерминированности пользовательского кода при произвольных внешних входных данных.

## Снимок запуска и автономные утилиты: примеры 61–65

### 61. Содержимое модулей удерживается в оперативной памяти

При подготовке запуска всё содержимое выбранных .gbin загружается в оперативную память, проверяется и удерживается до завершения процесса. После этого исходные архивы не перечитываются.

```text
1. Программа проверила geometry@1.2.0.
2. Разработчик пересобрал и заменил её .gbin на диске.
3. Программа впервые вызывает нативную функцию geometry.
```

На шаге 3 библиотека извлекается из проверенных данных в памяти. Замена на диске не смешивает старый байткод с новым нативным кодом и становится видна только следующему запуску. Ленивая загрузка DLL/SO средствами ОС сохраняется; она не означает ленивого чтения исходного архива.

### 62. Нехватка памяти завершает процесс

```text
App загружен.
Для geometry@1.2.0 не хватает памяти.
Завершение до исполнения пользовательского кода.
```

Применяется общее правило Goat для исчерпания памяти. Частичная загрузка, переход к другой копии или попытки продолжить запуск не выполняются.

### 63. Inspect не требует внешних зависимостей модуля

```text
Geometry@1.2.0 зависит от math@2.0.0.
На компьютере есть только geometry.gbin.
```

```sh
goat-inspect geometry.gbin
```

Утилита проверяет сам архив, его хеши и подходящую нативную библиотеку по ранее согласованным правилам. Запись о math показывается как метаданные; отсутствие её файла не является ошибкой инспекции. Успешная инспекция отдельного файла не подтверждает доступность всего графа. При запуске программы полная проверка графа по-прежнему обязательна.

### 64. Merge не требует файлов внешних зависимостей

```text
windows.gbin → math@2.0.0, основной хеш зависимости H
linux.gbin   → math@2.0.0, основной хеш зависимости H
```

```sh
goat-merge windows.gbin linux.gbin --output geometry.gbin
```

Если основные хеши самих объединяемых модулей совпадают и архивы исправны, отсутствие math не мешает объединению. Имя, версия и ожидаемый основной хеш зависимости сохраняются. Наличие зависимости проверяется при сборке потребителя или запуске, а не при упаковке нативных вариантов.

### 65. Merge не загружает нативные библиотеки средствами ОС

```sh
# Команда выполняется на Linux.
goat-merge windows.gbin linux.gbin --output geometry.gbin
```

Merge проверяет структуру архивов, метаданные, хеши и правила объединения. DLL/SO не загружаются даже для текущей платформы, код их инициализации не исполняется. Пробная загрузка — задача goat-inspect. Объединение возможно на машине, не поддерживающей ни одну из целевых платформ входных библиотек.

## 66. Машиночитаемая инспекция и сведения об авторе

```sh
goat-inspect geometry.gbin --json
```

В режиме --json стандартный вывод содержит только JSON, включая результаты проверок и найденные ошибки. Код завершения сохраняет согласованный смысл: ненулевой при ошибке. Без флага вывод человекочитаемый. Пример части результата (полная схема ещё не определена):

```json
{
  "name": "geometry",
  "version": "1.2.0",
  "validation": "ok",
  "nativeLoad": "ok"
}
```

В описание сборки .gmod и метаданные готового .gbin добавить необязательные сведения об авторе и контактах, включая имя автора и email. Компилятор переносит указанные сведения в модуль; отсутствие этих полей не препятствует сборке или загрузке. Просмотрщик должен представлять их как информацию о модуле, в том числе в JSON-режиме.

Набор полей, правила хеширования и объединения уточнены в решениях 67–70 ниже. Наличие поля email не предполагает отправки сообщений или сетевой проверки адреса.

## Информационные поля: решения 67–70

### 67. Согласованный набор полей

Фрагмент .gmod, дополняющий обязательные поля:

```json
{
  "description": "Библиотека геометрических вычислений",
  "authors": [
    { "name": "Ivan", "email": "ivan@example.com" }
  ],
  "license": "MIT",
  "homepage": "https://example.com/geometry"
}
```

Все четыре поля необязательны. Authors допускает нескольких авторов; email можно опустить. Сведения переносятся в .gbin и показываются просмотрщиком.

### 68. Информационные поля исключаются из основного хеша

Description, authors, license и homepage не входят в основной хеш. Исправление email или homepage при неизменном коде и зависимостях не требует пересборки потребителей. Метаданные исполнения и прав доступа продолжают входить в основной хеш. Исключение действует только для явно перечисленных информационных полей.

### 69. Конфликт информации запрещает объединение

```text
windows.gbin: authors → Ivan, ivan@old.example
linux.gbin:   authors → Ivan, ivan@new.example
```

Даже при одинаковом основном хеше goat-merge выдаёт ошибку с указанием различающегося поля. Автор должен согласовать метаданные перед объединением; порядок аргументов ничего не выбирает. Поле, присутствующее только в одном входе, также вызывает конфликт. Различия форматирования JSON и порядка ключей объектов не являются различиями значений.

### 70. Необязательность не допускает неверного типа

Допустимо опустить email:

```json
{ "authors": [{ "name": "Ivan" }] }
```

Следующий фрагмент содержит ошибки схемы:

```json
{ "description": 123, "authors": "Ivan", "homepage": null }
```

Присутствующие поля обязаны соответствовать схеме: description, license и homepage — строки, authors — массив объектов, name/email имеют строковые значения. Числа в строки автоматически не превращаются; null не трактуется как отсутствие. Это относится к .gmod и метаданным .gbin.

## Текстовые сведения о модуле: решения 71–75

### 71. Информационные строки поддерживают Unicode

```json
{
  "description": "Геометрические вычисления",
  "authors": [{ "name": "Иван Князьков" }]
}
```

JSON читается и записывается в UTF-8. Ограничения на строчную латиницу относятся к техническим имени модуля и версии, но не к именам авторов и описанию.

### 72. Сетевые проверки не выполняются

```json
{
  "authors": [{ "name": "Иван", "email": "ivan@example.com" }],
  "homepage": "https://example.com/project"
}
```

Сборка и просмотр работают без интернета. Инструменты не отправляют письма, не открывают сайт и не подтверждают достоверность этих сведений автора.

### 73. Содержимое строк сохраняется точно

```json
{
  "authors": [{ "name": "Иван Князьков" }],
  "description": "Первая строка\nВторая строка"
}
```

Не удаляются пробелы и не меняется регистр. Перенос строки сохраняется как часть значения. «Иван» и « Иван » — разные значения, в том числе для объединения модулей. Канонизация JSON меняет представление, а не содержимое строки.

### 74. Запись автора требует непустого имени

```json
{
  "authors": [
    { "name": "Иван" },
    { "name": "Команда проекта", "email": "team@example.com" }
  ]
}
```

Автором может быть человек или организация. Email необязателен; name обязателен и не может быть пустой строкой. Записи {}, {"email":"ivan@example.com"} и {"name":""} ошибочны. Это не вводит автоматическую обрезку пробелов из решения 73.

### 75. Лицензия — информационная строка

```json
{ "license": "MIT" }
```

```json
{ "license": "Proprietary" }
```

```json
{ "license": "Использование по отдельному соглашению" }
```

Все примеры допустимы. Соответствие каталогу лицензий не требуется. Просмотрщик показывает текст автора; компилятор не толкует условия лицензии и не меняет из-за них поведение программы.

## Верхнеуровневый return и exit: решения 76–80

### 76. Return вне функции вызывает исключение

```goat
// settings.goat
public value = 10;
return;
public extra = 20;
```

Верхнеуровневому return некуда возвращать управление: он вызывает исключение, а не успешно завершает файл. Предложение отдельного синтаксического запрета не принято. Исключение, вышедшее из инициализации, делает её неуспешной по согласованным правилам.

Добавляется встроенная exit(code). При штатной работе она немедленно завершает весь интерпретатор и передаёт код завершения ОС. При инициализации подключаемого файла/модуля вызов exit вызывает исключение вместо завершения процесса.

### 77. Контекст инициализации распространяется на вызовы

```goat
// library.goat
public stop = func() { exit(7); };
stop(); // Исключение при инициализации подключённого файла.
```

Правило определяется текущим исполнением, а не тем, находится ли exit синтаксически внутри функции. Вызванная из инициализатора функция не может обойти запрет завершения. Вызов той же функции при штатной работе после успешной инициализации завершает процесс с кодом 7.

### 78. Главный файл при прямом запуске выполняет обычную программу

```goat
// main.goat, прямой запуск исходника или входного файла .gbin
if (__main__) {
    println("Завершение");
    exit(7);
}
```

Верхнеуровневое выполнение главного файла при прямом запуске считается штатной работой для exit, а не инициализацией импортируемого модуля. Поэтому пример завершается с кодом 7. Когда главный файл подключает другой через include/import, выполнение подключаемого инициализатора и вызванных им функций находится в контексте инициализации: exit там выбрасывает исключение. Это уточняет ранние упоминания верхнеуровневой инициализации и не меняет значение __main__.

### 79. Штатный exit не выполняет пользовательскую очистку

```goat
// Главный файл, прямой запуск
try {
    exit(7);
} finally {
    println("Очистка");
}
```

Процесс завершается на месте вызова с кодом 7; «Очистка» не печатается. Catch не перехватывает штатное завершение, пользовательские finally не выполняются. Это не обычное раскручивание стека исключением.

В контексте инициализации тот же exit вызывает обычное исключение; для него catch/finally действуют по стандартным правилам. Внутренняя очистка при штатном exit определена в решениях 82–84 ниже и не выполняет пользовательские finally.

### 80. Аргумент проверяется до завершения

```goat
exit(0);   // Допустимый код.
exit(7);   // Допустимый код.
// Следующие вызовы — независимые примеры ошибок:
exit("7"); // Неверный тип.
exit(7.5); // Неверный тип.
exit();    // Отсутствует аргумент.
```

Exit принимает ровно один аргумент целого типа из определённого диапазона, без неявных преобразований. Проверка числа аргументов, типа и диапазона выполняется при вызове. Неверный аргумент вызывает обычное перехватываемое исключение, а не немедленное завершение процесса. Это не означает, что неперехваченное исключение автоматически игнорируется. Диапазон 0–255 включительно закреплён в решении 81 ниже.

## Коды и завершение exit: решения 81–85

### 81. Единый диапазон 0–255 без встроенных констант

Exit принимает ровно одно целое число от 0 до 255 включительно на всех платформах. Отрицательные значения и числа выше 255 вызывают обычное перехватываемое исключение; код не обрезается и не приводится по модулю 256.

```goat
try {
    exit(256);
} catch (e) {
    println("Программа продолжает работу");
}
```

Встроенные константы для кодов завершения не вводятся. Программист при необходимости объявляет собственные. Диапазон не отменяет запрет exit во время инициализации подключаемого файла.

### 82. Буферы стандартного вывода сбрасываются

```goat
print("Готово");
exit(0);
```

При штатном exit интерпретатор сбрасывает буферы стандартного вывода перед завершением, чтобы уже выполненная печать попала в вывод даже без перевода строки. Это внутренняя очистка; пользовательские finally по-прежнему не выполняются.

### 83. Временные нативные библиотеки очищаются

```goat
// Программа уже использовала нативные функции.
exit(7);
```

Временный каталог с распакованными библиотеками после завершения процесса удаляет заранее запущенный уборщик (решения 148 и 152). Нельзя выгружать библиотеку из-под исполняющего её потока. Ошибка очистки не меняет код завершения 7. Это уточняет внутреннее завершение из решения 79 и не разрешает вызов пользовательских finally.

### 84. Ошибка сброса вывода не заменяет выбранный код

```goat
print("Результат");
exit(7);
```

Если сброс буфера завершился ошибкой, интерпретатор по возможности сообщает её через stderr и сохраняет код 7. Ошибка внутреннего завершения не подменяет явно выбранный программистом статус, как и ошибка удаления временных файлов.

### 85. Штатный exit из библиотеки завершает весь процесс

```goat
// Входной файл library
external stop = func() { exit(7); };

// main.goat, прямой запуск
const lib = import "library@1.0.0";
lib.stop();
println("Продолжение"); // Не выполняется.
```

Library уже успешно инициализирована. Stop завершает весь интерпретатор с кодом 7, а не только работу библиотеки. Решает текущий контекст исполнения: если такую же функцию вызовет активный инициализатор подключаемого файла, exit вместо завершения выбросит исключение.

## Аналитические метаданные функций: решения 86–90

Эти сведения описывают доказанные свойства кода для анализатора потребителя. Неизвестное свойство не считается отсутствующим эффектом. Точная схема метаданных ещё проектируется.

### 86. Изменяемый экспорт не фиксирует первоначальную функцию

```goat
// Входной файл library
external var calculate = func(x) { return x + 1; };

// Программа
const lib = import "library@1.0.0";
println(lib.calculate(3)); // 4.
lib.calculate = func(x) { return x * 2; };
println(lib.calculate(3)); // 6.
```

Описание первоначальной функции не разрешает навсегда связать вызовы с ней. Исполнение использует текущее значение поля; анализ и нативные оптимизации сохраняют возможность замены.

### 87. Константность ссылки не означает чистоту функции

```goat
// Входной файл library
var counter = 0;
external next = func() {
    counter += 1;
    return counter;
};

// Программа
const lib = import "library@1.0.0";
println(lib.next()); // 1.
println(lib.next()); // 2.
```

Метаданные различают неизменность ссылки и свойства функции. Предусмотреть подробное описание чтения и записи захваченного состояния, изменения аргументов, ввода-вывода, возможных исключений и завершения программы. Для каждого свойства различать доказанный результат и неизвестность. External const само по себе не разрешает считать функцию чистой или заранее вычислять её вызовы.

### 88. Эффекты могут зависеть от переданного callback

```goat
// Входной файл library
external apply = func(callback, value) {
    return callback(value);
};

// Программа
const lib = import "library@1.0.0";
lib.apply(func(x) {
    println(x);
    return x;
}, 5);
```

Метаданные указывают вызов аргумента callback и зависимость эффектов apply от него. Потребитель может уточнить свойства для конкретного callback, если способен его проанализировать. Иначе эффекты остаются неизвестными, вызов не считается чистым.

### 89. Результат может быть тем же объектом, что аргумент

```goat
// Входной файл library
external identity = func(value) { return value; };

// Программа
const lib = import "library@1.0.0";
var items = [1, 2];
var result = lib.identity(items);
result.push(3);
println(items); // [1, 2, 3].
```

Предусмотреть сводку «результат — тот же объект, что аргумент 0». Анализатор должен учитывать связь изменений result и items без исходников библиотеки. Недоказанная связь записывается как неизвестная, а не как независимость.

### 90. Новый внешний объект может разделять вложенные значения

```goat
// Входной файл library
external copy = func(value) { return value.clone(); };

// Программа
const lib = import "library@1.0.0";
var items = [[1]];
var result = lib.copy(items);
result.push([2]);  // Внешний массив items не меняется.
result[0].push(3); // Вложенный массив общий.
println(items);   // [[1, 3]].
```

Сводки о новом объекте результата недостаточно для доказательства глубокой независимости. Описывать общие вложенные ссылки, когда они доказаны; если точную связь установить нельзя, сохранять консервативное предположение о возможном совместном состоянии. Clone не становится глубоким копированием из-за пересечения границы модуля.

## Нативные специализации и условия выбора: решения 91–95

### 91. Перечисляются конкретные готовые специализации

```goat
// Библиотека
external add = func(a, b) { return a + b; };

// Потребитель; упакован только вариант для двух целых.
lib.add(2, 3);     // Применима нативная специализация.
lib.add("a", "b"); // Исполняется байткодом в обычном режиме.
```

Метаданные перечисляют специализации и условия их применения. Отсутствие подходящего варианта не делает функцию недоступной: обычный режим использует VM. Во время запуска новые специализации автоматически не компилируются; используются упакованные варианты или байткод.

### 92. Условия могут быть строже типов аргументов

```goat
external divide = func(a, b) { return a / b; };
```

Если конкретный нативный вариант рассчитан только на ненулевой делитель, divide(10, 2) может использовать его, а divide(10, 0) направляется в VM для обычного поведения языка. Условие проверяется до входа в нативную функцию. Аргументы уже вычислены; повторно вычислять их при переходе на VM нельзя. VM получает те же значения. Это правило не утверждает, что у всех реализаций деления должен быть именно такой контракт.

### 93. Неоднозначный выбор — ошибка метаданных

```text
Вариант A: два целых, делитель не равен нулю.
Вариант B: два целых, делитель положительный.
Вызов divide(10, 2) подходит обоим.
```

Порядок записей не разрешает конфликт. Компилятор должен формировать однозначные условия выбора. Загрузчик отклоняет пересечение, если его можно установить при проверке; оставшаяся неоднозначность проверяется перед вызовом и считается ошибкой. Нельзя произвольно выбрать вариант или скрыть некорректные метаданные обычным отсутствием специализации.

### 94. Проверки декларативны и не имеют побочных эффектов

Пример предлагаемого представления (не окончательная схема):

```json
{
  "argumentTypes": ["integer", "integer"],
  "conditions": [
    { "argument": 1, "operation": "notEqual", "value": 0 }
  ]
}
```

Условия — не исполняемый Goat-код. Загрузчик понимает ограниченный явно определённый набор проверок, например типов и сравнений с константами. Они не вызывают пользовательские функции и не имеют побочных эффектов. Проверка применимости не меняет состояние программы.

### 95. Непредставимые условия не допускают небезопасную специализацию

```text
Требование варианта: переданный callback не имеет побочных эффектов.
```

Если требование не доказано при сборке и не может быть проверено поддерживаемыми декларативными средствами перед вызовом, такая специализация не включается в модуль. Условие не записывается произвольным текстом в надежде на интерпретацию загрузчиком. Функция остаётся доступной через байткод; required применяется по ранее согласованным правилам.

## Безопасность нативного вызова и required: решения 96–100

### 96. Неприменимость специализации относится к одному вызову

```goat
// У add есть нативный вариант только для двух целых.
println(lib.add("a", "b")); // VM: ab.
println(lib.add(2, 3));     // Нативно: 5.
```

Первый вызов не отключает функцию или библиотеку до конца запуска. Условия специализации проверяются для каждого вызова. Запоминание ошибки загрузки библиотеки остаётся отдельным механизмом и не распространяется на штатное несовпадение аргументов.

### 97. Общие проверки вызова предшествуют нативному выбору

```goat
// Функция была передана наружу до неудачи инициализации её файла.
savedFunction(2, 3);
```

Если исходный файл функции завершился исключением «Ошибка A», вызов выбрасывает это сохранённое исключение даже при подходящей нативной специализации для двух целых. Сначала проверяется допустимость вызова, включая состояние исходного файла; нативный путь не обходит этот запрет.

### 98. Копирование метода не переносит нативную привязку автоматически

```goat
const original = {
    var counter = 0;
    public next = func() {
        counter += 1;
        return counter;
    };
};
const copy = original.clone();
println(copy.next());     // 1.
println(original.next()); // Тоже 1.
```

Даже если у исходного метода есть нативная реализация, перенаправленные clone/flat захваты не должны обращаться к старым ячейкам. Перенесённый метод исполняется на VM, пока не доказана применимость нативного варианта к новым захватам и правам. Само наличие специализации оригинала таким доказательством не является.

### 99. Обнаруженное нарушение ABI не допускает повторного вызова

```text
Метаданные обещают integer.
Нативная функция вернула недопустимый тег результата.
```

Обнаруженное после вызова нарушение ABI завершает исполнение с диагностикой модуля, функции и нарушенного требования. Повторно вызывать функцию на VM нельзя: нативный вызов уже мог иметь побочные эффекты. Это относится к проверяемым нарушениям контракта, а не обещает перехват произвольных ошибок машинного кода.

### 100. Required допускает VM для вызовов без специализации

```goat
// У add упакован вариант только для двух целых.
println(lib.add(2, 3));     // Нативно.
println(lib.add("a", "b")); // VM, допустимо и в required.
```

Required сохраняет требование наличия нативного исполнения, но не требует нативного исполнения каждого вызова. Штатное отсутствие специализации для аргументов допускает VM. Если подходящий вариант имеется, но его библиотеку не удалось загрузить, required завершается ошибкой по ранее согласованным правилам. Требование при сборке модуля — хотя бы одна собственная нативная реализация — остаётся в силе.

## Требования сборки и содержимое архива: решения 101–105

### 101. Требования отражают фактическую нативную сборку

Если флаги компилятора разрешают AVX2, требования варианта должны учитывать это, даже если номинальная цель указана как обычная x86-64. Метаданные формируются по фактическим настройкам сборки, а не только по названию цели. Если инструменты не позволяют достоверно определить требования совместимости, сборка завершается ошибкой: неполные требования публиковать нельзя.

### 102. Плоская структура нативных файлов

```text
module.json
bytecode.bin
native/
    variant-1.dll
    variant-2.so
```

module.json содержит общие метаданные и описания нативных вариантов с путями к библиотекам. bytecode.bin содержит байткод всех включённых исходных файлов с сохранением отдельных областей видимости. Нативных библиотек может не быть. Каждый вариант представлен одной библиотекой непосредственно в native/, без отдельного каталога варианта, исходников, заголовков, объектных файлов или дополнительных DLL/SO рядом с ним. Имена служебные: совместимость определяется метаданными, а не именем или расширением файла.

### 103. Неописанные файлы запрещены

Если метаданные описывают native/variant-1.dll, но архив также содержит неописанный native/old-library.dll, проверка отклоняет весь модуль. Каждый файл должен быть предусмотрен форматом или метаданными. Записи каталогов допускаются. Будущие ресурсы и отладочные данные потребуют явной поддержки форматом, а не молчаливого игнорирования неизвестного содержимого.

### 104. Символические ссылки запрещены

```text
native/variant-1.so -> /usr/local/lib/something.so
```

Такая запись недопустима: ZIP содержит только обычные файлы и записи каталогов. Символическая ссылка делает весь модуль некорректным ещё при проверке, даже если её вариант не нужен текущей платформе. Библиотека должна находиться внутри архива. Обычные системные зависимости самой DLL/SO по-прежнему разрешаются загрузчиком ОС по согласованным правилам.

### 105. Единые правила путей внутри ZIP

```text
native/variant-1.dll       — допустимо
native\variant-1.dll       — ошибка
native/../variant-1.dll    — ошибка
```

Разделитель — только /. Регистр значим: путь из метаданных должен точно совпадать с именем записи архива. При этом имена, различающиеся только регистром, запрещены: native/variant-1.dll и native/Variant-1.dll не могут сосуществовать. Это предотвращает коллизии при извлечении на Windows. Абсолютные пути и компоненты .. также запрещены; правила одинаковы для всех платформ.

## Упаковка и проверка ZIP: решения 106–110

### 106. Только хранение без сжатия и Deflate

Поддерживаются два способа хранения записей: без сжатия и Deflate. Шифрование и пароли запрещены. Например, bytecode.bin можно сжать Deflate, а DLL/SO оставить несжатыми. Хэши вычисляются по распакованным данным: изменение уровня сжатия не меняет идентичность модуля. Неизвестный метод сжатия или зашифрованная запись делает весь модуль некорректным, даже если запись относится к другой платформе.

### 107. ZIP64 пока не поддерживается

Первая версия использует обычный ZIP. При превышении его ограничений сборка завершается понятной ошибкой, а не автоматически переключается на ZIP64. Например, bytecode.bin размером 5 ГиБ требует разбить программу на модули. Загрузчик явно отклоняет ZIP64. Это соответствует решению не создавать огромные модули.

### 108. Детерминированная упаковка

Порядок записей фиксирован, временные метки постоянны, права доступа стандартны. Время сборки и исходные файловые атрибуты не переносятся в ZIP. Одинаковые module.json, байткод и нативные библиотеки при одинаковых настройках и версии упаковщика должны давать побайтово одинаковый .gbin, независимо от дня сборки и упаковки на Windows или Linux. Это требование к упаковке одинакового содержимого, а не обещание одинакового машинного кода от разных C-компиляторов. Хэши содержимого не зависят от упаковки.

### 109. Проверка размеров до и во время распаковки

Заявленные размеры записей проверяются до распаковки, фактические — во время неё. Если ZIP обещает bytecode.bin размером 1 МиБ, но распаковщик выдаёт больше, обработка немедленно прекращается и модуль отклоняется, без бесконтрольного выделения памяти. Несоответствие фактического размера заявленному является ошибкой. При суммировании размеров проверяется переполнение. Если корректно заявленный объём не помещается в память, действует обычное правило нехватки памяти: завершение без попытки выбрать другой модуль.

### 110. CRC32 проверяется дополнительно к SHA-256

Проверяется CRC32 каждой файловой ZIP-записи; несовпадение делает весь модуль некорректным. Например, если native/variant-2.so соответствует SHA-256 из метаданных, но имеет неверный CRC32, архив всё равно отклоняется, даже при запуске на Windows, где этот вариант не нужен. CRC32 проверяет целостность ZIP, SHA-256 — соответствие содержимого метаданным. Ни одна из этих проверок сама по себе не подтверждает доверенность автора.

## Точность JSON и канонизация: решения 111–115

### 111. Целочисленные поля читаются точно

```json
{ "formatVersion": 1 }
```

Целочисленные поля метаданных записываются целыми JSON-числами без дробной части и экспоненты. Значения 1.0, 1e0 и строка "1" в поле formatVersion недопустимы. Диапазон проверяется без промежуточного преобразования в double. Большие целые читаются точно либо отклоняются при выходе за допустимый для поля диапазон, но никогда не округляются.

### 112. Строгий UTF-8 без BOM

```json
{ "description": "Геометрия 📐" }
```

JSON читается только в UTF-8 без BOM. Некорректные Unicode-последовательности отклоняются, а не заменяются символом замены. Тот же символ 📐 можно записать корректной парой \uD83D\uDCD0: после декодирования и канонизации результат одинаков. Одиночный \uD83D недопустим. Правило действует для .gmod, module.json и JSON-описания внутри нативной библиотеки.

### 113. Unicode не нормализуется автоматически

Символ é и последовательность e с отдельным комбинируемым знаком ударения могут выглядеть одинаково, но остаются разными строками. Обе записи допустимы в описании модуля; различие между ними вызывает конфликт метаданных при объединении. Текст автора сохраняется без скрытой нормализации. Напротив, "a" и "\u0061" — одна строка: JSON-экранирование снимается до сравнения и канонизации.

### 114. Дубликаты ключей проверяются после декодирования

```json
{
  "name": "geometry",
  "\u006eame": "another"
}
```

Этот пример синтаксически читаем как JSON, но недопустим по контракту: оба ключа означают name. Повторяющиеся ключи запрещены на любом уровне вложенности, даже при одинаковых значениях. Нельзя молча выбирать первое или последнее значение. Проверка выполняется после декодирования экранирования для .gmod, module.json и описания внутри нативной библиотеки.

### 115. Порядок ключей при канонизации

```json
{ "version": "1.0.0", "name": "geometry" }
```

```json
{ "name": "geometry", "version": "1.0.0" }
```

Эти объекты имеют одинаковое каноническое представление и одинаковый хэш. Ключи объектов сортируются лексикографически по байтам их декодированного UTF-8, независимо от языка и настроек ОС. Порядок элементов массивов сохраняется: ["a", "b"] и ["b", "a"] остаются разными.

## Канонические байты и проверка байткода: решения 116–120

### 116. Единственное каноническое написание строк

В каноническом JSON обычные символы записываются непосредственно в UTF-8. Кавычка и обратная косая черта экранируются как \" и \\, управляющие символы U+0000–U+001F — как \u00xx со строчными шестнадцатеричными цифрами. Символ / не экранируется. Например, "a" и "\u0061" превращаются в одно каноническое "a", а перевод строки — в \u000a независимо от исходного экранирования.

Обычный JSON-парсер и обработку экранирования предоставляет сторонняя библиотека. Её сериализатор используется для канонизации только при точном соответствии контракту; иначе нужен небольшой канонический сериализатор поверх модели данных, а не собственный JSON-парсер. Сам выбор \u000a вместо \n не имеет особого преимущества: важны однозначность и стабильность, в том числе после обновления библиотеки. Исходный .gmod может использовать обычные JSON-экранирования и удобное форматирование.

### 117. Оформление JSON отделено от канонизации

module.json внутри .gbin может содержать отступы. Загрузчик разбирает JSON, выбирает поля, участвующие в основном хэше, и канонизирует их. Пробелы, переносы строк и исходный порядок ключей не влияют на этот хэш. Компилятор сам использует стабильное оформление для побайтовой воспроизводимости упаковки, но загрузчик не требует того же оформления от других инструментов.

### 118. Части основного хэша имеют однозначные границы

```text
фиксированная метка формата хэширования
длина канонических метаданных
канонические метаданные
длина байткода
байткод
```

SHA-256 вычисляется по этой последовательности. Длины задаются в байтах как беззнаковые 64-битные числа в little-endian независимо от платформы. Метка отделяет этот формат хэширования от других применений SHA-256; её точные байты должны быть закреплены в спецификации формата. Состав значимых метаданных не меняется: сам хэш, нативные варианты и информационные поля исключены.

### 119. Нативный хэш покрывает весь файл библиотеки

SHA-256 нативной библиотеки вычисляется непосредственно по всем байтам DLL/SO, без исключения служебных секций и без преобразований. Изменение только временной метки внутри DLL уже меняет её хэш. Основной хэш модуля остаётся прежним, если байткод и общие значимые метаданные не изменились. Для этой проверки библиотека — непрозрачный файл; воспроизводимость её содержимого обеспечивается настройками нативной сборки, а не исключениями при хэшировании.

### 120. Совпадение хэша не заменяет проверку байткода

Перед исполнением любого пользовательского кода проверяются структура байткода и его ссылки. Например, совпадающий SHA-256 не делает допустимым переход за пределы функции или несуществующий индекс константы: такой модуль отклоняется даже при недостижимости повреждённой функции. Проверка охватывает формат, допустимые инструкции и их операнды; она не обещает заранее обнаружить все ошибки программы.

## Переносимость и общая проверка: решения 121–125

### 121. Архитектурно независимый байткод

Байткод внутри .gbin использует фиксированные размеры числовых полей и little-endian, без сохранённых C-структур, указателей и платформенного size_t. Например, один geometry.gbin без нативных библиотек должен исполняться на Windows x64 и Linux ARM64 без пересборки при поддержке соответствующей версии байткода интерпретатором. Загрузчик преобразует файловое представление во внутреннее. Это требование к формату, а не утверждение о необходимости его переписать: при реализации нужно проверить существующий формат и переиспользовать уже обеспеченные свойства переносимости.

### 122. Метаданные сверяются с байткодом

Независимой корректности метаданных и байткода недостаточно. Если нативная специализация ссылается на отсутствующую функцию №42 или идентификатор входного файла отсутствует в байткоде, модуль отклоняется до запуска, даже при правильных хэшах. Проверяются межкомпонентные ссылки.

### 123. Загрузка нативной библиотеки требует применимого вызова

Если библиотека содержит только add(integer, integer), а программа вызывает add(string, string), вызов выполняется на VM без извлечения DLL/SO и обращения к загрузчику ОС. Одной совместимости библиотеки с платформой недостаточно для её загрузки. Целостность файла всё равно проверяется при начальной проверке модуля. goat-inspect по-прежнему отдельно проверяет загрузку совместимого варианта. Это уточнение ленивой загрузки, а не отмена предварительной проверки.

### 124. Нативные описания согласованы даже при native off

Список специализаций и описания библиотек проверяются на согласованность до загрузки DLL/SO. Например, ссылка специализации на variant-3 при наличии только variant-1 и variant-2 делает весь модуль некорректным, в том числе при --native off. Отключение нативного исполнения не скрывает повреждённые метаданные.

### 125. Общий код проверки и сборка через CMake

Загрузчик, goat-inspect и goat-merge используют общий C-код проверки архива. Компилятор проверяет им готовый временный .gbin перед публикацией: неверная ссылка на функцию завершает сборку ошибкой и оставляет старый выходной файл нетронутым. Дополнительные действия различаются: загрузчик проверяет граф зависимостей, goat-inspect пробует загрузить совместимую нативную библиотеку в дочернем процессе, goat-merge этого не делает.

CMake собирает общую библиотеку проверки и линкует её с интерпретатором и утилитами. Установленные программы выполняют проверку самостоятельно, без CMake. Существующий механизм запуска тестов сохраняется; CTest не добавляется.

## Дальнейшее уточнение

Правила выше согласованы; обсуждение продолжается по одному вопросу с примерами. Полная схема форматов, детали канонического кодирования, служебные символы и поддерживаемые системные ABI уточняются при проектировании реализации. Они не отменяют согласованную семантику.

## Проверка графа зависимостей: решения 126–131

126. При сборке проверяется весь транзитивный граф зависимостей: наличие, целостность, версии, ожидаемые хэши, конфликты и циклы import. Ошибка не позволяет опубликовать результат сборки.
127. При конфликте основных хэшей одной пары «имя + версия» диагностика содержит обе полные цепочки зависимостей и ожидаемые SHA-256.
128. Искусственного ограничения глубины зависимостей нет. Обход итеративный, с явным стеком задач, без риска переполнения стека вызовов.
129. Предварительная проверка собирает все независимо обнаруживаемые ошибки за один проход. Если метаданные узла невозможно разобрать, его зависимости дальше не обходятся.
130. Диагностика выводится в детерминированном порядке: по полной цепочке зависимостей, затем по типу ошибки и месту в модуле.
131. Каждый отдельный модуль проверяется один раз за проход компилятора или загрузчика, результат проверки кешируется. При ошибке показываются все ведущие к модулю цепочки зависимостей; кеш не должен скрывать различные пути.

Зависимости выявляются по всем синтаксическим import, включая ветки, которые не выполняются. Инициализация остаётся ленивой, при фактическом выполнении import. Неиспользуемые записи зависимостей по-прежнему вызывают предупреждение согласно решению 56.

## Время жизни модулей и параллельная инициализация: решения 132–135

132. Выгрузка модулей и освобождение занимаемой ими памяти откладываются на будущие итерации. Загруженные модули остаются в памяти до завершения программы.
133. Инициализация блокирующая, выполняется одним потоком и никогда не повторяется. Остальные потоки ожидают завершения и получают тот же объект области видимости либо сохранённую ошибку.
134. Инициализация подключаемых исходных файлов и модулей сериализуется глобальной рекурсивной блокировкой. Прямое выполнение главного файла исключено из этой блокировки по решению 143. Повторный вход инициализирующего потока поддерживает ранее согласованные циклические include. Независимые инициализации не выполняются параллельно.
135. Обычные вызовы функций полностью инициализированных модулей не захватывают глобальную блокировку и не ждут её. Обращения, требующие инициализации либо затрагивающие инициализируемый файл, подчиняются ранее согласованным правилам инициализации и ожидания.

## Ограничения при инициализации: решения 136–140

136. Попытка создать поток во время инициализации исходного файла или модуля вызывает перехватываемое исключение времени выполнения.
137. Запрет создания потоков действует только в потоке, непосредственно выполняющем инициализацию, и не распространяется на другие потоки, выполняющие обычный код.
138. join и другие блокирующие операции ожидания потоков во время инициализации вызывают исключение времени выполнения, в том числе ожидание ранее созданных потоков.
139. Блокирующий файловый и сетевой ввод-вывод при инициализации разрешён. Глобальная блокировка остаётся захваченной, инициализация других модулей ожидает.
140. После реализации пользовательских мьютексов блокирующий захват при инициализации должен вызывать исключение времени выполнения. Неблокирующий tryLock разрешён. Мьютексов пока нет: это требование к будущей реализации.

## Завершение инициализации: решения 141–142

141. Специального таймаута инициализации нет. Она может выполняться неограниченно долго, в том числе при блокирующем вводе-выводе; внешнее завершение процесса не входит в контракт инициализации.
142. После неудачной инициализации повторный include/import выбрасывает тот же самый объект исключения с исходной трассировкой. Клонирование исключения и повторный запуск инициализации запрещены.

## Прямой запуск и граница контекста инициализации: решение 143

143. Верхнеуровневый код главного файла при прямом запуске .goat или .gbin выполняется как обычная программа: без глобальной блокировки инициализации и без запретов создания потоков и join из решений 136–138. Это распространяется и на функции, вызываемые этим кодом при отсутствии активного инициализатора подключаемого файла.

При фактической инициализации файла через include или модуля через import текущий поток захватывает глобальную рекурсивную блокировку и входит в контекст инициализации. Контекст охватывает весь динамический вызов инициализатора, включая вызванные им функции независимо от файла их объявления. На это время действуют запреты exit, создания потоков и блокирующего ожидания потоков; для будущих пользовательских мьютексов действует решение 140. Блокирующий файловый и сетевой ввод-вывод разрешён.

После завершения инициализатора или выхода из него с исключением восстанавливается предыдущий контекст. Вложенный инициализатор не снимает ограничения внешнего; после выхода из самого внешнего инициализатора главный код снова выполняется как обычная программа. Повторное include/import уже готового файла не создаёт новый контекст инициализации.

Эта граница уточняет решения 78 и 133–140. Она не отменяет однократность исполнения файлов, состояния их областей, правил циклического include и проверки готовности объявлений.

## Доступ к выполняемому главному файлу: решение 144

144. Для прямо выполняемого главного файла готовность проверяется по отдельным объявлениям, а не ожиданием завершения всего верхнеуровневого кода. Уже объявленные функции и инициализированные переменные доступны другим потокам с обычной проверкой прав. Вызов такой функции не ждёт завершения главного файла. Чтение или запись ещё не готового объявления вызывает перехватываемое исключение, а не блокирующее ожидание.

Например, главный файл объявляет функцию, передаёт её новому потоку и выполняет join. Новый поток может вызвать эту функцию до завершения верхнеуровневого кода главного файла; взаимная блокировка на ожидании его готовности недопустима. Если функция обращается к ещё не инициализированному объявлению главного файла, исключение возникает в месте такого обращения.

Это исключение из ожидания в решениях 133 и 135 относится только к прямо выполняемому главному файлу. При обычной инициализации подключаемых файлов другие потоки по-прежнему ожидают её завершения. Готовность объявления и его значение публикуются с необходимой межпоточной синхронизацией; это правило не делает последующие пользовательские изменения переменных автоматически атомарными.

## Required при запуске: решение 145

145. При запуске готового .gbin с --native required главный модуль обязан содержать хотя бы одну нативную специализацию в варианте, совместимом с текущей платформой. Нативный код зависимостей это требование не удовлетворяет. Отсутствие такого варианта или специализации — ошибка предварительной проверки до выполнения пользовательского кода.

Зависимости могут содержать только байткод или не иметь совместимого нативного варианта; само по себе это не запрещает запуск в required. При вызове без применимой специализации используется VM. Если для конкретного вызова выбрана применимая специализация совместимого варианта, но её библиотека не загружается или не проходит проверку экспортируемых символов/описания ABI, required завершается ошибкой. Последнее правило действует и для главного модуля, и для зависимостей.

Предварительная проверка наличия специализации опирается на проверенные метаданные, не извлекает и не загружает библиотеку средствами ОС. Извлечение и загрузка остаются ленивыми, при первом применимом вызове. Не требуется, чтобы программа фактически выполнила нативный вызов: наличие специализации проверяется до запуска, применимость — для конкретного вызова.

Правило сборки required не меняется: собираемый модуль должен получить хотя бы одну собственную нативную реализацию для выбранной цели сборки. Совместимость с платформой запуска проверяется отдельно.

## Относительные include и символические ссылки: решение 146

146. Относительный путь include разрешается от каталога канонического пути исходного файла, содержащего выражение, после разрешения символических ссылок. Каталог ссылки, через которую найден исходник, не используется как база вложенных include. Это правило применяется к каждому исходнику, включая входной файл.

Например, project/math.goat ссылается на /shared/math.goat. Выражение include "./helpers.goat" внутри этого файла подключает /shared/helpers.goat, а не project/helpers.goat. Затем путь подключаемого файла также канонизируется для определения его идентичности внутри модуля. Подключение одного файла напрямую и через ссылку даёт один набор зависимостей, одну область и одну инициализацию.

Правило действует при сборке .gmod и прямом запуске .goat. В готовом .gbin связи между исходными файлами уже зафиксированы при сборке; исходные пути и ссылки заново на машине пользователя не разрешаются. Канонические абсолютные пути нужны сборщику, но не сохраняются в модуле вместо логических имён.

## Равноправие потоков и время жизни VM: решение 147

147. У VM нет выделенного «главного потока»: все потоки исполнения программы равнозначны. Входной файл определяет точку запуска, но не даёт выполняющему его потоку особых прав и не делает его завершение условием остановки всей VM.

При обычном исполнении VM продолжает работать, пока остаётся хотя бы один незавершённый поток программы. Завершение верхнеуровневого кода входного файла завершает соответствующее выполнение, но не останавливает остальные потоки. Работающие потоки могут продолжать использовать уже готовые объявления входного файла, модули и нативные библиотеки. Их общее состояние не освобождается из-за завершения потока, начавшего программу.

Обычное завершение VM начинается после завершения всех потоков программы; временный каталог затем удаляет отдельный уборщик после завершения процесса по решению 152. Это не неявный join, выполняемый особым главным потоком, а условие завершения VM в целом.

Явный допустимый exit(code) из любого потока по-прежнему завершает весь процесс без ожидания естественного завершения остальных потоков и без пользовательских finally. Ограничения exit в динамическом контексте инициализации сохраняются. Решение 147 не меняет правила фатальных ошибок VM.

## Удаление нативных временных файлов после exit: решение 148

148. Для очистки временного каталога после явного exit используется отдельный процесс уборки. Он ожидает фактического завершения процесса Goat и затем удаляет его временный каталог, включая распакованные DLL/SO. Уборка не требует ожидания естественного завершения рабочих потоков внутри Goat.

Нельзя вручную выгружать библиотеку, пока другой поток может выполнять её код. При таком завершении освобождение нативных библиотек оставляется ОС; удаление файлов выполняется после завершения процесса. При обычном завершении всех потоков временные файлы также удаляет отдельный уборщик после завершения процесса (решение 152).

Это уточняет решение 83: явный exit не обязан успеть удалить загруженные DLL/SO до завершения процесса Goat. Ошибка удаления не меняет уже выбранный код завершения. Момент запуска и подтверждение готовности определены решением 152; поведение при невозможности запуска ещё уточняется; решение не обещает успешную очистку при любых внешних сбоях.

## Exit при исполнении нативного кода: решение 149

149. Семантика exit одинакова для VM и нативных реализаций. Сгенерированный нативный код обращается к общему механизму Goat через нативный ABI, а не самостоятельно вызывает C exit или завершение ОС в обход проверок языка.

Общий механизм проверяет число аргументов, целый тип и диапазон 0–255, а также динамический контекст инициализации. Неверный аргумент или запрещённый вызов во время инициализации вызывает обычное перехватываемое исключение, в том числе из нативного кода. При таком исключении действуют обычные правила catch/finally.

Допустимый exit завершает весь процесс без ожидания возврата из активных нативных функций, включая бесконечный цикл или блокирующий вызов в другом потоке. Не требуется кооперативная проверка флага завершения всеми нативными функциями. Пользовательские finally не выполняются; уже начатая нативная операция может быть прервана, её побочные эффекты не откатываются и не повторяются на VM.

Библиотеки не выгружаются вручную из-под исполняющего их кода. После фактического завершения процесса временные файлы удаляет отдельный процесс уборки по решению 148. Это правило не отменяет согласованную обработку стандартного вывода; бюджет его сброса определён решением 151.

## Одновременные вызовы exit: решение 150

150. Среди допустимых вызовов exit первый вызов, атомарно переведший процесс в состояние завершения, фиксирует код выхода. Остальные вызовы не меняют этот код и не запускают процедуру завершения повторно. У потоков нет приоритета; при гонке exit(0) и exit(7) допустим любой из этих кодов в зависимости от победителя атомарного перехода.

Проверка числа аргументов, типа, диапазона и динамического контекста инициализации предшествует участию в этом переходе. Неверный вызов или запрещённый exit из инициализатора вызывает обычное исключение и не резервирует код завершения. Это не гарантирует доставку такого исключения, если другой поток уже завершает весь процесс.

Состояние завершения и выбранный код публикуются согласованно. Проигравшие вызовы не возвращают управление пользовательскому коду; завершение процесса остаётся общим. Повторный вызов не дублирует действия завершения или передачу задания уборщику.

## Ограничение сброса вывода при exit: решение 151

151. При допустимом явном exit на сброс stdout и stderr выделяется общий бюджет в одну секунду. Это один срок для обоих потоков вывода, а не по секунде на каждый. В бюджет входит ожидание внутренних блокировок вывода и завершения операций записи. Срок отсчитывается по монотонному времени с начала процедуры сброса и не продлевается повторными вызовами exit.

Если сброс завершился раньше, ждать остаток секунды не нужно. При исчерпании бюджета процесс завершается с уже выбранным кодом, даже если сброс не завершён; часть буферизованного вывода может потеряться. Предупреждение выводится только если это возможно без дополнительного ожидания. Ошибка или таймаут вывода не заменяет код exit.

Ограничение должно действовать и при блокировке потока, выполняющего сброс: проверка времени только после возврата из блокирующей записи недостаточна. Эта политика уточняет решения 82, 84 и 149 и относится к явному exit; отдельный таймаут инициализации не вводится.

## Запуск уборщика и единая очистка: решение 152

152. Один процесс уборки для временного каталога запуска Goat запускается перед первым извлечением нативной библиотеки. Goat получает подтверждение готовности уборщика до создания распакованных файлов. До подтверждения извлечение и загрузка не выполняются. Если извлечение не требуется, уборщик не запускается.

Уборщик ждёт фактического завершения процесса Goat и удаляет его временный каталог независимо от пути завершения: явный exit и обычное окончание всех потоков используют один механизм. Ему не нужен отдельный запрос из exit для начала уборки. После удаления либо завершения обработки ошибки уборщик сам завершается.

Одновременные первые нативные вызовы не создают несколько уборщиков для одного запуска и не обходят ожидание готовности. Уборщик не должен удерживать процесс Goat от завершения. Ошибка удаления не меняет код завершения Goat.

Это уточняет решения 83, 147 и 148: прежнее разделение на внутреннее удаление файлов при обычном завершении и внешнее при exit отменено. Отказ запуска, таймаут готовности и отказ уборщика во время работы требуют дальнейшего уточнения.

## Отказ запуска уборщика: решение 153

153. Если процесс уборки не удалось запустить либо он не подтвердил готовность, извлечение и загрузка нативных библиотек не выполняются.

В режиме auto выводится одно предупреждение с причиной, нативное исполнение отключается для всего оставшегося запуска, и вызовы выполняются на VM. Повторные вызовы не повторяют попытку запуска уборщика и предупреждение. Ограничение относится ко всем модулям запуска, а не только к первому вызвавшему извлечение.

В режиме required этот отказ завершает программу с ошибкой. Это ошибка подготовки нативного исполнения, а не исключение пользовательского кода. Уже выполненные до первого применимого вызова побочные эффекты не откатываются.

Готовность уборщика проверяется до первого извлечения, поэтому при таком отказе распакованных DLL/SO ещё нет. Правило не заменяет отдельную политику отказа уже работавшего уборщика. Предельный срок ожидания готовности определён решением 154.

## Срок готовности уборщика: решение 154

154. На запуск уборщика и получение подтверждения его готовности отводится общий предельный срок в одну секунду. Срок отсчитывается по монотонному времени с начала попытки запуска; время создания процесса входит в него. Это не обязательная задержка: после получения подтверждения Goat продолжает работу сразу.

Если процесс не запущен или готовность не подтверждена за этот срок, подготовка считается неудачной и применяется решение 153: auto один раз предупреждает и использует VM до конца запуска, required завершается с ошибкой. До подтверждения распакованные DLL/SO не создаются.

Опоздавшее подтверждение не отменяет зафиксированный отказ и не включает нативное исполнение обратно. Конкурирующие вызовы используют одну попытку и один срок, не перезапуская отсчёт. Срок готовности уборщика независим от отдельного секундного бюджета сброса вывода при exit.

## Ошибка извлечения нативной библиотеки: решение 155

155. Если исправную нативную библиотеку не удалось извлечь из проверенного снимка во временный каталог из-за ошибки файловой операции, например нехватки места или запрета записи, частично записанный файл не загружается.

В auto ошибка сообщается один раз, а эта библиотека помечается недоступной до конца запуска. Текущий вызов и последующие вызовы её специализаций выполняются на VM; повторные попытки извлечения и повторные сообщения не выполняются. Другие библиотеки не отключаются автоматически. В required ошибка извлечения завершает программу с ошибкой.

Повреждение содержимого или несовпадение хеша не относится к этому переходу на VM: это безусловная ошибка целостности в обоих режимах. Ошибка извлечения не меняет выбранную физическую копию модуля и не запускает поиск в следующих каталогах.

Частичные файлы остаются под ответственностью уборщика временного каталога и не считаются успешно опубликованными библиотеками. Конкурирующие первые вызовы должны наблюдать единый результат попытки извлечения этой библиотеки.

## Идентичность исходников и жёсткие ссылки: решение 156

156. Внутри модуля идентичность исходного файла определяется каноническим путём после разрешения символических ссылок, а не физическим идентификатором файла. Пути, приводящие к одному каноническому пути, обозначают одну область, одну копию байткода и одну инициализацию.

Разные канонические пути жёстких ссылок считаются разными исходными файлами, даже если у них одинаковый физический идентификатор и содержимое. Не объединять их по inode, файловому ID или хешу содержимого. У каждого такого пути своя область, состояние и база относительных include.

Например, a/math.goat и b/math.goat — жёсткие ссылки на один файл с include "./helper.goat". Первый исходник подключает a/helper.goat, второй — b/helper.goat. Оба исходника могут входить в один модуль как разные единицы. Принадлежность разным модулям по-прежнему создаёт отдельные сущности независимо от совпадения канонического пути.

## Символическая ссылка на описание сборки: решение 157

157. Перед разрешением путей сборки путь самого .gmod канонизируется с разрешением символических ссылок. Относительный main, локальный каталог поиска modules и каталог вывода modules по умолчанию привязаны к каталогу настоящего .gmod, а не к каталогу ссылки. Способ обращения к одному описанию не меняет состав проекта и место сборки.

Пример настоящего проекта:

```text
/work/project/app.gmod
/work/project/src/main.goat
/work/project/modules/
```

Содержимое app.gmod:

```json
{
  "formatVersion": 1,
  "name": "app",
  "version": "1.0.0",
  "main": "src/main.goat"
}
```

Путь /home/ivan/app.gmod — символическая ссылка на /work/project/app.gmod. При команде:

```sh
goat build /home/ivan/app.gmod
```

используются следующие пути:

| Назначение | Путь |
| --- | --- |
| Входной исходник | /work/project/src/main.goat |
| Локальный каталог зависимостей | /work/project/modules/ |
| Результат сборки по умолчанию | /work/project/modules/app/1.0.0.gbin |

Каталоги /home/ivan/src/ и /home/ivan/modules/ не становятся базой сборки из-за расположения ссылки. Даже если в них лежат другие файлы, сборщик не подменяет ими файлы настоящего проекта.

Явный относительный --module-dir сохраняет отдельное правило: он разрешается относительно рабочего каталога запуска. Например, при рабочем каталоге /tmp:

```sh
goat build /home/ivan/app.gmod --module-dir ./output
```

результат записывается в /tmp/output/app/1.0.0.gbin. Входной исходник остаётся /work/project/src/main.goat. Порядок поиска зависимостей: /work/project/modules/, затем /tmp/output/, затем каталоги GOAT_MODULE_PATH. Явный --module-dir не отменяет приоритет локального modules настоящего проекта.

Это уточняет правила main и каталогов сборки, не меняя разрешение относительных --module-dir и GOAT_MODULE_PATH от рабочего каталога запуска.

## Запуск программы через символическую ссылку: решение 158

158. При прямом запуске .gbin или .goat путь запускаемого файла канонизируется с разрешением символических ссылок. Значение __dir__ и локальный каталог поиска modules определяются по каталогу настоящего запускаемого файла, а не ссылки.

Например:

```text
/home/ivan/app.gbin -> /opt/myapp/app.gbin
/opt/myapp/modules/
/opt/myapp/config.json
```

При команде:

```sh
goat /home/ivan/app.gbin
```

__dir__ равен /opt/myapp, а первым каталогом поиска зависимостей является /opt/myapp/modules/. Файл config.json можно находить относительно __dir__. Каталог /home/ivan/modules/ не получает приоритет из-за расположения ссылки.

То же правило действует для прямого запуска исходника: если /home/ivan/main.goat ссылается на /opt/myapp/main.goat, __dir__ равен /opt/myapp и локальные модули ищутся в /opt/myapp/modules/. Относительные include разрешаются по настоящему пути каждого содержащего исходника согласно решению 146.

Канонический путь запуска фиксируется при подготовке запуска. Последующая смена рабочего каталога или перенаправление исходной символической ссылки не меняют __dir__ и базу локального поиска. Значение __dir__ остаётся общим для всего запуска, включая импортированные библиотеки. Явный относительный --module-dir и относительные элементы GOAT_MODULE_PATH по-прежнему привязаны к рабочему каталогу при запуске.
