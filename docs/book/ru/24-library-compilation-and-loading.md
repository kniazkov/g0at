## 24.1. Сборка, публикация и исполнение — разные этапы

Goat генерирует C, запускает внешний компилятор, исследует полученную библиотеку ELF/PE и при необходимости загружает её для исполнения. Linux использует `.so`, Windows — `.dll`. Успешный exit компилятора сам по себе не доказывает наличие нужных экспортов и требований.

`--save-library` для отдельного исходника сохраняет соседнюю библиотеку без исполнения Goat-кода. `build app.gmod` упаковывает байткод и необязательный нативный вариант в один ZIP-модуль, не загружая библиотеку и не исполняя инициализаторы. Запуск модуля сначала проверяет и удерживает весь граф зависимостей; загрузка ОС ленивая. См. [API сборки](../../module-build-api.md) и [API загрузки](../../module-loading-api.md).

<a id="section-24-2"></a>

## 24.2. Поиск компилятора и профили целей

`--cc` выбирает один исполняемый файл, а не команду оболочки с флагами. Отдельный `.goat` и `--save-library` также сохраняют `CC`, который перекрывается `--cc`. Поиск для модулей идёт по PATH: Linux `cc`, `gcc`, `clang`; Windows `gcc`, `clang`, `cc`; затем поддерживаемые кандидаты кросс-компиляции. Диск не сканируется, унаследованное окружение не изменяется.

`--list-native-targets` перечисляет успешные пробы компиляции/линковки отдельно от отказов. Поддерживаемые имена backend: `linux-x86_64-gnu`, `linux-aarch64-gnu`, `windows-x86_64-mingw64`, `windows-x86_64-ucrt64`, `windows-x86-mingw32`. Известное имя не обещает установленного toolchain. `host` описывает реально выполняющийся процесс. `+avx2` и AArch64 `+sha2` повышают требования; `+sha2` означает SHA1/SHA2, а не AES/PMULL.

Проба исследует полученный бинарный файл, но не загружает его. `--native-probe-timeout` по умолчанию равен 10 секундам и ограничивает пробы, а не компиляцию пользовательского C. Кеш существует только в текущем контексте сборки. Недоступная явная цель не заменяется молча на host, а ошибка компиляции пользовательского C после выбора не вызывает перебор других компиляторов.

<a id="section-24-3"></a>

## 24.3. Файлы, процессы и публикация

Процессы используют переносимый API дочерних процессов с явными массивами аргументов без интерпретации оболочкой. Пути процессов/файлов Windows используют Unicode-aware API. Управляемые рабочие каталоги и относительные ASCII-имена временных исходников обходят искажение путей ассемблером MinGW без изменения окружения процесса.

Общий процесс уборки обязан подтвердить READY до создания временных файлов нативной сборки или извлечения. Он владеет временным деревом запуска и учитывает потомков компилятора. Один сервис разделяется компиляцией и загрузкой модулей; сохранённые пользовательские артефакты находятся вне его дерева. Бюджет запуска/READY равен одной секунде. Последующая гибель уже готового уборщика не меняет код завершения программы, но очистка больше не гарантируется.

Публикация использует общий файловый API и атомарную замену в том же каталоге с сохранением прав. Неуспешная сборка модуля оставляет прежний архив целым. Эта однофайловая гарантия не означает атомарную транзакцию над отдельным `.gbin` и соседней библиотекой. См. [файловый API](../../file-system-api.md) и [уборку](../../cleanup-service-api.md).

<a id="section-24-4"></a>

## 24.4. Нативная совместимость измеряется

Флаги компилятора сохраняют числовую семантику Goat (`-fno-fast-math`, `-ffp-contract=off`); целевые флаги применяются и к сгенерированному коду, и к встроенному runtime. Сборки Windows статически связывают поддерживаемый runtime компилятора там, где это требуется, вместо зависимости от установленного компилятора при исполнении.

Статическое исследование определяет реальные требования CPU/ОС/runtime по ELF/PE и зависимостям. Версия glibc сборочного хоста не копируется в метаданные. Неизвестные зависимости и неподдерживаемые импорты отклоняются. Основной хеш модуля не меняется от добавления native; каждая полная нативная библиотека имеет собственный SHA-256.

CI поставки проверяет перенесённые артефакты Debug/Release и реальные смешанные библиотеки MINGW64/UCRT64. Точные нижние границы контрольных библиотек исполнены в средах glibc 2.35/2.36. Обычные заявленные границы 2.14/2.17 и реальное исполнение на Windows 10 остаются отдельной невыполненной проверкой нижних границ, а не следствием проверки на новых runner. Свидетельства и план приведены в [тестах поставки](../../module-delivery-tests.md).

<a id="section-24-5"></a>

## 24.5. Ленивая загрузка и время жизни

До пользовательского кода проверяются весь граф архивов и все нативные байты, даже в `off` и для чужих вариантов. Повреждение фатально и не разрешает `auto` fallback. В `off` библиотека не выбирается, не извлекается и не загружается. В `required` собственный совместимый вариант корня обязан содержать хотя бы одну специализацию; зависимости не удовлетворяют этому требованию. Отдельные вызовы без подходящей специализации всё ещё могут использовать VM.

Только первый применимый вызов извлекает и загружает выбранную библиотеку модуля. Загрузчик использует удерживаемые проверенные байты, а не перечитывает архив. Ошибка извлечения/загрузки/привязки ABI библиотеки сохраняется: `auto` предупреждает один раз и использует VM для этой библиотеки; `required` завершается с ошибкой. Отказ готовности уборщика отключает native во всём запуске `auto` с одним предупреждением. Эти отказы до входа отличаются от фатального нарушения ABI после входа в адаптер.

Библиотеки и области живут для всех потоков программы и потомков. Обычное завершение безопасно выгружает их; `exit` всего процесса не выгружает библиотеку из-под активных нативных потоков. Загрузка не является песочницей: инициализаторы ОС могут исполняться до проверок после загрузки. `goat-inspect` предоставляет изолированную пробу, но не защитную изоляцию от вредоносного кода.

<a id="section-24-6"></a>

## 24.6. Команды отдельных исходников и модулей

Из корня репозитория, с подходящим компилятором:

```sh
mkdir -p build/book-native
cp docs/book/examples/22-native-module.goat build/book-native/module.goat
./goat --save-library build/book-native/module.goat
./goat --native required --print-native build/book-native/module.goat
./goat --list-native-targets
```

Первая команда Goat сохраняет `module.so` на Linux или `module.dll` на Windows; вторая готовит собственную временную библиотеку, а не использует сохранённую. Эквиваленты PowerShell используют `New-Item -ItemType Directory -Force`, `Copy-Item` и `.\goat.exe`.

Для именованного модуля используйте `goat build app.gmod --native required`, затем запускайте полученный `modules/<name>/<version>.gbin` без компилятора. Полные примеры `.gmod` даёт глава 30. Наборы сборки, загрузки, toolchain, уборки и поставки в CI проверяют отдельные этапы; отчёт `ready` свидетельствует о подготовке, а счётчики native устанавливают реальное исполнение адаптера.
