<a id="section-24-1"></a>

## 24.1. От текста к загружаемому файлу

Компиляция C — отдельная операция, выполняемая внешним инструментом. Goat подготавливает исходник, запускает компилятор, проверяет результат и передаёт файл загрузчику операционной системы. Linux использует разделяемую библиотеку `.so`, Windows — `.dll`. Библиотека содержит код, который процесс может загрузить во время работы.

Есть два близких сценария. `--save-library` сохраняет библиотеку рядом с исходником, не запуская Goat-программу. Подготовка нативного исполнения создаёт библиотеку во временной рабочей области, загружает её, проверяет и привязывает к байткоду. Само успешное создание файла ещё не доказывает пригодность библиотеки для данного байткода.

Координация подготовки находится в [native_pipeline.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/codegen/native_pipeline.c), выдача сохранённого C и библиотеки — в [c_output.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/cli/c_output.c).

<a id="section-24-2"></a>

## 24.2. Компилятор и аргументы

Исполняемый файл выбирается из непустой переменной окружения `CC`; иначе используются `cc` в Linux и `gcc` в Windows. Значение `CC` — имя или путь одного исполняемого файла, а не строка команды с дополнительными флагами.

На Linux [native_compiler_linux.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/codegen/native_compiler_linux.c) вызывает `posix_spawnp` с массивом аргументов. В Windows [native_compiler_windows.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/codegen/native_compiler_windows.c) находит программу через `SearchPathA`, формирует экранированную командную строку и использует `CreateProcessA`. Командная оболочка для интерпретации аргументов не запускается.

| Назначение | Linux | Windows / MinGW |
|---|---|---|
| Язык и оптимизация | `-std=c11 -O2` | `-std=c11 -O2` |
| Библиотека | `-fPIC -shared` | `-shared` |
| Числовая семантика | `-fno-fast-math -ffp-contract=off` | `-fno-fast-math -ffp-contract=off` |
| Неразрешённые символы | `-Wl,-z,defs` | `-Wl,--no-undefined` |
| Служебные библиотеки компилятора | Обычная линковка | `-static -static-libgcc` |
| Разрядность | Определяется средой компилятора | `-m32` или `-m64` по сборке Goat |
| Экспорты | Обычные правила ELF | `-DGOAT_NATIVE_BUILD -Wl,--exclude-all-symbols` |

Обе команды также передают `-o`, путь результата, путь C-исходника и `-lm`. Порядок и способ передачи путей задаёт реализация, а не пользовательская оболочка.

> [!CAUTION]
> Автоматическая сборка реализована для Linux и Windows с указанным интерфейсом компилятора. Произвольный C-компилятор с другими флагами не поддерживается автоматически. Тайм-аут завершения компилятора не установлен: зависший внешний процесс может задержать подготовку.

<a id="section-24-3"></a>

## 24.3. Рабочие файлы и публикация

Для отдельной операции сборки создаётся уникальный каталог рядом с целевым файлом. Linux использует `mkdtemp`; Windows — случайное имя и создание нового каталога. Внутри находятся исходник, выходная библиотека и журнал компилятора. В Windows временная DLL имеет итоговое базовое имя: оно участвует в формате экспортов PE.

Стандартный ввод компилятора направляется в `/dev/null` или `NUL`, вывод и ошибки — в файл журнала. Это позволяет дождаться процесса без взаимной блокировки из-за заполненной трубы. В память считываются не более 64 КиБ диагностики; об усечении сообщается отдельно. Проверяются код завершения, а в Linux также завершение по сигналу.

Успех требует существующего непустого обычного выходного файла. Публикация выполняется переименованием в Linux и `MoveFileExA` с заменой в Windows. Неудачная компиляция не должна затирать ранее сохранённую библиотеку. Временные файлы удаляются; ошибка очистки учитывается отдельно от результата компилятора.

При исполнении вся такая сборка размещается внутри временной области Goat. После успешной загрузки ответственность за её удаление передаётся объекту библиотеки. Каталог нужен до выгрузки, а не только до конца функции подготовки.

<a id="section-24-4"></a>

## 24.4. Почему пользователю не нужно копировать libgcc

MinGW может выпускать DLL, зависящую от `libgcc_s_dw2-1.dll`; эта библиотека, в свою очередь, может требовать `libwinpthread-1.dll`. Наличие `gcc.exe` в `PATH` само по себе не делает всю цепочку доступной выбранному режиму загрузки DLL.

Текущая Windows-команда использует `-static -static-libgcc`, чтобы служебный код GCC и MinGW POSIX threads подключался при линковке. Для библиотек, созданных этим конвейером при наличии соответствующих статических библиотек в комплекте компилятора, ручное копирование этих двух DLL не является требуемым шагом.

Это не означает отсутствие любых зависимостей. Системные DLL Windows остаются системными DLL; установленный компилятор по-прежнему нужен для сборки. Раздельный запуск готовых файлов без компилятора рассмотрен в главе 26.

<a id="section-24-5"></a>

## 24.5. Загрузка, проверка и владение

Linux получает абсолютный путь и вызывает `dlopen` с `RTLD_NOW | RTLD_LOCAL`: символы разрешаются при загрузке, а библиотека не публикует их в глобальную область поиска. Windows использует полный путь и `LoadLibraryExA` с `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`. Затем ищется ровно `goat_native_query_v1` и проверяется ABI из главы 23.

Нативный конвейер проверяет весь ожидаемый набор записей перед установкой привязок. Если привязка не удалась, уже установленные связи очищаются. Состояние `ready` требует хотя бы одной привязанной функции.

Дескриптор функции (структура со ссылками на её специализации) удерживает ссылку на библиотеку. Объекты функций и байткод могут удерживать дескрипторы. При освобождении последней ссылки библиотека выгружается, затем очищается её рабочая область. Поэтому указатель адаптера не должен пережить содержащий его машинный код. Общая часть владения находится в [native_library.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/native_library.c), платформенная — в [native_library_linux.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/native_library_linux.c) и [native_library_windows.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/native_library_windows.c).

> [!CAUTION]
> Загрузка не является песочницей (изолированной средой исполнения). Инициализаторы библиотеки могут выполниться ещё до проверки таблицы ABI. Компилятор и загружаемый код должны быть доверенными. В Windows текущие операции с путями и системными сообщениями используют варианты API `A`; полноценная поддержка всех Unicode-путей и корректный UTF-8 для любой локализованной ошибки не обеспечены.

<a id="section-24-6"></a>

## 24.6. Команды для двух платформ

Для рабочей копии из главы 22, в Linux:

```sh
./goat --save-library build/book-native/module.goat
./goat --native required --print-native build/book-native/module.goat
```

Первая команда сохраняет `module.so`. Вторая подготавливает собственную временную библиотеку и исполняет программу; она не означает «подхватить ранее сохранённый `.so`».

В PowerShell, из корня репозитория:

```powershell
New-Item -ItemType Directory -Force .\build\book-native | Out-Null
Copy-Item .\docs\book\examples\22-native-module.goat .\build\book-native\module.goat
.\goat.exe --save-c .\build\book-native\module.goat
.\goat.exe --save-library .\build\book-native\module.goat
.\goat.exe --native required --print-native .\build\book-native\module.goat
```

Сохраняемая библиотека здесь называется `module.dll`. Обе платформы должны получить `7`, `6`, `4.0`, затем отчёт с `preparation=ready`. Ошибка запуска компилятора, ошибка компиляции и ошибка загрузки — разные стадии; точный статус и диагностика полезнее общего утверждения «нативный код не работает».

Поведение внешнего инструмента и сохранность результата проверяют [check_native_library.sh](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/scripts/check_native_library.sh); Windows-случаи, включая линковку, — [check_native_windows.sh](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/scripts/check_native_windows.sh); целую подготовку — [check_native_pipeline.sh](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/scripts/check_native_pipeline.sh).
