<a id="section-29-1"></a>

## 29.1. Какой вопрос задаёт эксперимент

Исторический [check_native_performance.py](https://github.com/kniazkov/g0at/blob/d8eb008bc6c2fd5625cef9720f921a0dd7131ee7/scripts/check_native_performance.py), теперь заменённый на [native_performance_scenarios.c](../../../test/src/functional/native_performance_scenarios.c), сравнивает два запуска одной вычислительной нагрузки: сохранённый байткод в VM и сохранённую программу с нативной библиотекой. Проверяется узкое утверждение: для этого дерева числовых вызовов медиана времени нативного процесса должна быть меньше медианы VM.

Это не рейтинг языков и не оценка произвольного приложения. Нагрузка специально содержит много вызовов чистых числовых функций — ту область, которую обслуживает текущий бэкенд. Ввод, строки, объекты и исключения она не представляет.

<a id="section-29-2"></a>

## 29.2. Дерево вызовов

Генератор создаёт `leaf(n)`, вычисляющую `n * n + 3 * n + 7`, и функции `level1` … `level11`. Каждый уровень дважды вызывает предыдущий: с `n + 1` и `n + 2`. Верхний уровень программы суммирует 1024 дерева с начальными аргументами от 0 до 1023.

При глубине 12 одно дерево содержит \(2^{12}-1=4095\) входов в функции; всего получается 4 193 280 входов. Максимальная цепочка неглубока, но число вызовов велико. В исходнике верхние вызовы выписаны генератором отдельно: циклы Goat для этого не требуются.

Накопительного бюджета входов в нативные функции нет. Это неглубокое дерево вызовов укладывается в ограничения глубины и стека независимо от общего числа вызовов. В отчёте ожидаются 1024 входа в адаптер, а не миллионы внутренних C-вызовов.

Ожидаемую сумму C-runner, как и исходная Python-проверка, вычисляет независимо, через биномиальные коэффициенты: на 11 уровнях число путей с заданным количеством прибавлений `2` известно комбинаторно. Это проверяет результат другим способом, чем рекурсивное выполнение Goat.

<a id="section-29-3"></a>

## 29.3. Подготовка не входит в выборку

Runner создаёт одинаковые `vm.goat` и `native.goat`, затем вызывает `--compile --native off` и `--compile --native required`. Обе команды должны завершиться без stdout и stderr. После подготовки оба исходника удаляются; копия для изучения сохраняется под именем `call_tree.goat`.

Перед исполнением `CC` заменяется на `goat-no-such-compiler`. Запускаются только `.gbin`. Следовательно, незаметная компиляция во время замера не может стать частью успешного сценария. Подготовка и отдельные прогревочные запуски измеряются технически общей функцией, но их времена не добавляются к выборке.

<a id="section-29-4"></a>

## 29.4. Что именно измеряется

C-runner получает монотонные наносекундные отметки непосредственно перед созданием дочернего процесса и сразу после ожидания его завершения. На Linux используется `CLOCK_MONOTONIC`, на Windows — `QueryPerformanceCounter`; сохранение диагностических артефактов и проверка результата находятся за пределами этого интервала. Историческая Python-проверка использовала `time.perf_counter_ns()` вокруг `subprocess.run`. Это прошедшее время процесса, а не сумма длительностей одних арифметических инструкций. В него входят запуск интерпретатора, чтение и проверка `.gbin`, загрузка снимка библиотеки в нативном варианте, исполнение, вывод, запись отчёта и завершение.

После одного прогрева каждого варианта выполняются пять пар замеров. Порядок чередуется: сначала VM/нативный, затем нативный/VM. Это уменьшает систематический перекос порядка, но не устраняет влияние планировщика, частоты CPU и файлового кеша.

Для каждого запуска проверяется точный stdout и отсутствие stderr. Отчёт должен подтвердить:

| Поле | VM | Нативный вариант |
|---|---|---|
| `preparation` | `disabled` | `ready` |
| `attempts` | 0 | 1024 |
| `succeeded` | 0 | 1024 |
| `retries` | 0 | 0 |

Без этой проверки быстрый запуск, случайно ушедший в другой режим или вычисливший неверный ответ, не имел бы смысла. На один дочерний процесс установлен тайм-аут 180 секунд.

<a id="section-29-5"></a>

## 29.5. Команды и результаты

Нужна Release-сборка без `MEMORY_DEBUG`. Из корня репозитория в Linux:

```sh
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=gcc
cmake --build build/release --target native_performance_scenarios
ctest --test-dir build/release --output-on-failure -R '^integration.native_performance.benchmark$'
```

В PowerShell, при доступном MinGW:

```powershell
cmake -S . -B build/release -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=gcc
cmake --build build/release --target native_performance_scenarios
ctest --test-dir build/release --output-on-failure -R '^integration.native_performance.benchmark$'
```

Сценарий CTest запускается только в Release, последовательно и отдельно от проверок корректности. Он выбирает настроенный C-компилятор через `CC` и сохраняет каждый запуск в уникальном каталоге внутри `build/release/ctest/native performance/`. Сам benchmark-runner не требует Python. Прямой запуск и подтверждение сверки описаны в [карте миграции](../../../test/data/native-performance/README.md).

`timings.json` содержит параметры дерева, ожидаемый результат, все времена `samples_ns`, медианы `vm_median_ns` и `native_median_ns`, отношение `speedup` и флаг `passed`. Медиана — средний по порядку элемент отсортированной выборки; здесь это третий из пяти замеров. Тест проходит только при строгом `native_median_ns < vm_median_ns`.

<a id="section-29-6"></a>

## 29.6. Как ссылаться на измерение

При публикации результата указываются commit, ОС и архитектура, процессор, компилятор и его версия, параметры сборки, команда, исходные выборки и обе медианы. Коэффициент без этих данных невозможно нормально воспроизвести. Файлы `*.report` подтверждают режим, а `timings.json` позволяет проверить расчёт отношения.

> [!CAUTION]
> Runner сохраняет времена и параметры нагрузки, но не полный паспорт машины и сборки. Пять измерений и чередование порядка не дают статистической гарантии; посторонняя нагрузка может вызвать падение проверки быстродействия при корректном результате. Runner требует реального ускорения и не заменяет неудачный результат предупреждением.

Время компиляции намеренно исключено, а накладные расходы загрузки включены. Поэтому результат отвечает на вопрос о повторном запуске подготовленной программы. Он не показывает, окупится ли компиляция при единственном коротком вызове, и не обещает такой же коэффициент для другой программы. На этой границе заканчивается утверждение эксперимента.
