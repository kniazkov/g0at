## 16.1. Операция преобразует сведения

Передаточная функция описывает, как операция меняет абстрактные значения и состояние. Для сложения она получает описания операндов и выдаёт описание суммы; для присваивания дополнительно меняется запись переменной. В Goat методы узлов AST координируют вычисление, а файлы `src/analysis` реализуют операции над доменами.

Узел обычной бинарной операции вычисляет левый операнд, затем правый. Если первый уже прекратил нормальный путь, второй не должен анализироваться как выполненный. Результат `BOTTOM` и режим управления передают этот факт дальше. Для вызова порядок другой: аргументы справа налево, затем вызываемое значение, как в VM.

Это не косметическая подробность. В `f(x++, x++)` перестановка обхода меняет значения аргументов и последующее состояние `x`. Абстрактная модель обязана следовать семантике языка, а не удобному порядку обхода детей дерева.

## 16.2. Точность арифметики

[addition.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/addition.c), [subtraction.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/subtraction.c) и [multiplication.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/multiplication.c) различают константы, целые диапазоны и общие числовые типы. Для констант сохраняется конкретный результат. Для интервалов, где это возможно, вычисляются границы.

Целочисленное переполнение требует осторожности. Константная операция использует арифметику языка по модулю `2^64`. Но интервал, переходящий через границу представления, уже нельзя описать обычным непрерывным интервалом между наивно переполненными концами. В таких случаях результат расширяется до `integer`.

[division.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/division.c) учитывает ноль, точное целое частное и переход к вещественному. Деление двух произвольных целых обычно даёт `numeric`: для одних аргументов результат целый, для других — вещественный. Отдельно учитывается минимальное целое, делённое на `-1`. Операции `%` и `**` имеют свои правила в [modulo.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/modulo.c) и [power.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/power.c).

Абстрактный нормальный результат не всегда доказывает отсутствие исключения для всех входов. Если делитель может быть нулём и ненулевым числом, описание успешных частных ещё не описывает ошибочный путь. Поэтому оптимизатору недостаточно увидеть один подходящий тип результата.

<a id="section-16-3"></a>

## 16.3. Сравнения, истинность и биты

[comparison.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/comparison.c) вычисляет известное логическое значение, когда константы или границы позволяют это доказать; иначе остаётся `boolean`. Целые границы не переводятся безусловно в `double`: это сохранило бы не все различия больших целых.

`lattice_truth` даёт четыре исхода: `ABSTRACT_TRUE`, `ABSTRACT_FALSE`, `ABSTRACT_EITHER` и `ABSTRACT_NEVER`. Последний означает отсутствие нормального значения, а не ещё один вариант логического `false`. Интервал, не содержащий нуля, истинен; произвольная строка может быть пустой и поэтому даёт `EITHER`.

Побитовые операции в [bitwise.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/bitwise.c) работают с целочисленной областью, вычисляют константы и отдельные полезные ограничения. Например, маска может ограничить диапазон результата. Неподдерживаемый тип и недопустимый известный сдвиг не должны превращаться в произвольный успешный результат.

Префиксные и постфиксные изменения используют [update.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/update.c). Обе формы записывают новое значение, но возвращают разные описания: префикс — новое, постфикс — старое. Сведение обеих форм к одному чистому арифметическому выражению потеряло бы запись в состояние.

## 16.4. if и короткое замыкание

В [if_else.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/if_else.c) известное условие выбирает одну ветвь; неизвестное создаёт копии состояния, выполняет обе ветви и объединяет результаты. Отсутствующий `else` означает второй путь без тела. Завершившаяся ветвь не участвует в текущих значениях продолжения.

Логические `&&` и `||` в [logic.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/logic.c) также ветвят вычисление. Если левый операнд уже определил результат, правый пропускается вместе с его эффектами. При неопределённой истинности нужно учитывать как вычисление правого, так и его пропуск.

Файл [16-control.goat](../examples/16-control.goat):

```goat
var count = 0;
false && ++count;
true || ++count;
var result = 10;
if (input()) { result = 20; } else { result = 30; }
println(count);
println(result);
```

При строке ввода `yes` результат:

```text
0
20
```

При пустой строке:

```text
0
30
```

Оба `++count` пропущены. Анализ также не должен приписывать им выполненную запись. В последнем условии заранее неизвестна ветвь, но известны возможные значения результата после объединения.

### Циклу нужны факты для всех итераций

Первое посещение с `i = 0` не позволяет заменить `i < n` или ветвление внутри цикла для всех дальнейших посещений. Поэтому [`for.c`](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/for.c) вычисляет инвариант заголовка (факты, охватывающие каждое прибытие к условию). Выполняется один абстрактный проход условия, тела и шага, продолжающееся состояние обратного перехода объединяется с предыдущим заголовком, затем процесс повторяется. Возвраты пополняют сведения о результате функции, но не возвращаются к условию.

[`widen_loop_state`](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/abstract_state.c) расширяет меняющиеся константы и интервалы до областей типов. Например, растущий счётчик со значениями `0` и `1` становится `integer`, вместо бесконечной цепочки увеличивающихся интервалов. Неизменившиеся факты сохраняются. После стабилизации текущих фактов условие вычисляется из этого инварианта для описания выхода. Ложное первое условие сохраняет факты для нуля итераций; всегда истинное условие на инварианте не даёт обычного выхода. Это не доказательство завершения.

Обычный проход достижимости использует такое абстрактное исполнение, не записывая первую итерацию как константу общего AST. Доказательства выражений конкретной специализации пересекают наблюдения разных проходов, поэтому ранняя константа не сохраняется при последующем несовместимом наблюдении.

> [!CAUTION]
> Для одного цикла отведено 16 абстрактных проходов; с вызовами и вложенными циклами он разделяет существующий бюджет вычисления, изначально равный 1024. Если стабилизация не получена, текущие факты и сведения о возврате становятся неизвестными, а сигнатура не получает нативный допуск из незавершённого анализа. Проверки выхода не сужают интервалы счётчиков; даже для конечного исходного цикла могут сохраниться только типы переменных.

<a id="section-16-5"></a>

## 16.5. Возврат и недостижимость

`return` сначала анализирует выражение. Его нормальный результат добавляется к общему аккумулятору возвращаемых значений через `join`, а управление становится `FLOW_RETURN`. Операторы после возврата на этом пути уже не исполняются. Достижение конца функции добавляет возможный `null`.

При неизвестном условии один путь может вернуть значение, а другой продолжиться. Поэтому «в теле есть return» не означает «функция всегда возвращает здесь». Объединяются отдельно возвращённые значения, наблюдения за переменными и возможность обычного продолжения.

Позже отдельный проход [reachability.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/reachability.c) устанавливает `NODE_FLAG_UNREACHABLE` и `immediate_value`. Это уже подготовка доказательств для изменения общего AST. Он консервативнее обычного анализа вызовов: пользовательский вызов заставляет забыть текущие факты, а тело функции не выполняется только потому, что встретилось выражение её создания. Результат конкретного исследованного вызова не становится глобальным свойством общего тела.

<a id="section-16-6"></a>

## 16.6. Исключения: исполнение опережает анализ

В VM `try/catch` работает с точным выброшенным значением и разворачиванием контекстов. Абстрактному анализу для такой же точности потребовались бы отдельные состояния исключительного выхода и их перенос в обработчик.

> [!CAUTION]
> В текущей реализации такой модели нет. Метод `execute` узла `try/catch` в [try_catch.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/try_catch.c) забывает известные значения и сохраняет возможность продолжения; он не вычисляет точные состояния тела и обработчика. Обычный анализ известного вызова отказывается от точного обхода тела с `try/catch`, а анализ типов помечает такую попытку незавершённой.

Явный `throw` и заведомо ошибочная операция могут прекратить нормальный путь. Это полезно, но не заменяет точное моделирование того, где и с какими изменёнными переменными будет перехвачена ошибка. Поддержка исполнения конструкции и точность её анализа — разные свойства.

<a id="section-16-7"></a>

## 16.7. Где сведения расширяются

Точность теряется по нескольким причинам: домен не умеет выразить множество результатов, тип операнда неизвестен, вызов может менять окружение или нужный переход ещё не смоделирован. `TOP` в журнале поэтому не обязательно означает дефект; часто это честная граница доказательства.

> [!CAUTION]
> Анализ условий сейчас не является решателем ограничений, а поддержка операторов в абстрактной интерпретации шире нативного подмножества. Точный результат для `%`, сдвига или логического оператора сам по себе не разрешает генерацию соответствующей C-функции.

Для проверки поведения служат программы в [list.txt](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/analysis/list.txt) и тесты достижимости в [test_reachability.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/test/test_reachability.c). Они сопоставляют не только тип результата, но и записи, которые должны либо не должны появляться при данном порядке вычисления.
