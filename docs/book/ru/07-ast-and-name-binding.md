<a id="section-7-1"></a>

## 7.1. Дерево уже есть, но имена ещё не связаны

Парсер может построить узел переменной `x`, не зная, где эта переменная объявлена. Для синтаксиса достаточно распознать имя. Для анализа этого мало: два одинаковых имени могут обозначать разные переменные, а разные обращения должны иногда вести к одному объявлению.

Поэтому AST (абстрактное синтаксическое дерево) после разбора дополняется областями видимости, родительскими ссылками и связями с объявлениями. Вход этого этапа — корневой узел; результат — структура, по которой можно определять, какие данные читает и изменяет программа. Главный проход находится в [analysis.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/analysis.c) и выполняется даже при `--optimize none`.

<a id="section-7-2"></a>

## 7.2. Узлы и виды связей

Общая часть [node_t](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/node.h) хранит таблицу методов, родителя, исходный диапазон, область видимости, идентификатор обхода и флаги анализа. Конкретный узел добавляет собственные данные: литерал — значение, бинарная операция — операнды, объявление — список объявляемых имён.

Полезно различать категории из [node_type.h](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/node_type.h):

| Категория | Примеры и назначение |
|---|---|
| Структурные узлы | Корень, список параметров, тело функции |
| Деклараторы | По одному узлу для имени переменной, константы или параметра |
| Выражения | Литерал, переменная, вызов, операция, функция, блок-выражение |
| Инструкции | Объявление, возврат, `throw`, обёртка выражения |
| Управление | Условие и обработчик исключения |
| Замены | Исходная и преобразованная версии выражения или инструкции |

Декларатор (узел, вводящий одно имя) не равен всей инструкции объявления. В `var a = 1, b = 2;` одно объявление содержит два декларатора. Анализ должен иметь возможность различать их значения.

У дерева есть структурные рёбра — например, от сложения к его операндам. Есть и смысловые связи: от употребления переменной к декларатору. Последняя не делает объявление дочерним выражением переменной. Для неё предусмотрены отдельные методы `get_related` и тип связи `RELATION_DECLARATION` в [variable.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/variable.c). Поэтому представление становится графом связей, хотя основой обхода остаётся дерево конструкций.

<a id="section-7-3"></a>

## 7.3. Как назначаются области и идентификаторы

Область видимости описана [scope_t](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/scope.h): у неё есть родитель и таблица имён. [Поиск](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/scope.c) сначала проверяет текущую область, затем идёт к родителю. Ближайшее найденное объявление затеняет одноимённое внешнее.

Вначале создаётся область встроенного окружения. Далее обход устанавливает `parent` и `scope` узлов, создаёт вложенные области для функций и обычных блоков и ставит функции в очередь на связывание. Для `try/catch` дополнительно разделяются область защищённого кода и область обработчика; имя исключения относится к обработчику.

Идентификатор `node_t.id` назначается при обходе. Нумерация начинается заново на границе функции, но продолжается внутри обычных блоков. Это не глобальный уникальный номер узла для всех функций и не постоянный адрес в сохранённой программе. У синтетических узлов, добавленных после первоначального обхода, идентификатор может оставаться нулевым.

Обход также сбрасывает результаты прежнего анализа: флаги, точечные значения выражений, сводки функций и другие вычисленные сведения. Повторный анализ должен строить их заново, а не принимать старый результат за доказательство для нового состояния дерева.

`for` вводит область видимости для инициализации, условия, шага и тела. Тело имеет вложенную область даже без явных скобок. Поэтому `var i` в заголовке затеняет внешнюю `i`. Запись `for (i = 0; ...)`, напротив, присваивает существующей переменной; если `i` неизвестна, неявно объявить её в заголовке цикла нельзя — это ошибка компиляции (см. раздел 7.6).

<a id="section-7-4"></a>

## 7.4. Одно написание, разные переменные

[Пример областей и захвата](../examples/07-bindings.goat):

```goat
var x = 10;
{
    var x = 20;
    println(x);
}
println(x);
const make = func() {
    const read = func() { return value; };
    var value = 30;
    return read;
};
const read = make();
println(read());
try { throw 40; } catch (x) { println(x); }
println(x);
```

Результат:

```text
20
10
30
40
10
```

В примере одновременно видны несколько независимых связей:

| Употребление имени | К чему оно относится |
|---|---|
| `x` при печати внутри обычного блока | Локальное `var x = 20` |
| `x` после обычного блока | Внешнее `var x = 10` |
| `value` в теле вложенной `read` | `var value = 30` внутри `make` |
| `x` в обработчике | Значение исключения, введённое `catch (x)` |
| `x` после обработчика | Снова внешнее `var x = 10` |

При встрече декларатора связывающий проход добавляет его в таблицу текущей области. При встрече узла переменной ищет объявление и записывает указатель в `variable_t.declarator`. Последующий анализ использует эту связь, чтобы различать состояния одноимённых переменных.

Встроенные имена тоже участвуют в поиске. Для них используется общий синтетический декларатор (служебный узел без обычного объявления в исходнике), а конкретная встроенная функция дополнительно определяется по имени и реестру. Поэтому один такой указатель сам по себе не различает `print` и `println`. Локальное объявление с тем же именем получает собственный декларатор и обычным образом затеняет встроенное значение.

<a id="section-7-5"></a>

## 7.5. Почему вложенные функции связываются позже

В `make` функция `read` записана раньше объявления `value`. Обычный последовательный обход с немедленным входом в каждую функцию на этом месте ещё не встретил бы нужное объявление. Goat использует очередь: сначала связывает внешнюю область, пропуская тела вложенных функций, затем обрабатывает отложенные функции. Порядок обеспечивает обработку внешней функции раньше вложенной.

К моменту связывания `read` объявление `value` уже находится в таблице окружающей области. Употребление имени получает ссылку на него и становится захватом (обращением функции к переменной внешнего окружения). Тот же порядок позволяет разрешать ссылки между функциями, объявления которых встречаются позже во внешней области.

Связать имя и исполнить объявление — разные действия. Наличие ссылки на поздний декларатор не означает, что его инициализатор уже был выполнен. В нашем примере `read` вызывается после завершения `make`, поэтому `value` уже получил `30`. Этот порядок выбран намеренно; связывание само по себе не доказывает корректность любого более раннего вызова.

AST хранит факт связи с объявлением. Сохранение конкретного окружения при создании функции и продление жизни захваченных значений выполняет уже [объект функции](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/model/function.c). Поэтому функция в примере продолжает читать `value` после выхода из `make`.

<a id="section-7-6"></a>

## 7.6. Неизвестное имя создаёт объявление

Если поиск не находит имени, поведение зависит от того, как имя используется. Самостоятельное присваивание необъявленному имени объявляет константу: `x = 10;` превращается в `const x = 10;`, а оператор присваивания заменяется узлом объявления. Чтение необъявленного имени ничего не объявляет и даёт `null`. [Пример](../examples/07-implicit.goat):

```goat
println(missing);
missing = 5;
println(missing);
```

Он выводит `null`, затем `5`, каждое значение с новой строки: первый вызов `println` читает ещё не объявленное имя и получает `null`, затем `missing = 5` объявляет константу со значением `5`, и последний вызов печатает `5`. Увидеть вставленное объявление можно на Linux:

```sh
./goat --optimize none --enable-warnings --print-source-code docs/book/examples/07-implicit.goat
```

В Windows PowerShell:

```powershell
.\goat.exe --optimize none --enable-warnings --print-source-code .\docs\book\examples\07-implicit.goat
```

В восстановленном исходнике второй оператор заменён на `const missing = 5;`. Предупреждение укажет на чтение `missing` до объявления; затем программа исполнится. Предупреждение и вывод программы направляются в разные потоки, поэтому их взаимное расположение на экране может зависеть от окружения.

Сама замена откладывается до завершения связывающего обхода: иначе изменение детей меняло бы индексы и последовательность, по которой прямо сейчас идёт алгоритм. Правая часть присваивания становится инициализатором константы, а созданный декларатор сразу заносится в область, чтобы следующие употребления имени могли найти его. После замены новому поддереву назначаются родительские связи и существующая область.

Константа объявляется только тогда, когда слева от присваивания стоит необъявленное имя, а само присваивание является самостоятельным оператором. В цепочке `x = y = 10`, в аргументе вызова `println(a = f(3))`, в шаге цикла `i++` или в заголовке `for (i = 0; ...)` необъявленное имя нельзя превратить в константу однозначно, поэтому такие случаи являются ошибкой компиляции. Опечатка в имени при чтении по-прежнему может остаться незамеченной, поэтому включение предупреждений помогает её выявить. Неявное объявление является реализованным правилом, а не признаком того, что анализатор доказал намерение автора.

Запись в ту же неявную константу внутри её инициализатора, например `x = x = 1` или `x = x++`, также является ошибкой компиляции. Проверка различает одноимённые локальные объявления и не запрещает рекурсивные обращения в телах функций.

<a id="section-7-7"></a>

## 7.7. Исходное дерево и результаты анализа

Узел выражения может хранить `immediate_value` — сведения о значении в конкретной точке немедленного исполнения. Декларатор хранит `abstract_value` — накопленное описание присваиваемых ему значений. Специализации функции хранятся отдельно. Эти данные нельзя автоматически заменять друг другом: имя переменной, её конкретное употребление и функция для целого набора типов отвечают на разные вопросы.

Флаги узла отмечают установленные свойства: недостижимость, чистоту и совместимость с поддерживаемым C-подмножеством. Отсутствие флага не доказывает противоположного свойства. В частности, отсутствие доказанной чистоты не означает, что эффект обязательно произойдёт в каждом запуске.

При упрощении [узел замены](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/replacement.c) сохраняет исходный и новый варианты. Исполнение через байткод использует результат замены; история остаётся доступной для просмотра и восстановления. [restore_graph](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/simplification.c) возвращает исходные поддеревья перед новым анализом.

Из-за сохранённой истории некоторые потомки могут быть общими для старого и нового вариантов. Поэтому `parent` трактуется как родитель в исполняемом дереве; его нельзя одновременно понимать как единственного владельца по каждому историческому ребру. Саму память узлов удерживает арена. Здесь важно знать устройство хранения; условия, при которых замена сохраняет поведение, будут рассмотрены в главе 21.

<a id="section-7-8"></a>

## 7.8. Область анализа не является контекстом VM

Статическая область хранит связь имени с объявлением во время подготовки программы. [Контекст VM](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/model/context.h) хранит конкретные данные исполнения и сведения о возврате или обработке исключения. При двух вызовах одной функции появляются разные исполнительные контексты, хотя дерево функции и её статическая область одни и те же.

Ссылка `variable_t.declarator` не записывается в байткод как адрес ячейки значения. В [генерации переменной](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/variable.c) используются имя в сегменте данных и инструкции `VLOAD`/`STORE`; исполнительная среда выполняет поиск в своих объектах окружения. Анализатор же различает объявления по их узлам. Эти два механизма служат разным этапам системы.

Для проверки полезны [пример затенения в анализе](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/analysis/shadowing.goat), [проверка локальной функции с именем println](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/analysis/purity_shadow_println.goat), [изменение внешнего окружения](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/functional/external_scope_changing/program.goat) и [тесты восстановления дерева](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/test/test_replacement.c). Пример этой главы дополнительно показывает позднее объявление в замыкании и локальность имени обработчика.

После связывания система располагает не только структурой записи, но и связями, необходимыми для рассуждения о программе. Далее эта структура станет байткодом, а статические имена получат конкретные значения в исполнительной среде.
