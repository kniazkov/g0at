## 27.1. Несколько окон в одну программу

Интерпретатор умеет показывать программу на разных этапах. Каждый вид вывода отвечает на свой вопрос: как разобран текст, что установил анализ, какие инструкции созданы и какой способ исполнения действительно использован. Смешение этих вопросов приводит к ошибочным выводам: зелёная функция на графе ещё не означает, что процессор исполнил её нативную версию.

Порядок действий задаёт [launcher.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/cli/launcher.c): анализ, журнал, восстановленный текст, граф, затем экспорт C либо генерация байткода и исполнение. Параметры `--print-*` обычно добавляют диагностический вывод к обычному запуску, а не заменяют запуск. Экспорт C и `--compile` составляют отдельные режимы без исполнения тела.

## 27.2. Пример для наблюдения

Файл [27-observability.goat](../examples/27-observability.goat):

```goat
var value = 2;
if (false) { value = 100; }
const twice = func(x) { return x * 2; };
println(twice(value));
```

Его результат — `4`. Ветвь с `100` недостижима, а для `twice` можно получить целочисленную специализацию. Из корня репозитория:

```sh
./goat --optimize none --print-source-code docs/book/examples/27-observability.goat
./goat --print-source-code docs/book/examples/27-observability.goat
./goat --optimize none --print-bytecode docs/book/examples/27-observability.goat
```

Восстановленный текст строится из AST: комментарии и исходные пробелы не восстанавливаются. При `none` сохраняется исходная структура вычислений; при `all` видны выбранные замены и удалённые недостижимые действия. Это способ проверить преобразование дерева, но не доказательство эквивалентности двух программ для всех входов.

В листинге байткода адреса — индексы инструкций, а не байтовые смещения. Для удобства печатается каждый пятый индекс. Например, в неоптимизированном примере `JIF` переходит к инструкции 10, а `ARG 20` перед `FUNC` задаёт начало тела. `END` завершает верхний уровень, но после него в буфере находится тело `twice`. Полный справочник — в [приложении В](appendix-c-vm-instructions.md).

## 27.3. Журнал: наблюдения и доказательства

```sh
./goat --print-analysis docs/book/examples/27-observability.goat
```

Среди строк журнала находятся:

```text
#1 27-observability.goat, 1.1: write value = 2
#4 27-observability.goat, 3.15: summary x = 2
#27 27-observability.goat, 3.15: function-summary analyzed (integer) -> integer effects=none c=supported purity=pure direct-effects=none calls=no captures=[] c-blockers=none
```

`#` — порядковый номер события коллектора, затем идут имя файла, строка и столбец. `write` описывает наблюдение присваивания, `join` — объединение состояний, `summary` — накопленную сводку объявления. Это журнал работы анализатора, а не трасса фактического исполнения VM.

Сводка `x = 2` получена для конкретного наблюдаемого вызова. Строка `function-summary` описывает отдельное доказательство для всех значений сигнатуры `(integer)`. Она сообщает статус анализа, тип результата, эффекты, чистоту и допуск C. Записи `c-expression` относятся к точкам выражений внутри сигнатуры, а `call-group` — к компонентам графа вызовов. Отсутствие эффекта в одном наблюдении нельзя подменять доказанной чистотой всей специализации.

Коллектор и текстовое представление находятся в [collector.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/collector.c). При изменении программы или состава проходов номера событий могут измениться; они не являются постоянными идентификаторами исходника.

## 27.4. Граф и его легенда

Для графа нужен установленный Graphviz с доступным `dot` (`dot.exe` в Windows):

```sh
mkdir -p build/book-observe
./goat --save-graph build/book-observe/program.svg docs/book/examples/27-observability.goat
```

[visualization.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/graph/visualization.c) строит DOT и вызывает Graphviz, затем удаляет промежуточный `.dot`. Допустимы `.svg` и `.png`.

| Оформление | Значение |
|---|---|
| Светло-серая граница и серый текст | Недостижимый узел; без цветной заливки |
| `forestgreen`, зелёная граница | Признак совместимости C в текущем представлении |
| Светло-зелёная заливка | Признак чистоты в текущем представлении |
| Фиолетовая граница и заливка | Узел замены с исходной и заменяющей ветвями |
| Пунктирная синяя связь | Дополнительное отношение, например ссылка на объявление |
| Пунктирная рамка группы | Область видимости |

У функции может быть пометка `C view:` с выбранной сигнатурой. [function_summary.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis/function_summary.c) выбирает первую чистую `supported`-специализацию; визуализатор распространяет её отображаемые признаки на достижимое поддерево. Это слой отображения, а не изменение общих флагов AST и не обещание для остальных сигнатур. Читать цвет следует вместе с `C view` и журналом.

> [!CAUTION]
> Граф показывает одну выбранную C-специализацию, а не все варианты одновременно. Длинные строковые подписи сокращаются. Ошибка Graphviz печатается в stderr, но сама по себе не обязательно делает итоговый код завершения Goat неуспешным: нужно проверить наличие изображения и диагностику.

## 27.5. Подтверждение реального нативного входа

```sh
./goat --native required --print-native docs/book/examples/27-observability.goat
```

При обычном достаточном запасе стека после `4` выводится:

```text
mode=required
preparation=ready
bound=1
omitted=0
attempts=1
succeeded=1
retries=0
```

`supported` относится к анализу, `ready` — к подготовке, `succeeded=1` — к успешному фактическому вызову адаптера. Это три разных свидетельства. Значения счётчиков и случаи возврата в VM разобраны в главе 25.

Чтобы не смешивать журнал с результатом программы, используем файлы:

```sh
./goat --save-analysis build/book-observe/analysis.txt --native required --save-native build/book-observe/native.txt docs/book/examples/27-observability.goat
```

На stdout останется результат программы. Сообщения об ошибках по-прежнему идут в stderr. Параметры и запрещённые сочетания собраны в [приложении Д](appendix-e-launch-interfaces.md); проверка цветов и выбранного представления — в [check_graph.sh](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/scripts/check_graph.sh).
