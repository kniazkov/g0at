<a id="section-28-1"></a>

## 28.1. Разные проверки обнаруживают разные ошибки

Тест устанавливает конкретное соответствие: операция дала ожидаемое значение, анализ сохранил нужный факт, программа напечатала нужный текст или отказала до исполнения. Один уровень не заменяет остальные. Правильный абстрактный тип результата не доказывает правильность машинного кода; совпавший stdout не доказывает отсутствие утечки.

В репозитории три основных исполнителя: `unit_testing`, `analysis_testing` и `functional_testing`. Интеграционные сценарии в `scripts` соединяют интерпретатор, внешний компилятор и загрузчик. Они проверяют границы, которые неудобно проверять одной C-функцией.

<a id="section-28-2"></a>

## 28.2. Юнит-тесты и учёт памяти

[unit_testing.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/unit_testing.c) регистрирует тесты из `src/test`. Здесь проверяются контейнеры, арены, UTF-8, решётка, состояния, разбор, модель объектов, генерация, ABI и двоичный формат. Проверка утверждения сообщает строку отказа и имя случая; затем печатается итог с числами прошедших и упавших случаев.

В обычной Debug-сборке действует `MEMORY_DEBUG`: обёртки выделения памяти ведут учёт. Это помогает проверить возвращение к исходному объёму после освобождения и найти потерянные блоки. В конфигурации Release этот режим отключён. Данные о времени из этих двух сборок нельзя смешивать без оговорки.

Тесты владения особенно важны для арены, разделяемых абстрактных состояний, циклов объектов, исключений и дескрипторов библиотек. Последняя ссылка должна освобождать ресурс, а временное удаление одной ссылки не должно уничтожать ещё используемый объект.

<a id="section-28-3"></a>

## 28.3. Исходные тесты анализатора

[analysis_testing.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/analysis_testing.c) читает имена из `test/analysis/list.txt`. Каждому имени соответствуют `.goat` и `.expect`. Программа проходит разбор и анализ; VM для проверки результата не запускается. Ожидания выбирают структурированные события, а не сравнивают весь текст журнала.

Строка ожидания содержит шесть полей: режим, вид события, строку, уточняющую координату, селектор и ожидаемое значение. Значение четвёртого поля зависит от вида: для событий переменной это строка объявления, для флагов и специализаций — столбец. Нулевая координата может служить отсутствием ограничения.

| Режим | Требование |
|---|---|
| `one` | Ровно одно подходящее событие с нужным значением |
| `last` | Есть подходящие события; последнее имеет нужное значение |
| `none` | Подходящих событий нет; вместо значения записывается `-` |

Для функций селектор задаёт сигнатуру, например `integer,real`, а `-` означает отсутствие параметров. Проверяются не только значения, но и статус результата, эффекты, чистота, причины блокировки C и представления выражений. Поэтому `TOP` после незавершённого анализа нельзя выдать за успешно доказанный результат.

Пример из [false_without_else.goat](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/analysis/false_without_else.goat) и [false_without_else.expect](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/test/analysis/false_without_else.expect):

```goat
var x = 0;
if (false) {
 x = 9;
}
var y = x;
```

```text
none write 3 1 x -
one summary 5 5 y int=0
```

Первое ожидание запрещает событие записи в недостижимой ветви. Второе требует единственную итоговую сводку `y = 0`; оно не требует полного совпадения всех остальных событий.

<a id="section-28-4"></a>

## 28.4. Функциональные и интеграционные проверки

[functional_testing.c](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/functional_testing.c) использует каталог случая с `program.goat`, необязательным `input.txt` и эталонами `expected_output.txt` / `expected_error.txt`. Отсутствие эталона означает пустой соответствующий поток. Сравнение игнорирует символы `\r`, но не произвольные пробелы. Наличие эталона ошибки требует ненулевого завершения; точное числовое значение кода не сравнивается.

В обычном режиме каждый случай запускается с `--optimize none` и `all`. Режим `compiled` проверяет отдельные компиляцию и запуск байткода; `auto` и `required` используют только `all`. На сбое сохраняются `actual_output_*` и `actual_error_*`. Для воспроизведения важны также stdin, язык сообщений и выбранный режим.

| Сценарий | Существенная проверяемая граница |
|---|---|
| `check_c_generation.sh`, `check_c_module.sh` | Числа и порядок вычисления после компиляции C |
| `check_native_abi.sh`, `check_native_loader.sh` | Формат адаптера, отказы, метаданные и выгрузка |
| `check_native_call.sh`, `check_native_pipeline.sh` | Вход через `CALL`, результат, ресурсный повтор |
| `check_native_modes.sh` | Совпадение поведения режимов и реальные счётчики |
| `check_binary_program.sh` | Повреждённые файлы, пары артефактов, запуск без компилятора |
| `check_native_library.sh`, `check_native_windows.sh` | Внешний компилятор, пути, зависимости и отказы сборки |

Проверки циклов охватывают вложенные `for`, оба направления вложения с `if`, тела без скобок, привязку `else` к ближайшему `if`, пустые части заголовка, ноль итераций, области объявлений, захват переменных отдельных итераций, возвраты, исключения, целочисленное переполнение, ошибочный синтаксис и исчерпание бюджета анализа. `scripts/check_for.py GOAT OUTPUT_DIR` дополнительно разбирает восстановленный исходник, исполняет сохранённый байткод и компилирует бесконечный цикл без его запуска. Скрипт запускает сохранённую нативную пару после удаления исходника и сокрытия компилятора, затем проверяет успешные нативные входы и ровно один ресурсный повтор. Он включён в CI Linux и Windows; набор проверки нативных режимов также сравнивает пример с циклами в `off`, `auto` и `required`.

<a id="section-28-5"></a>

## 28.5. Запуск и матрица CI

Из корня репозитория, при установленных GCC и CMake:

```sh
bash scripts/build.sh
```

Скрипт собирает Debug и запускает три основных исполнителя. Для Windows с MinGW и CMake в `PATH`:

```powershell
.\scripts\build_mingw.cmd
```

Это не полный набор отдельных интеграционных заданий CI. Например, ABI можно проверить дополнительно:

```sh
bash scripts/check_native_abi.sh build/goat build/native-abi
```

[build_and_test.yml](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/.github/workflows/build_and_test.yml) задаёт Linux с GCC и Clang, а также Windows с GCC в средах MINGW32, MINGW64 и UCRT64. Есть Debug и Release-проверки, компиляция с отсутствующим C++-компилятором на Linux, числовые проверки с `-fsanitize=undefined,float-cast-overflow` и отдельный GCC-вариант x87. Санитайзер — инструмент обнаружения определённых классов ошибок при исполнении; указанные проверки не означают, что вся программа всегда работает под санитайзером.

<a id="section-28-6"></a>

## 28.6. Что остаётся за пределами зелёного статуса

Проверка стиля требует clang-format 18 и обрабатывает отслеживаемые `.c`/`.h`. Лёгкая проверка Doxygen отклоняет предупреждения о некорректной документации, но не требует описания каждого параметра. Это проверки оформления исходников, а не содержания двуязычной книги.

> [!CAUTION]
> Текущая CI-конфигурация не проверяет автоматически смысловую эквивалентность русской и английской книги и не запускает все `docs/book/examples` как отдельный набор. При изменении книги требуется отдельно сверять ссылки, таблицы и примеры. Успешный CI также не доказывает корректность для всех программ, отсутствие всех утечек или поддержку платформ вне матрицы.

Для регрессии (возврата ранее исправленной ошибки) полезен небольшой случай с наблюдаемым отличием: граничное число, пропущенный эффект, неверный повтор, повреждённое поле. Проверка, которая только повторяет алгоритм реализации, может повторить и его ошибку. Сведения о составе сборки находятся в [CMakeLists.txt](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/src/CMakeLists.txt), правила оформления — в [check_style.sh](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/scripts/check_style.sh) и [Doxyfile.check](https://github.com/kniazkov/g0at/blob/cf51b8cb27a102d15260c7822ce503404462b0fd/scripts/Doxyfile.check).
