# 25. Выбор нативного выполнения и возврат к VM

<a id="section-25-1"></a>

## 25.1. Один вызов, два способа исполнения

Пользователь пишет обычный вызов `calculate(3)`. Выбор нативного кода не требует другого синтаксиса и не меняет значение переменной, содержащей функцию. Диспетчеризация (выбор конкретного способа выполнения вызова) происходит внутри уже знакомой инструкции `CALL`.

На этапе подготовки к инструкции `FUNC` привязывается дескриптор нативных специализаций. Когда VM создаёт объект функции, он получает ссылку на этот дескриптор вместе с обычными данными: параметрами, адресом байткода и замыканием. Байткод тела остаётся доступным, даже если есть нативная версия.

В [function.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/model/function.c) выбор производится до создания контекста байткодного вызова. Именно здесь сходятся результаты анализа, загруженная библиотека и реальные аргументы текущего исполнения.

<a id="section-25-2"></a>

## 25.2. Выбор по фактическим типам

К моменту `CALL` выражения аргументов уже вычислены и их объекты лежат на стеке VM. Диспетчер просматривает их, не извлекая: формальных аргументов должно хватать, а каждый использованный объект должен точно соответствовать метке `I64` или `F64` выбранной специализации.

Если подходящей записи нет, тело исполняется в VM. Целый аргумент не превращается в вещественный только ради подходящей нативной сигнатуры. Недостающий аргумент также не заполняется для нативного вызова: обычная VM свяжет его с `null`.

Лишние аргументы не препятствуют выбору специализации по формальным параметрам. Их выражения уже исполнились; отбрасывается только ненужное значение. Файл [25-dispatch.goat](../examples/25-dispatch.goat):

```goat
const identity = func(x) { return x; };
println(identity(3));
println(identity(1.5));
println(identity("text"));
println(identity());
println(identity(7, println("extra")));
```

Результат:

```text
3
1.5
text
null
extra
7
```

При успешной нативной подготовке числовые вызовы используют две специализации `identity`. Строковый вызов и вызов без аргумента остаются в VM. `extra` печатается один раз до входа в `identity`; чистота её тела не делает чистым выражение вызова вместе с аргументами.

<a id="section-25-3"></a>

## 25.3. Успех фиксируется после проверки результата

Перед вызовом адаптера требуемые числа копируются из объектов в массив значений ABI. Исходные объекты остаются на стеке. Счётчик `attempts` увеличивается непосредственно перед входом в адаптер.

При `OK` проверяются ожидаемый тип результата и нулевое резервное поле. Затем число упаковывается в обычный объект Goat, все фактические аргументы снимаются со стека с освобождением ссылок, результат помещается на стек, а указатель инструкции продвигается за `CALL`. Увеличивается `succeeded`.

До этой точки неуспешная попытка не поглощает аргументы. Это существенно для разрешённого повторного исполнения: VM может начать тело с теми же значениями, не вычисляя выражения аргументов заново.

<a id="section-25-4"></a>

## 25.4. Какие ресурсы ограничены

Обычный C-вызов использует машинный стек процесса. Нативная рекурсия поэтому не может бесконтрольно подменять последовательность контекстов VM. Защита работает на двух уровнях.

Перед входом в адаптер платформенная проверка требует не менее 512 КиБ запаса стека. Linux получает сведения о стеке потока через `pthread_getattr_np`, Windows использует `VirtualQuery`. Если запас не подтверждён, вызов направляется в VM без нативной попытки.

Внутри сгенерированного модуля действует отдельная защита:

| Ограничение | Текущее значение |
|---|---:|
| Одновременные входы в сгенерированные функции | 32 |
| Общий бюджет входов на один вызов адаптера | 4096 |
| Расстояние от отметки стека адаптера | 65 536 байт |
| Параметры + локальные + временные в одном определении | Не более 128 |

Бюджет входов расходуется и при последовательных вызовах, а глубина уменьшается при возврате. Таким образом, широкое дерево вызовов может исчерпать бюджет без большой глубины. Ограничение 128 проверяется при генерации, остальные — при исполнении.

Адаптер устанавливает локальное состояние защиты через потоковый указатель и `setjmp` (точку для нелокального возврата в C). Проверка входа при превышении лимита использует `longjmp`, после чего адаптер восстанавливает прежнее состояние и возвращает `RESOURCE_LIMIT`. Внутренние функции помечены `noinline`, чтобы внешняя оптимизация не устраняла предусмотренные границы кадров.

> [!CAUTION]
> Эти пределы — фиксированные ограничения текущего бэкенда, а не параметры языка. Защита не перехватывает произвольное повреждение памяти или аппаратное переполнение стека и не ограничивает общее время работы VM. Возврат в VM может продолжить длительное или незавершающееся вычисление.

<a id="section-25-5"></a>

## 25.5. Когда можно начать тело заново

Повтор разрешён при недостаточном подтверждённом запасе стека до входа, а после входа — при `RESOURCE_LIMIT` у записи с флагом `PURE`. Вторая проверка нужна потому, что часть тела уже могла выполниться. Чистая функция не оставляет внешних изменений, которые повторение продублировало бы.

Повтор начинается с начала байткодного тела, а не с места прерванного C-вызова. Уже вычисленные аргументы используются повторно. Новый контекст и его потомки получают признак `native_disabled`: рекурсивное продолжение не пытается снова войти в ту же нативную цепочку. Увеличивается `retries`.

Прочие отказы адаптера, в том числе несовместимость ABI, неверный результат или внешний отказ, не становятся поводом тихо выполнить тело второй раз. Исполнение завершается с ошибкой нативного бэкенда. Это отличается от отсутствия подходящей специализации, при котором нативная попытка вообще не начиналась.

Файл [25-fallback.goat](../examples/25-fallback.goat):

```goat
const count = func(n) {
    if (n <= 0) { return 0; }
    return count(n - 1) + 1;
};
println(count(100));
```

При обычном достаточном запасе стека команда:

```sh
./goat --native required --print-native docs/book/examples/25-fallback.goat
```

даёт:

```text
100

mode=required
preparation=ready
bound=1
omitted=0
attempts=1
succeeded=0
retries=1
```

Глубина нативного вызова достигает предела, после чего VM вычисляет `100`. Внутренние рекурсивные C-вызовы не являются отдельными `attempts`: отчёт считает пересечения границы VM/адаптер.

<a id="section-25-6"></a>

## 25.6. Что означают off, auto и required

| Режим | Подготовка | Отсутствие подходящей сигнатуры при вызове | Допустимый ресурсный отказ |
|---|---|---|---|
| `off` | Нативная подготовка пропускается | VM | Нативной попытки нет |
| `auto` | Неудача позволяет продолжить в VM | VM | Повтор в VM |
| `required` | Требуется хотя бы одна привязанная функция | VM | Повтор в VM |

`required` требует успешной подготовки, а не нативного исполнения каждого вызова. Поэтому пример рекурсии корректно завершается и в этом режиме. Подготовка без доступных функций получает `empty`; ошибка компиляции — `compile-error`, загрузки — `load-error`, привязки — `bind-error`. Есть также `io-error`. В `auto` отсутствие функций допустимо, а сбои подготовки сопровождаются диагностикой.

Для обычного исходного файла режим по умолчанию — `off`. Для `--run` сохранённого `.gbin` — `auto`. Нативная подготовка несовместима с `--optimize none`, потому что ей нужны доказательства анализа.

<a id="section-25-7"></a>

## 25.7. Как читать отчёт

`bound` считает привязанные функции, а не специализации; `omitted` — отклонённых кандидатов генератора. `attempts`, `succeeded` и `retries` описывают исполнение и суммируются по потокам VM. Если отказала предварительная проверка стека, возможен повтор без увеличения `attempts`.

Для примера `25-dispatch.goat` при нормальном запасе стека получаются `bound=1`, `attempts=3`, `succeeded=3`, `retries=0`. Два остальных вызова `identity` исполняются байткодно и не являются неуспешными нативными попытками. При `--compile` исполнения нет, поэтому счётчики вызовов нулевые даже после успешной подготовки.

Политика CLI и отчёт описаны в [native_execution.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/cli/native_execution.c); защита адаптера — в [c_adapter.c](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/src/codegen/c_adapter.c). [check_native_call.sh](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/scripts/check_native_call.sh) проверяет границу вызова, а [check_native_modes.sh](https://github.com/kniazkov/g0at/blob/8d1fe867ff5272d8d59a44785871f0db1b454df0/scripts/check_native_modes.sh) — режимы, эффекты и возврат в VM.
