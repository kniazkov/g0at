<a id="section-21-1"></a>

## 21.1. Доказательство становится изменением программы

Анализ может знать, что `2 + 3` равно `5`. Оптимизация делает следующий шаг: заменяет выражение узлом числа. Это уже изменение представления программы, поэтому недостаточно получить красивый результат в журнале. Должны сохраниться возвращаемые значения, порядок эффектов, исключения и возможность незавершения.

В [analysis.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/analysis/analysis.c) преобразования стоят после анализа функций, достижимости и классификации свойств. При `--optimize none` анализ заканчивается после связывания имён; эти оптимизирующие проходы не выполняются. Поэтому сравнение двух режимов позволяет наблюдать, что меняет оптимизатор.

Общий AST остаётся программой для всех её допустимых вызовов. Свойства одной нативной специализации не дают права изменить его так, будто других типов или аргументов не существует.

<a id="section-21-2"></a>

## 21.2. Недостижимый путь и ненужное вычисление

[reachability.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/analysis/reachability.c) отмечает поддеревья, которые не выполняются на доказанном пути. В `if` с известной истинностью одна ветвь может исчезнуть из байткода. Но вычисление самого условия не всегда можно убрать.

Если условие печатает строку и возвращает ложь, ложность не отменяет печать. Генератор в [if_else.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/graph/if_else.c) умеет сохранить вычисление нелитерального условия, удалить его результат через `POP` и оставить только выбранную ветвь. При `ABSTRACT_NEVER` остаётся само вычисление условия: оно не даёт нормального продолжения.

Для полной замены узла `if` выбранной ветвью требуется более сильное свойство: условие должно быть безопасно удаляемым. Проверка `can_discard_expression` специально отделена от знания истинности.

<a id="section-21-3"></a>

## 21.3. Свёртка констант

[simplification.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/analysis/simplification.c) обходит детей раньше родителя. Если скалярное выражение имеет доказанное значение и его вычисление можно заменить, создаётся соответствующий литерал. Целые и вещественные значения передаются прямо в конструкторы узлов, без печати и повторного разбора.

Проверяются чистота и состав поддерева. Вызовы, создание функций и блоки-объекты не принимаются как произвольно удаляемые скалярные операции. Вызов может выбросить исключение или не завершиться, даже если все его нормальные возвраты дают одну константу.

Для отложенного тела функции есть безопасный частный случай: замкнутое выражение только из литералов можно вычислить независимо от параметров. А вот `x + 1`, которое при исследованном вызове дало `5`, нельзя заменить на `5` в общем теле.

Если константа не доказана или путь прекратился, литерал не создаётся. Оптимизация должна уметь оставить выражение как есть — это обычный результат проверки, а не повод угадать значение.

<a id="section-21-4"></a>

## 21.4. Оригинал не исчезает

Замена хранится в специальном узле из [replacement.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/graph/replacement.c). Он связывает исходное и результирующее представления. Исполнение и генерация используют результат; исходная структура остаётся доступна для восстановления и отображения истории.

Это не глубокая копия всего дерева: поддеревья могут разделяться. Родительские ссылки приводятся к исполняемой структуре, а исторические связи не должны трактоваться как дополнительное владение независимыми копиями узлов. Память по-прежнему принадлежит арене.

Перед новым анализом `restore_graph` возвращает оригиналы на места замен и исправляет родителей. Затем сбрасываются прежние факты, области видимости и сводки строятся заново. Иначе повторный анализ мог бы принять результат прошлой оптимизации за исходную программу и потерять альтернативные пути.

Тесты [test_replacement.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/test/test_replacement.c) проверяют эти договорённости, включая восстановление. Правильный результат первого запуска ещё не доказывает корректность повторной обработки того же графа.

<a id="section-21-5"></a>

## 21.5. Факты одной специализации

У C-проверок свой набор точечных доказательств. Он относится к определённым типам параметров и хранится в сводке, а не как безусловная подмена общего тела. `c_expression_constant` возвращает константу только при известном представлении и разрешении удалить вычисление.

Например, сравнение двух целочисленных выражений может иметь доказанный результат внутри одной специализации. Генератор вправе использовать этот факт при выпуске её C-кода. Но из этого не следует, что исходная функция с другими допустимыми аргументами должна лишиться ветви в VM.

Равенство вещественных констант для такого доказательства учитывает знак нуля. `NaN` не проходит обычную проверку `a == b`, поэтому не сохраняется как согласованная константа этого механизма. Сохранение числового представления важно наряду с математической величиной.

> [!CAUTION]
> Общая свёртка намеренно ограничена и не выполняет произвольные пользовательские функции во время компиляции. Пустой флаг или несвёрнутое выражение не означают, что вычисление нельзя оптимизировать в принципе; это означает, что текущий механизм не получил необходимого разрешения.

<a id="section-21-6"></a>

## 21.6. Программа, в которой важно сохранить поведение

Файл [21-preservation.goat](../examples/21-preservation.goat):

```goat
if (1 + 2 == 3) { println("selected"); } else { println("dead"); }
const signal = func() { println("effect"); return 0; };
if (signal()) { println("unselected"); }
const step = func(x) {
    if (x < 0) { return 0; }
    return x + 1;
};
println(step(4));
println(step(-4));
var count = 0;
const pair = func(a, b) { return a * 10 + b; };
println(pair(count++, count++));
try { println(1 / 0); } catch (error) { println(error); }
println(-0.0);
```

В обоих режимах оптимизации результат:

```text
selected
effect
5
0
10
DIVISION_BY_ZERO
-0
```

Первое условие вычисляется из литералов; ветвь с `dead` не нужна. Вызов `signal` должен сохранить строку `effect`. Пользовательский вызов здесь не получает глобального константного результата в проходе достижимости, поэтому сам факт, что он возвращает ноль, не позволяет удалить его.

Два вызова `step` проверяют, что общий код не стал специализированным для первого аргумента `4`. `pair` проверяет вычисление аргументов справа налево: первый параметр получает `1`, второй — `0`. Обработчик деления на ноль подтверждает, что исключение сохраняется при оптимизации. Последняя строка показывает текущий формат печати отрицательного вещественного нуля — `-0`.

<a id="section-21-7"></a>

## 21.7. Как сопоставить представления

Из корня репозитория можно посмотреть восстановленный текст в двух режимах:

```sh
./goat --optimize none --print-source-code docs/book/examples/21-preservation.goat
./goat --optimize all --print-source-code docs/book/examples/21-preservation.goat
```

```powershell
.\goat.exe --optimize none --print-source-code .\docs\book\examples\21-preservation.goat
.\goat.exe --optimize all --print-source-code .\docs\book\examples\21-preservation.goat
```

Эти команды также исполняют программу, поэтому после восстановленного текста следует её вывод. Для сравнения инструкций используется `--print-bytecode`. Тексты двух представлений могут различаться; сравнивать нужно сохранение поведения, а не требовать одинакового листинга.

Тесты [test_c_replacement.c](https://github.com/kniazkov/g0at/blob/b1f72ad8ccd273427f256243ad4d1625ced37a77/src/test/test_c_replacement.c) проверяют использование констант в C-представлении, а функциональные примеры позволяют сопоставлять результат с оптимизациями и без них. При работе с ошибками существенны также `stderr` и код завершения, а не только успешный вывод.

<a id="section-21-8"></a>

## 21.8. Что передаётся нативному бэкенду

К концу части IV программа прошла несколько разных проверок. Абстрактные значения описали возможные результаты; состояния — изменения привязок; граф — зависимости вызовов; эффекты — взаимодействие с окружением; C-проверки — допустимые представления и тела. Упрощение воспользовалось только теми фактами, которые разрешают менять соответствующее представление.

Эта последовательность не делает анализатор всеведущим. Она даёт явные границы: что доказано, что не завершено и что пока не поддерживается. Часть V начинается там, где для выбранной специализации уже получен допуск: с формирования C-модуля, который обязан сохранить установленные правила Goat.

### Удаление неиспользуемых привязок

После замены скалярных выражений и ветвей дополнительный проход учитывает чтения в исполняемом дереве. Архивные оригиналы не удерживают привязку от удаления. Ссылки сопоставляются по идентичности объявления, поэтому одинаковые имена в разных областях не смешиваются; чтения из вложенных функций тоже учитываются. Простое присваивание изменяемой переменной считается записью, а операция вроде `++` читает прежнее значение. Присваивания константам сохраняются, поскольку их ошибка наблюдаема.

Если у привязки не осталось чтений, проход удаляет её хранение. Инициализатор, который доказанно можно отбросить, исчезает вместе с ним. Иначе инициализатор остаётся выражением-оператором: сохраняются вызовы, побочные эффекты, исключения и порядок вычисления. Простые записи в удалённую переменную заменяются правой частью; присваивание с отброшенным результатом и безопасно удаляемым вычислением ничего не генерирует. Проход повторяется, пока привязки не перестанут исчезать. Поэтому удаление неиспользуемого замыкания может разрешить удаление его захватов на следующем проходе.

Узлы удаления выражения и удаления оператора имеют по одному ребёнку — архивному оригиналу. Они не генерируют байткод, включая отложенные тела функций. Узел удаления выражения используется только там, где результат отбрасывается, поэтому окружающий оператор не генерирует `POP`. Перед новым анализом восстановление разворачивает и удаления, и замены.

Например, `a=2; b=3; x=a+b; println(x);` оставляет только `ILOAD32 5`, `VLOAD "println"`, `CALL 1`, `POP` и `END`. Индекс `println` в сегменте данных может измениться, поскольку удалённые имена больше не занимают записи.

> [!CAUTION]
> Одна чистота не доказывает завершение вычисления и отсутствие исключений. Вызовы сохраняются, если их уже не удалило существующее более строгое преобразование. Операции, читающие прежнее значение, и привязки в блоках-объектах обрабатываются консервативно. Этот проход удаляет хранение в VM; нативная генерация может сохранить исходные операции, поскольку её доказательства для всей сигнатуры построены до удаления. Восстановленный текст объявлений сохраняет архивную форму, в том числе в смешанных списках объявлений и заголовках циклов; само удаление хранения видно в графе и байткоде.
