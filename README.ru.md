# Язык программирования Goat

[![Сборка и тесты](https://github.com/kniazkov/g0at/actions/workflows/build_and_test.yml/badge.svg)](https://github.com/kniazkov/g0at/actions/workflows/build_and_test.yml)

**Goat — экспериментальный язык программирования, реализованный на C, с байткодовой виртуальной машиной, статическим анализом и нативным бэкендом.**

Проект Ивана Князькова служит для исследования устройства языков программирования и даёт работающие примеры для технических обсуждений и консультаций. Исходный код позволяет проследить путь программы от текста до исполнения.

## Пример на Goat

Функции являются значениями. Внутренняя функция может сохранять доступ к окружающей области видимости (замыкание):

<!-- readme-closure -->
```goat
const add = func(a) {
    return func(b) {
        return a + b;
    };
};
const add_two = add(2);
println(add_two(3));
```

Результат: `5` с переводом строки. Другие программы находятся в [примерах книги](docs/book/examples) и [функциональных тестах](test/functional).

Цикл в форме языка C использует те же значения и области видимости:

<!-- readme-loop -->
```goat
var sum = 0;
for (var i = 0; i < 5; i++) sum = sum + i;
println(sum);
```

Он выводит `10`. Части заголовка могут быть пустыми; тело может быть одиночным оператором или блоком. [Глава 2](docs/book/ru/02-implemented-language.md) описывает области видимости и управление исполнением, а [глава 22](docs/book/ru/22-c-code-generation.md) показывает нативный числовой цикл.

Goat поддерживает динамически типизированные значения, лексические области видимости, функции и рекурсию, условные ветвления и `switch`, циклы `for`, `while` и `do…while` с `break`/`continue`, объекты на основе блоков, исключения, массивы, наследование прототипов, include/import, модификаторы файлового/модульного доступа, потоки программы, математические функции и ввод-вывод. Статический анализ отслеживает приближённые значения, вызовы функций, эффекты и скалярные специализации. Подходящие функции можно перевести на C и исполнять как машинный код через разделяемую библиотеку (нативное исполнение).

> [!CAUTION]
> Goat — экспериментальная реализация. Циклы, индексный доступ, свойства и модульная система реализованы; [пример модулей](docs/book/ru/30-modules.md) проверяет сборку, запуск, просмотр и объединение. Нативная генерация охватывает только доказанно подходящие специализации, а не все конструкции; VM остаётся запасным исполнителем. Книга указывает реальные ограничения реализации и [переносимости](docs/module-delivery-tests.md), не выдавая невыполненные проверки нижних границ ОС за успешные.

## Сборка и запуск

Получите репозиторий и перейдите в его каталог:

```sh
git clone https://github.com/kniazkov/g0at.git
cd g0at
```

### Linux

Установите GCC или Clang, GNU Make, Bash, CMake версии 3.13 или новее и стандартные библиотеки для разработки на C, включая pthread и libm. Нативные Linux-backend поддерживают glibc и musl на x86-64 и AArch64; Goat и его нативные модули должны соответствовать одному семейству runtime. Установка второй libc не меняет runtime уже собранного процесса Goat. На Alpine перед теми же командами сборки установите `build-base`, `cmake`, `bash`, `python3` и `linux-headers`. Обычным пользователям glibc устанавливать musl не требуется.

```bash
bash scripts/build.sh
./goat example/hello_world.goat
```

Скрипт Debug собирает `goat`, `goat-inspect`, `goat-merge` и компонентные тесты в `build`, копирует только `goat` в корень репозитория и запускает строгие проверки JSON модулей, unit-тесты, тесты анализа и функциональные тесты исполнения. Полная интеграционная матрица CI им не запускается. Пример выводит `it works!`.

Компиляция идёт параллельно, по умолчанию с числом логических CPU. Положительный аргумент ограничивает число заданий (`1` собирает последовательно):

```bash
bash scripts/build.sh 8
```

Оба скрипта Debug также принимают `CMAKE_BUILD_PARALLEL_LEVEL` как число заданий по умолчанию; явный аргумент имеет приоритет. Тесты запускаются последовательно. Справка доступна через `--help`.

Для Clang с отдельным каталогом сборки:

```bash
CC=clang BUILD_DIR=build/clang bash scripts/build.sh
```

Для сборки Release без запуска тестов:

```bash
bash scripts/build_release.sh
```

Исполняемый файл Release помещается в `build/release` и копируется в корень репозитория. Этот скрипт также учитывает `CC` и `BUILD_DIR`. В Release отключены собственный учёт выделений памяти и защитные проверки (`MEMORY_DEBUG`); в Debug они сохранены.

### Windows (MinGW)

Установите CMake версии 3.13 или новее и комплект MinGW с GCC, `mingw32-make` и поддержкой pthread, доступный через `PATH`. В PowerShell из корня репозитория:

```powershell
.\scripts\build_mingw.cmd
.\goat.exe .\example\hello_world.goat
```

Скрипт Debug собирает интерпретатор, оба инструмента модулей и компонентные тесты в `build`, копирует только `goat.exe` в корень и запускает те же проверки JSON и три основных набора тестов. Для выбора числа параллельных заданий:

```powershell
.\scripts\build_mingw.cmd 8
```

Без аргумента используются `CMAKE_BUILD_PARALLEL_LEVEL`, затем `%NUMBER_OF_PROCESSORS%`. Для сборки Release без тестов:

```powershell
.\scripts\build_release_mingw.cmd
```

Он создаёт `build\release\goat.exe` и копирует его в корень репозитория.

Релизные скрипты также создают переносимый архив в `<каталог сборки>/packages`
(`.tar.gz` на Linux, `.zip` на Windows). В нём находятся `bin/goat`, `bin/goat-inspect`, `bin/goat-merge` (с `.exe` на Windows), публичные
нативные заголовки, статическая библиотека поддержки, примеры, лицензия и [инструкция](docs/package/README.md).
CI проверяет распакованный архив и публикует его как артефакт `goat-*`.
Для локальной проверки нужны Python 3 и C-компилятор подходящей архитектуры:

```sh
python3 scripts/check_package.py build/release/packages
```

Проверка переносит пакет за пределы репозитория, компилирует C только с его
публичными заголовками, проверяет экспорт C и сборку нативных модулей. Затем
запускает сохранённые VM/нативные программы без их исходников и с недоступным
C-компилятором.


### Нативное исполнение и сохранённые программы

Отдельный `.goat` по умолчанию использует `--native off`; исполнение на VM не требует C-компилятора. Готовый бинарный вход по умолчанию использует `auto`; `.gmod` берёт режим из описания (по умолчанию `auto`) и цель (по умолчанию `host`). Для сборки/запуска модулей без компилятора явно задайте `--native off`. Чтобы проверить нативное исполнение и посмотреть отчёт:

```bash
./goat --native required --print-native docs/book/examples/22-native-module.goat
```

В PowerShell замените `./goat` на `.\goat.exe`. Нативная подготовка требует совместимого C-компилятора. `--cc` выбирает одно имя или путь к исполняемому файлу без флагов оболочки; отдельный исходник также учитывает `CC`, который перекрывается `--cc`. Сборка модулей проверяет поддерживаемые toolchain из PATH; `--list-native-targets` показывает реально успешные цели, а не просто известные имена. Недоступная явная цель вызывает ошибку, а не молча заменяется на host. См. [правила нативной сборки](docs/module-build-api.md).

Для отдельного исходника `required` требует хотя бы одну привязанную нативную функцию, а `auto` разрешает переход на VM при предусмотренных отказах подготовки. Нативная подготовка требует анализа (`--optimize all`, значение по умолчанию). Модули сохраняют обязательный анализ интерфейса даже с `--optimize none`; `required` проверяет совместимую специализацию собственных файлов корня, а не только его зависимостей. **Ни один режим не требует нативности каждого вызова.** Применимые библиотеки модулей загружаются лениво; повреждения артефактов и обнаруженные нарушения ABI не допускают молчаливого fallback или повтора. См. [нативную загрузку](docs/module-loading-api.md).

Чтобы сохранить байткод без исполнения программы, а затем запустить его:

```bash
mkdir -p build/quickstart
cp docs/book/examples/22-native-module.goat build/quickstart/program.goat
./goat --compile build/quickstart/program.goat
./goat --run build/quickstart/program.gbin
```

Эквивалент для PowerShell:

```powershell
New-Item -ItemType Directory -Force .\build\quickstart | Out-Null
Copy-Item .\docs\book\examples\22-native-module.goat .\build\quickstart\program.goat
.\goat.exe --compile .\build\quickstart\program.goat
.\goat.exe --run .\build\quickstart\program.gbin
```

В этом примере нет include/import, поэтому используется отдельный бинарный путь. Добавление `--native required` в его команду компиляции также создаёт сопутствующую библиотеку `.so` или `.dll`. Храните её рядом с `.gbin` с одинаковым базовым именем. Для исполнения сохранённой пары не нужны ни исходный текст, ни компилятор C. Правила совместимости и обработки ошибок описаны в главе [«Раздельная компиляция»](docs/book/ru/26-separate-compilation.md).

Сгенерированный нативный C использует [библиотеку поддержки](docs/native-runtime.md). `--save-c` экспортирует её заголовки и `libgoat_native.a` рядом с C-файлом; автоматическая компиляция DLL/SO подготавливает и связывает соответствующий архив из комплекта интерпретатора.

[Устройство модели](docs/model-layout.md) описывает разделение хранения значений, прототипов и адаптеров встроенных методов (русский и английский).

### Модули: сборка, запуск, просмотр и объединение

Модульная система v1 реализована. Строгий JSON `.gmod` задаёт имя, точную версию и главный исходник. `include` соединяет исходные файлы с раздельными областями; `import` использует готовый модуль с точной версией зависимости. Объявления без модификатора доступны своему файлу, `public` — своему модулю, `external` — другим модулям; `protected`/`private` сохраняют правила объектных областей. Вызывающий не передаёт свои полномочия вызываемой функции. См. [пример и формат](docs/book/ru/30-modules.md).

Сборка модуля публикует один детерминированный ZIP `.gbin` с метаданными, переносимым байткодом и необязательными нативными вариантами. Она не исполняет инициализаторы и не загружает DLL/SO. Запуск `.gmod` собирает в памяти без публикации; готовому ZIP не нужны исходники или компилятор, но используемые архивы зависимостей должны быть доступны для поиска. ZIP-модули **не** используют описанную выше схему соседней библиотеки отдельной программы. Старый платформенно-зависимый формат `GOATBI11` не принимается: пересоберите старые артефакты.

Попробуйте готовый учебный пример из двух модулей в рабочей копии. После обычной сборки Debug, из корня репозитория:

```bash
export PATH="$PWD/build:$PATH"
mkdir -p build/quickstart/modules
cp -R docs/book/examples/30-modules/. build/quickstart/modules/
cd build/quickstart/modules
```

Подготовка PowerShell (из корня репозитория):

```powershell
$env:PATH = "$PWD\build;$env:PATH"
New-Item -ItemType Directory -Force .\build\quickstart\modules | Out-Null
Copy-Item .\docs\book\examples\30-modules\* .\build\quickstart\modules\ -Recurse -Force
Set-Location .\build\quickstart\modules
```

Затем выполните одинаковые команды на любой платформе:

<!-- module-book-cli -->
```sh
goat build geometry.gmod --native off
goat build app.gmod --native off
goat run app.gmod --native off
goat run modules/tutorial/1.0.gbin --module-dir modules --native off
goat-inspect --json --module-dir modules modules/tutorial/1.0.gbin
goat-merge merged.gbin modules/geometry/1.0.gbin
```

Обе команды запуска печатают `25`. `--module-dir modules` явно указывает поиск зависимостей; корень хранилища не угадывается по вложенному пути архива. Здесь merge принимает один источник; несколько источников добавляют совместимые нативные варианты той же основной сборки. Конфликты скалярных информационных полей отклоняются. Несколько непустых списков авторов требуют интерактивного выбора порядка; без нужного ввода слияние завершается ошибкой, не заменяя назначение.

`goat-inspect` проверяет полный граф зависимостей и показывает метаданные; **совместимые локальные нативные библиотеки также могут проверяться в изолированных подпроцессах с исполнением конструкторов**. `--target PROFILE.json` выбирает профиль среды; чужой профиль анализируется без локальной загрузки, но профиль, совпадающий с текущей средой, по-прежнему допускает пробы. Изоляция процесса не является защитной песочницей для вредоносного нативного кода. `goat-merge` никогда не исполняет байткод и не загружает библиотеки; внешние архивы зависимостей ему не нужны. См. [inspect](docs/module-inspect-api.md) и [merge](docs/module-merge-api.md).

Перед следующими командами вернитесь в корень репозитория (`cd ../../..` или `Set-Location ../../..`). Для нестандартного каталога сборки используйте в PATH его; релизный пакет содержит все три инструмента в `bin`.

## Наблюдение и тестирование

Для отдельных исходников `--print-source-code`, `--print-bytecode` и `--print-analysis` показывают промежуточные представления; эти параметры также запускают программу. `--save-graph graph.svg` сохраняет изображение AST и требует Graphviz (`dot` в `PATH`). `--print-c` экспортирует сгенерированный C без исполнения программы. Модульный вход пока явно отклоняет экспорт C/исходника/анализа/графа; для метаданных и диагностики графа используйте `goat-inspect`. Полные примеры приведены в главе [«Средства наблюдения»](docs/book/ru/27-observability.md).

Скрипты Debug запускают строгие проверки JSON модулей и три основных набора; полный CI дополнительно выполняет компонентные/интеграционные проверки форматов, графов модулей, доступа, инициализации, нативного ABI/сборки/загрузки, потоков, exit, inspect/merge, поставки и двуязычного учебного примера. Исходные семь платформенных заданий охватывают Linux/glibc GCC/Clang на x86-64 и AArch64, Windows MINGW32/MINGW64/UCRT64. Два дополнительных задания Alpine на настоящих x86-64 и AArch64 проверяют Linux/musl, включая перенесённые Release-пакеты и выбор модулей разных libc. Стиль, Doxygen и эталоны форматов проверяются отдельно. См. [главу о тестировании](docs/book/ru/28-testing.md) и [workflow](.github/workflows/build_and_test.yml).

Целевая проверка учебных примеров книги/README после сборки (нужен Python 3):

```sh
python3 scripts/check_module_book.py build/goat
```

На Windows используйте `python scripts/check_module_book.py build/goat.exe`. Проверяются документированные примеры и локальные ссылки, а не все возможные программы или смысловая эквивалентность всей прозы. Проверки производительности Release описаны в [инструкции бенчмарков](test/performance/README.md).

Утверждения о переносимости ограничены свидетельствами: текущий CI исполняет перенесённые программы native/VM, реальные смешанные Windows CRT-варианты, контрольные модули на glibc 2.35/2.36 и musl-модули на версии runtime, использованной при линковке. Нижняя граница musl консервативна; исполнение на более старой musl не заявляется. Обычные заявленные границы glibc 2.14/2.17 и реальное исполнение на Windows 10 **ещё не подтверждены** на этих точных системах. [Свидетельства поставки и план проверки](docs/module-delivery-tests.md) отделяют ограничения проверки от реализованных возможностей. Метаданные совместимости native ELF/PE не являются гарантией для любого хоста или самого исполняемого файла интерпретатора.
