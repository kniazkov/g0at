# Полный локальный прогон

[English](full-check.md)

Linux: `bash scripts/build.sh --full-check 4`.
Windows cmd/PowerShell: `scripts\build_mingw.cmd --full-check 4`.
Можно запускать из другого каталога, указав путь к скрипту. Число задаёт параллелизм
сборки и CTest; без него действует существующий выбор из окружения/числа CPU.
CTest соблюдает последовательность замеров производительности и блокировки ресурсов.
При работе параллельно с другими приложениями разумно начать с 4.

Обычный режим, `--build-only` и `--test-only` сохраняются. `--full-check` — отдельный
режим: всегда конфигурирует, собирает и проверяет Debug и Release. Каталог быстрой
сборки не меняется. После успешного завершения всех проверок Release-утилиты
`goat`, `goat-inspect` и `goat-merge` публикуются в `target/` (с `.exe` в Windows).
При падении проверки предыдущая публикация сохраняется; ошибка публикации
завершает весь прогон с ошибкой.

Все сборочные этапы, включая санитайзеры, пакеты, инъекцию отказов и отдельные
генераторы, используют ту же синхронизацию вывода, что и обычные скрипты. GNU Make
4.0+ буферизует задания через `--output-sync=target`; Ninja использует собственную
буферизацию без ключей Make. Сообщения могут появляться после завершения задания.
Предупреждения, ошибки и число параллельных заданий сохраняются.

## Зависимости

- CMake/CTest не ниже 3.21, Bash, Git, поддерживаемый GCC/Clang и обычные утилиты
  окружения сборки (в том числе diff для shell-проверок).
- Linux: библиотеки санитайзеров и компилятор с
  `-ftrivial-auto-var-init=pattern`, как в CI. Неподдерживаемый компилятор приводит
  к явному отказу соответствующего этапа, а не к молчаливому уменьшению охвата.
- Windows: выбранное окружение MSYS2 MinGW (MINGW32, MINGW64 или UCRT64), его
  компилятор, CMake и make в PATH, доступный MSYS2 Bash. Режим не предназначен
  для чистого MSVC или WSL Bash. Для поставки модулей дополнительно нужны GCC
  MINGW64 и UCRT64. Они находятся через MSYS2; можно явно задать абсолютные пути
  в `GOAT_DELIVERY_MINGW64_CC` и `GOAT_DELIVERY_UCRT64_CC`. Отсутствие этих
  компиляторов обнаруживается до сборки.
- clang-format **18** с именем `clang-format-18`, Doxygen и Graphviz включают
  необязательные проверки стиля, документации и графов. Если инструментов нет,
  CMake/CTest явно отмечают проверки как отключённые. Успех без них не означает
  полный охват инструментальных проверок.

`CC` выбирает один исполняемый файл компилятора, без shell-флагов.
`FULL_CHECK_DIR` задаёт отдельный корень сборок; относительный путь считается от
репозитория. По умолчанию это `build/full-check-<host>-<compiler>`, в Windows
добавляется `MSYSTEM`, если он задан. Для разных toolchain используй разные корни:

```sh
CC=clang FULL_CHECK_DIR=build/check-clang bash scripts/build.sh --full-check 4
```

В PowerShell перед запуском `.cmd` задай `$env:CC` / `$env:FULL_CHECK_DIR`.
Скрипт не устанавливает пакеты и не удаляет старые рабочие каталоги.

## Охват

| Этап | Проверки |
| --- | --- |
| Debug | Все зарегистрированные CTest, кроме Release-замера и пакета; в Linux отдельно собираются исключённые из обычной сборки sanitizer-раннеры |
| Release | Допустимые для Release метки из CI, форматы и замороженные образцы, нативные режимы, сохранённые программы и последовательный замер производительности |
| Пакет | Создание архива, повторная конфигурация для регистрации теста, перенос и запуск через Release- и Debug-хосты |
| Нехватка памяти | Отдельные Debug/Release с `GOAT_TEST_ALLOC_FAILURE=ON` |
| Инициализация стека | Linux-проверки JSON/хеша с ненулевым заполнением автоматических переменных |
| Генераторы | Автономная конфигурация/сборка/проверка Unicode и схем модулей без сборки интерпретатора |

Release намеренно не запускает все отладочные хосты: часть использует `assert`
как механизм проверки. Метки совпадают с CI; регрессионный тест обнаруживает их
расхождение. Функциональные проверки нативного Release используют Debug-раннер,
как в CI. Новые зарегистрированные Debug-тесты подхватываются автоматически.

За пределами режима: другие архитектуры/компиляторы, контролируемые Docker-среды
минимальной glibc и пары glibc/musl, загрузка/хранение артефактов GitHub и требование
чистого checkout (локально могут быть твои правки). Обычные libc-контроли запускаются;
случаи с реальной парой явно пропускаются без внешних артефактов. Команда приближает
CI одной платформы, а не заменяет всю матрицу.

## Результаты и ошибки

Этапы выводятся в консоль; итог записывается в `<корень-сборки>/summary.txt`.
CTest сохраняет `<конфигурация>/<этап>.log`, обычные `Testing/Temporary` и каталоги
провалившихся сценариев. При следующем запуске журналы заменяются; для сравнения
прогонов предварительно скопируй их.

Независимые этапы продолжаются после ошибки; тесты не запускаются для неудавшейся
сборки. Любая неуспешная команда даёт ненулевой итоговый код. Отключённые/пропущенные
тесты видны в журналах отдельно от PASS этапов. Автоматических повторов нет;
ошибки очистки не скрываются. Известное падение Windows module-delivery может
воспроизвестись и локально.

Регрессионные проверки запуска: `cmake -P test/full_check_driver.cmake`.
Они выполняют настоящий драйвер на маленьком проекте с пробелами в путях,
проверяют отбор Release, регистрацию пакета, передачу ошибок и продолжение
независимых этапов. CI запускает их в Linux и Windows; полного рекурсивного
прогона Goat внутри этих проверок нет.
